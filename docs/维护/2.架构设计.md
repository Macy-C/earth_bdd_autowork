# 2. 架构设计

本文说明框架目录、执行链路和各层职责。

## 目录结构

```text
.vscode/
  settings.json           # 当前文件右键运行的项目根与导入路径
  launch.json             # 当前文件右键调试配置

Bdd/
  README.md               # 当前宿主的安装、生命周期与运维入口
  docs/                   # 当前宿主的评测账本和项目说明
  ai/                     # 当前宿主的项目身份、长期 Knowledge 和可移植知识
  environment.py          # behave 薄入口，实际逻辑在 autowork_core/runtime
  application.py          # 当前宿主的应用启停、辅助资源和页面就绪编排
  runner.py               # 正式用例薄入口，运行 Bdd/features
  local_runner.py         # 本地调试薄入口，运行 Bdd/test_features
  debug_tools.py          # 定位、OCR/PIC 和操作录制调试工具入口
  features/               # 正式 feature
  test_features/          # 本地调试 feature
  steps/                  # 业务 step 和调试 step
  page_obj/               # 页面对象，写脚本时主要编辑
  integrations/           # 产品 API wrapper 及其紧邻二进制依赖
  resources/              # 产品脚本等宿主运行资产
  tests/                  # 宿主启停、Page Object、设备和真实组合测试
  locators/               # locator yaml
  data/                   # 测试数据、图片模板等用例资产

autowork_core/
  actions/                # 通用 UI 动作，不写业务含义
  common/                 # locator、OCR/图片引擎、变量、日志、xpath 等底层能力
  page/                   # BasePage、get_page 等页面基类
  runtime/                # behave 生命周期钩子、runner 实现
  utils/                  # 通用工具、截图录屏和运行时视觉反馈
    overlay.py            # 运行时与调试 GUI 共用的透明覆盖层
    visual_marker.py      # OCR/PIC/POS 命中位置短暂标记
    debug_tools/          # 定位、OCR/PIC 和录制调试 GUI
      recorder/           # Feature/Step 计划、输入采集、控件证据、视频和 AI 产物协议

config/
  config.yaml             # 运行配置
  paths.py                # 路径常量
  settings.py             # 配置加载

resources/                # OCR、ffmpeg 等框架通用资源
requirements.txt          # 框架及随仓库交付集成的Python包依赖
artifacts/                # logs、reports、screenshots 输出产物
ai/                       # 可随框架完整替换的 Context、Prompt、Instruction、Schema 和 Policy
docs/                     # 框架文档
framework_validation/     # tests、fixtures、evaluations、ignored output/history
```

`framework_validation`不属于生产包，也不随框架同步到宿主项目。依赖方向只能是
`framework_validation -> autowork_core`；Recorder、运行时、Bdd和生成协议不得反向导入
验证资产，也不得把评测manifest作为工作流状态源。通用模拟窗口属于fixtures；Vela、
Gantry和真实设备验收继续由宿主项目拥有。框架测试使用临时目录；评测输出和历史cx工作区
只进入`framework_validation/output/`，项目级`artifacts/`只保存宿主运行产物。

Project Context Hygiene 属于项目级 Agent 协作呈现层，只负责可逆输出摘要、语义
里程碑识别和独立 Epic 边界。Recorder Adaptive Work Loop 在其上增加 owner 假设、
验证新鲜度、威胁检查和回归节奏；Shadow Companion 在有价值里程碑写一个本地
Capsule，并由 SessionStart Hook 只注入校验后的恢复指针。三层由薄发现入口
`.github/copilot-instructions.md`、权威 `ai/context/project.md` 和 `ai/manifest.json`
能力守卫共同定义。Companion 不增加服务、数据库或测试缓存，也不被 Recorder runtime
依赖；Hook 不推理业务语义、不生成摘要或修改工程文件。

## VS Code 文件级运行环境

框架源码不负责修改 `sys.path`。需要直接运行或调试任意深层 Python 文件时，由 VS Code 在启动解释器前提供项目根：

```text
右键运行/调试当前文件
  -> bdd_autowork 作为独立 workspace folder
  -> cwd = ${workspaceFolder}
  -> PYTHONPATH = ${workspaceFolder}
  -> 执行当前 ${file}
```

`.vscode/settings.json` 负责右键“运行 Python 文件”，`.vscode/launch.json` 中带 `debug-in-terminal` purpose 的配置负责右键“调试 Python 文件”。两者都使用工作区变量，不绑定机器绝对目录；框架移动后，只需把新位置的 `bdd_autowork` 重新作为多根工作区文件夹加入。

该配置保证项目绝对导入可解析，不会改变文件本身的执行语义。只定义类或函数的文件可以成功加载，但不会自动调用其中的函数；调试具体函数仍需测试、调用代码或 `if __name__ == "__main__":` 调试段触发它。

## Recorder V3 证据与生成架构

Recorder 只保留一条生成主链：

```text
CaptureSession
  -> EvidenceSnapshot（Evidence Graph 2.4 + Evidence Context 2.3；兼容旧版本）
  -> immutable RequestV3 + Execution Profile 1.0
  -> Semantic Pack 6.1（兼容读取 5.0-6.0；facts、候选、typed Observation Intent、semantic control state、effects、window causality、PIC audit）
  -> Semantic Reconciliation（全量分类、typed ambiguity、Brief 4.4 agent_tasks）
  -> Decision Pack 5.8 / Answers 5.1（用户业务 outcome + 白话呈现；兼容读取Pack 5.7 + Answers 5.0配对）
  -> GenerationDesignV1（业务概念 + operation + value/table/reuse/runtime关系）
  -> deterministic Design + Proof Compiler
  -> GenerationPlanV4.2（系统证明 + ownership + Scenario runtime binding + Contract lease；兼容读取3.0-4.1）
  -> AI Plan Context 1.1（内容寻址的再生成纯投影；不落盘）
  -> GenerationTransactionV3 + Implementation Manifest 1.7（AI/system文件所有权、预检ledger、恢复基线与lease）
  -> AI实现 + Plan-to-Code审计
  -> Code Manifest 1.0（从同次Plan-to-Code audit投影实际代码）
  -> Bdd/ai/knowledge（确认经验、结果、反馈和Capability）
```

Generation Brief 4.4 的`scenario_intelligence`是纯投影而非新事实源，并支持Annotation
Model 3.0：新Step只保存单一`business_context`；普通F9默认是中性系统观察，只证明目标和
运行时状态。Feature/Examples/Table声明本身是业务权威，不要求用户通过F9再次授权。规格来自冻结的
Feature/Rule/Background/Outline/Examples，示范来自当前 Take，参考案例来自带质量画像
的当前代码与 confirmed Capability，缺口来自 typed ambiguity/conflict。Semantic Pack
5.9 可引用显式、内容寻址的结构化 Observation receipt；默认采集行为不变，Provider
只能按需运行。Scenario Intelligence 1.1 通过 `coverage_manifest` 保留每个有动作的目标
Step、gap引用Action和每个含gap Step的轻量索引，并列出被省略Action/gap/Observation
的稳定ID和展开来源。

Brief 4.4不在episode中复制Action semantics，也不在Action和ambiguity间重复完整候选事实；
默认上下文保留ID、目标指纹、冻结effect/after_state、evidence-bound assertion参数和
coverage，不暴露operation hypothesis、数值排名或自动related set。详细事实从冻结
Reconciliation/Evidence按需展开。该投影不改变Plan校验输入的身份或安全门。

Brief 4.4 不包含规则生成的operation草案。`agent_tasks`只提供Step/Action索引、
typed ambiguity和调查工具；AI按需调用`generation_workflow evidence`或
`compare-takes`核对事实，再提交GenerationDesignV1。系统从冻结target Action、值权威、
table/reuse/runtime关系确定性派生Scenario Model、路径、Plan证明与目标指纹，并把原Design
及编译后的Plan分别纳入内容指纹。旧Plan形状Intent仍可兼容读取。

Evidence Graph 2.4为每个Action保存Canonical Action 1.0：`command`只来自原始操作事件，
`observed_after`只保存运行时结果，`business_expectation`只接受规格或用户权威。键盘命令由
结构化按键事实表达且不包含pywinauto字符串；只有AI选择`send_text_keys`后，Plan编译适配器
才生成当前运行时参数。不能使用最终文本替代按键，也不能把观察结果升级为业务期望。Request中的
Execution Profile 1.0默认禁止运行；只有显式attach或明确launch命令可在完整Transaction
验证后进入Runner，未配置时结果为静态已验证、运行未执行。

Window owner把录制`evidence_root`与公开`public_name`分开。内部Root和owner ID继续绑定
证据；新建Page包、Page类、locator包和公开Root只从稳定ASCII业务slug派生。录制Root含
机器身份后缀时，GenerationDesign必须显式给出`business_name`；复用候选的公开资产若已
泄漏该后缀则拒绝复用，避免把临时录制身份固化为长期业务API。

只有发生过矫正的Action才携带紧凑`correction`来源。它保留补录原Action ID或有界merge
来源ID，完整补录路径、时间线edit信息、媒体和merge快照仍留在effective evidence。

AI 在 PlanV4.2 的 `scenario_model` 中完成业务建模：按 Feature 顺序覆盖每个目标 Step，
声明 precondition、business action、business assertion 角色，命名状态及前向 transition，
并引用 Brief 中的 `feature_declared`、`runtime_observed`、`code_verified`、
`user_confirmed` 或显式 `ai_hypothesis` 支撑。`generation_plan.py` 只校验覆盖、顺序、
引用闭合和前向因果形状，不用代码规则推导业务状态。完整单Step且无Data Table时可用
`single_step_intent`，不为满足schema编造states/transitions。

再生成默认读取AI Plan Context 1.1：它从身份有效的完整Plan即时投影Scenario摘要、
owner/reuse、Step实现文件、table usage、operation顺序、value provenance和最近结果。完整Plan始终是事务、
验证和结果绑定的唯一backend identity；Intent、proof、Annotation、Decision或单个Step
只能通过`generation_workflow plan`按需展开。投影不落盘，也不能作为第二状态源提交修改。
AI Workflow Context 1.0同时去除revision与Brief/Plan/Decision identity重复，只保留路由、
风险、ambiguity摘要、事务结果和错误。完成态可用绑定Intent重新提交同一Plan并开启新事务；
自身上一条transaction result不会让Request过期，后续用户feedback或其他相关经验仍会
在Plan持久化前fail-closed并要求重新物化。
AI Context Budget 1.2按canonical compact JSON计量完整inspect输出，包括Budget自描述和
超限警告；Brief、生成Prompt与BDD instructions另行计入。已嵌入输出的Workflow摘要、
Plan Context和Capability只作组件诊断，不重复相加。

新Request使用`business-v1`身份，只绑定业务规格、Evidence、Annotation、目标相关Memory和
Execution Profile，不复制Framework Contract。Plan 4.2在Design提交时冻结Generation
Contract 1.0 lease并纳入Plan指纹；Contract变化只退休当前Plan并要求基于同一Request和
Decision重新Design。prepare与finish都重验lease，运行中变化失败关闭。

简单旅途使用只读`simple_path_evaluation`同时评估正确性、用户成本、可维护性、安全、
执行真实性和效率；评测只读取现有Request/Brief/Plan/Transaction/Run Result/Oracle receipt，
不进入生产协议，也不替AI选择实现。默认目标是一个Request、一个Plan、一个Transaction、
零重复业务问题、稳定公开命名、仅业务文件、默认上下文不超过50 KiB、Transaction不超过
180秒、端到端静态完成不超过300秒。运行获授权时必须有绑定Run Result和独立业务Oracle。

`prepare`后，AI从running Transaction读取内容寻址的Implementation Manifest 1.7。该
Manifest由Plan、Brief和事务输入快照确定性派生，分开AI可编辑、系统拥有和只读复用文件，并列出Step decorator、
模板pattern与函数参数、调用顺序、严格`$loc:`目标与动态输入绑定、Page method receiver和输入来源、locator ensure patch、已授权PIC的精确模板文件、
package marker及受保护路径。
系统在file lease内原子物化locator/PIC patch和package marker；AI仍负责方法body、抽象和错误处理。Design与实现提交前分别使用正式编译器和Plan-to-Code预检，技术修复追加到Transaction独立ledger；`finish`重建Manifest、要求最新valid预检与源码快照一致、从实际diff生成系统receipt，并由Plan-to-Code产生
Code Manifest 1.0记录实际实现，二者不能互相替代。Transaction另以project guard快照
拦截generation roots外未申报变化；运行产物与打包模型不进入该快照。

完成结果按语义选择、Design、实现、Transaction、Runtime、独立Oracle六层投影，任何缺失证据均不自动升级。最终源码若包含plugin、动态dispatch、外部可变状态或并发信号，系统冻结高风险矩阵策略；矩阵每个角色必须绑定不同的真实Run Result、目标Feature/Scenario/Step、框架环境快照和预注册Oracle。UIA Oracle先冻结具体PID/HWND和进程身份，再在同一实例上读取业务属性。
当前版本为Runtime Risk Policy 1.1、Oracle Registry/Runtime Matrix 1.1和Quality Gate 1.2；历史Quality Gate 1.1只用于读取既有证据。

Recorder 的生成作用域是一个录制 Session 中当前 Scenario 的目标 Step 集。Step 保持
录制、Take、时间线和修复单元；Request、Brief、Decision、Plan 和 Transaction 以
Scenario scope 聚合。完整范围默认覆盖 Scenario 全部 Step；显式部分范围必须携带
selected/excluded Step，不能投影为 Scenario 完成。Outline 实例证据按 example ID
隔离，`logical_template_id` 只用于参数化模板关联。相邻 Step continuity 由现有
Semantic Pack 派生，只提供 advisory 候选，不改变 evidence authority。

`ai/requests/<request-id>.json` 只保存不可变事实；新 Request 的 `request_fingerprint` 覆盖完整 canonical payload，同一 ID 不允许改写。`running` transaction 只冻结外部 evidence freshness，仍严格拒绝 Request 文件篡改。`ai/workflow/<request-id>.json` 是唯一运行时状态源，UI、CLI 和 Prompt 都只投影它。确认计划位于 `ai/plans/<request-id>/plan-*.json`，Request 不保存 plan、adjustment 或运行状态。

实现层按所有权拆分：

| 模块 | 唯一职责 |
| --- | --- |
| `capture_runtime.py` | Hook、视频、暂停/继续、观察、窗口通知、时间同步和采集错误的唯一生命周期所有者 |
| `observation_providers.py` | 结构化Observation Provider注册、能力选择和Receipt采集；Provider只产事实，不决定业务期望 |
| `session.py` | Step/Take 状态、窗口树证据、暂停区间证据和 Session 物化 |
| `session_projection.py` | 从 Session 快照重建 manifest、AI 索引、readiness 与 catalog |
| `request_repository.py` | Request 索引、路径边界、artifact hash 与 revision seal |
| `request_service.py` | “查找或创建 Request”应用服务，不保存 Repository 逻辑 |
| `workflow_service.py` | Request、Reconciler、Plan 与 Workflow State 的唯一编排入口 |
| `workflow_state.py` | Workflow State 校验、读写与状态转换 |
| `generation_plan.py` | Plan 规范化、校验与持久化，不修改 Workflow State |
| `code_manifest.py` | 将Plan-to-Code audit投影为绑定Request/Plan的内容寻址实现清单，不重复解析代码 |
| `decision_pack.py` | 一次结构化问题、不可变 Answers 和 Answer Compiler；自由备注不能修改 Plan |
| `semantic_reconciler.py` | 纯 reconciliation 规则；`reconcile_generation()` 不执行文件 I/O |
| `reconciliation_repository.py` | Reconciler 输入加载与 Brief/Report 原子持久化 |
| `memory_digest.py` / `project_memory.py` | 目标相关经验快照、有界结构化 Digest、append-only journal 和只读 freshness |
| `knowledge_audit.py` | 无副作用检查 durable knowledge；不迁移、修复或删除资产 |
| `knowledge_maintenance.py` | 显式确认后重建派生 catalog，或可逆隔离/恢复 invalid Capability |
| `capability.py` | 保存不可变Capability detail，并以单个原子catalog投影Take/revision精确的confirmed/stale状态 |
| `portable_knowledge.py` | 从确认 Capability 生成同项目内容寻址记录，严格审计并提供有界查询 |
| `code_reuse_index.py` | 增量 AST/YAML 复用索引，只提供带文件 hash 的候选，不替 AI 决定代码归属 |
| `ai_capability_registry.py` | Plan operation与可见BasePage API名称的唯一注册表；区分Plan可用和debug-only，不承载产品业务规则 |
| `pic_template_audit.py` / `generation_pic_policy.py` | PIC 模板裁剪、跨帧唯一性审计，以及 prepare/finish 双重授权校验 |
| `operation_coordinator.py` | 有界线程池、按 key/revision 淘汰旧任务、取消、结果隔离和阶段耗时 |
| `query_service.py` / `take_query_service.py` / `library_query_service.py` | 活跃Session、Take与离线Library的稳定DTO只读边界；View不解析JSON/YAML布局或打开Session |
| `workbench.py` | 录制、历史、修复/生成和时间线共用的单 Toplevel 工作台宿主 |
| `projection_store.py` | 临时目录构建、hash 校验、原子 revision 发布与 current pointer |
| `run_lock.py` | Capture长租约与Timeline、Take、Annotation、Transaction prepare/finish短事务共用的PID/token单写锁；只读审阅不加锁 |
| `status_overlay.py` | 主 Take 与补录共用的非激活录制状态、颜色、快捷键和临时通知界面 |
| `legacy_artifacts.py` | 旧 `actions.json` / locator artifact 的一次性迁移边界 |
| `supplement_capture.py` | 调用共享 CaptureRuntime，并负责补录事件命名空间、动作/locator 和片段产物 |
| `supplement_repository.py` | 不可变补录片段及 recording/completed/failed/discarded 生命周期 |
| `supplement_window.py` | 补录选窗、录制和完成回流，不解释 Timeline 业务规则 |

核心依赖方向固定为 `UI -> application service -> rules/repositories`。State、Plan 和 Repository 不反向调用 application service；UI 不读取 `session.active` 或 artifact 内部布局。

主 Take 与补录不得分别创建或停止 Hook/ffmpeg，也不得维护两套活动录制界面。两者统一调用 `CaptureRuntime.start/stop/abort`，共享 `RecordingStatusOverlay`、F7/F9/F10/Shift+F11、窗口通知和视频时间同步；Workbench 统一拥有采集期间的最小化/恢复，补录继承 Run 的 `minimize_window`。差异只留在设置输入和产物 Sink：Session 写 Step/Take 状态和窗口树证据，Supplement 只增加片段名称和可选窗口调整，写独立片段并等待 Timeline 插入。补录先按稳定窗口身份同步原 Take 的窗口集合及主窗口；新录制冻结进程名，并在系统允许读取时冻结可执行路径指纹。已冻结指纹的窗口跨 PID 只恢复同一可执行身份的唯一 class/title 候选；恢复时指纹缺失或不一致均失败关闭，并重新验证仍存活的 HWND 以防句柄复用。历史录制没有进程映像字段时保留 class/title 兼容降级。`auto` 无匹配时由第一次业务操作确定，`strict` 无匹配时才要求人工选择。

Recorder V4 仍是框架内的轻量文件功能：不使用数据库、消息队列、守护进程或网络服务。录制、历史、修复/生成、时间线嵌入同一个 Workbench；UI 只调用 Command/Query 边界，后台操作全部通过进程内 `OperationCoordinator`。

新 Take 根目录只保存 raw/canonical 输入：`take.json`、`events.jsonl`、`actions.auto.json`、`locator-candidates.auto.yaml`、`timeline-edits.jsonl` 与媒体。每次校正把 timeline-state、effective actions/events/locator、Action Media、media index、Evidence Graph 和 Semantic Pack 一起写入 Projection 5.5 的短物理目录 `p/<base32-revision>/`，hash 校验通过后原子替换 `current-projection.json`。完整 revision 仍保存在投影 manifest；旧 `projections/<hex-revision>/` pointer 继续只读兼容。派生协议升级时 active 生成入口发布新的 immutable revision，不原地覆盖历史目录。短物理目录避免 Windows 离线部署路径叠加 staging 和原子临时文件后超过传统路径上限。失败或进程中断时旧 pointer 不变；损坏 revision 会按同一 source revision 重建。V3 根目录 effective 文件只作为只读 fallback，不再双写。

新录制还保存 `raw-events.jsonl`、`raw-events.seal.json` 和
`capture-completion.json`。前者是 Hook ingress 的 append-only 事实，seal 固定事件数量、
顺序与 SHA-256；completion 证明 canonical `events.jsonl` 与 raw 事件集合一致。Hook、raw
journal、窗口证据、边界帧和事件富化使用独立进程内 lane；F10 只有在各 lane 收敛并
通过集合复核后才能提交 completed Take。旧 Run 没有 seal 时只读兼容为
`legacy_unavailable`，不得追溯生成伪造的完整性凭证。

Recorder 实时目标检查不执行 Child/XPath Root 唯一性回查。动作首事件只采集目标、
有限局部上下文和 deferred 候选，提交事件只刷新必要状态；结构 locator 在结束后按事件
记录的 HWND，使用完整且未截断的窗口树离线验证。跨窗口树不能互相证明唯一性。

补录不是第二种 Take。每个片段先独立写入 `<take>/supplements/supplement-*/`，保留自己的 events、actions、locator、边界帧和可选视频；`insert_supplement` 只在 append-only `timeline-edits.jsonl` 中记录插入位置。未插入片段不进入 Graph、不改变 Request revision；插入后统一物化 `events.effective.jsonl`、effective locator、action-media 和 Evidence Graph。撤销只停用插入记录，不删除补录原始证据。

每个 Take 的 `evidence/graph.json` 是原始 artifacts 的可重建投影，不覆盖源证据。`ai/evidence-context/<request-id>.json` 记录默认 Evidence ID、最小决策证据和延迟媒体。生成完成时，`evidence_audit` 和 Plan-to-Code audit 必须通过；完整视频不要求每次读取，但任何忽略 action 都必须有证据 provenance。

结构角色与目标可信度相互独立。`Document`、`Canvas`、`Pane` 等可以是 container-like，同时在唯一 locator 回查、目标一致和状态变化证据充分时具有高交互可信度。

项目经验是`Bdd/ai/knowledge/project-memory/events.jsonl`中的append-only事件日志，不直接修改业务代码，也不决定Page Object归属。Request ID只绑定当前target可见的结构化经验revision，不绑定整个journal hash；无关Feature/Step的事件不会使Request抖动。Memory Context、Request ID和Brief使用同一次目标快照，Brief只携带有界、白名单化的`memory_digest`。当前用户说明、当前代码和当前Recorder证据始终优先；用户确认经验高于历史生成结果，AI洞察在用户确认前始终标记为`provisional`。

### 轻量生成与风险路由

V3 保留 V2 Evidence Graph 和全部原始媒体，但把完整证据消费移到后台 `Semantic Reconciler`。AI 默认只读取 5～10 KB 的 `Generation Brief`：

```text
Evidence Graph
  -> Semantic Reconciler（全量分类、冲突检测、coverage=100%）
  -> Generation Brief（动作故事、目标、值、风险、复用候选）
  -> fast / clarify / forensic / blocked
  -> Decision Pack / Answers（仅 clarify 且有可验证选项时）
  -> GenerationPlanV4.2
  -> GenerationTransactionV3
  -> automatic validation + Plan-to-Code validation
```

`fast` 不是少检查，而是后台已经闭合动作、目标、输入、媒体和 revision；`forensic` 只展开 Reconciler 指定的冲突事件、图片、树或视频。selected Take、timeline、Graph或policy变化仍然 fail-closed；Contract/API变化退休Plan 4.2并要求同一business Request重新Design，不重复用户Decision。

Decision Answers只约束PlanV4.2，不表示用户认可AI补全的Scenario Model或ownership。Decision 5.8的用户可见`presentation`与机器option共同进入fingerprint，保证所见即所签。PlanV4.2把`external_ai`、`deterministic_surrogate`、`human_authored`或`legacy_import`来源及Generation Contract lease绑定到artifact；synthetic E2E只能证明协议连通，不能证明AI质量。Brief窗口和方法候选只提供建议；AI通过`scenario_model`、owner `resolution`、operation `implementation_resolution`和ambiguity resolutions记录场景因果、窗口复用/新增、实现位置及理由。Plan提交不发布confirmed Capability；AI生成结果首次accepted只记录候选，第二个独立来源同构且再次获认可后才发布。

多 Step Request 以 `(step_id, action_id)` 作为动作身份；Evidence ID、Plan 覆盖、PIC authorization、Plan-to-Code 和 transaction trace 都按 Step 隔离。不同 Take 可拥有相同本地 action ID，不会互相借用证据、locator 或实现文件。

旧 Request/understanding/adjustment 只能由 `legacy_import.py` 一次性读取并物化新 RequestV3；旧状态机不会重新进入核心。

## 执行链路

推荐把一次测试理解为：

```text
feature 场景
  -> steps 步骤定义
    -> WindowPage/View 窗口与 locator 所有权、稳定复用方法
      -> BasePage / actions 通用动作
        -> locator / data / OCR / 图片识别 / pywinauto
```

各层职责：

| 层级 | 负责内容 | 标准 |
| --- | --- | --- |
| `feature` | 描述业务场景和期望结果 | 写用户视角语言，避免堆 UI 细节 |
| `steps` | 把 Gherkin 步骤转换成 Python 调用 | 参数解析、场景特有线性动作、业务期望和跨窗口编排；通过所属 Page/View 使用命名 locator |
| `page_obj` | 拥有窗口/locator，并封装已验证复用能力 | WindowPage/View 声明和稳定业务方法；不为单次流程建包装方法 |
| `actions` | 提供通用 UI 行为 | 不写业务含义，不直接依赖具体页面 |
| `common` | 提供底层能力 | locator 编译、root 切换、OCR/图片引擎、XPath |
| `locators` / `data` | 管理配置 | 减少硬编码，Step 和页面方法都优先引用 YAML 名称 |

## behave 生命周期

`autowork_core/runtime/environment.py` 只作为 Behave hook 门面；Run、Feature、Scenario
状态分别由 `context_runtime.py`、`feature_runtime.py`、`scenario_runtime.py` 实现。
UI Scenario 的应用、宿主资源和录屏初始化由
`scenario_runtime.initialize_ui_scenario()` 拥有，Hook 只传入 Context、Scenario 和
标签决策并处理提示与异常边界。

共享 runtime 在模块导入时不得依赖宿主项目的具体 Page。宿主 Page 只在对应资源分支
实际执行时按需加载；子项目不能因为未包含无关产品 Page 而在 Behave 启动阶段失败。

| Hook | 主要职责 |
| --- | --- |
| `before_all` | 初始化 `context.autowork_run`、日志、录屏器和惰性运行提示服务，启动整次 Run 的提示计时，按配置预热 OCR |
| `before_feature` | 初始化 `context.autowork_feature`，打印开始日志，处理 `@maint`、`@skip`、`@rep` |
| `before_scenario` | 初始化 `context.autowork_scenario`，解析 effective tags，为普通 UI 场景显示提示或更新场景名，再把应用、宿主资源和录屏初始化委托给 `scenario_runtime` |
| `before_step` | 首个 Step 前等待 1 秒并冻结进程快照，然后打印 Step 开始日志 |
| `after_step` | 失败时尝试保存截图，并把截图路径或截图失败原因交给报告 |
| `after_scenario` | 按失败状态收尾录屏并关闭场景资源/应用；连续 UI 场景间保留运行提示和总计时，同步报告；ScenarioState 随 Context 出栈释放 |
| `after_feature` | 汇总报告并结束 Feature；FeatureState 随 Behave Context 出栈释放 |
| `after_all` | 输出报告结束事件，兜底销毁运行提示线程并记录测试结束日志 |

当前 Feature 的 Step 文件可以通过 `application_lifecycle.py` 注册
`before_app_start`、`after_app_start` 和 `after_app_stop` 回调。注册状态与 Behave
matcher 一起保存在 `PreparedStepScope` 的加载快照中，切换 Feature 时同时恢复，避免
跨 Step scope 泄漏。`before_scenario` 在进程快照和应用启动之前分发前置回调，在启动
命令成功返回后分发启动后回调；`after_scenario` 收集错误并先完成录屏、项目资源
和应用清理，再分发停止后回调。生命周期已激活后，即使前置回调、启动调用、Step 或
应用清理失败，也会尝试全部停止后回调，并在收尾结束后合并报告错误。

这些回调只用于必须包围应用进程生命周期的外部准备与收尾，不替代 Feature、Step 和
Page Object 的业务分层。`attach` 模式没有框架拥有的启停边界，因此匹配回调时失败；
跳过和 `@api` Scenario 不激活应用生命周期。回调只允许直接定义在当前 scoped Step
文件中；预检会拒绝共享 helper 中的注册，避免 Python 模块缓存造成回调静默丢失。

宿主项目在`Bdd/application.py`中编排辅助资源和项目就绪。auto模式在进入Step前完成
项目定义的依赖启动与Root就绪门；任一必要资源超时都失败关闭。拥有外部句柄或接口通道
的Page必须在初始化失败时立即释放，并提供幂等`close()`供Scenario收尾调用。attach模式
不拥有主应用启停边界，项目可连接已有资源，但不得启动主应用。具体Page、资源标签、
启动顺序、等待时长和设备动作属于宿主项目约定，记录在项目上下文而非框架文档中。

## Context 分层

框架只在 Behave Context 中保存当前运行产生的状态；全局规则、配置和昂贵缓存保留在模块外部。

| 生命周期 | Context 属性 | 状态类型 | 主要字段 |
| --- | --- | --- | --- |
| Test Run | `context.autowork_run` | `AutoworkRunState` | 公共 data 模板、`recorder`、`reporter`、`run_indicator` |
| Feature | `context.autowork_feature` | `FeatureRuntimeState` | `pages`、`locators`、`data` |
| Scenario | `context.autowork_scenario` | `ScenarioRuntimeState` | `windows`、`pages`、`variables`、`tag_decision`、`root_pid`、进程快照/`started_pids`、录屏状态、应用生命周期状态；项目可附加本场景临时资源句柄 |

`autowork_run`在`before_all`创建并贯穿一次Behave run；`autowork_feature`在
`before_feature`创建，同一Feature的Scenario共享页面对象和动态资源；
`autowork_scenario`在`before_scenario`创建，窗口句柄、进程和录屏会话不跨Scenario。
Feature/Scenario的纯内存状态随Behave对应Context层自动弹出；录屏进程、项目Page/设备
句柄和应用进程等外部资源仍在Hook中显式关闭。`TAG_MANAGER`、`settings`、OCR模型缓存、
项目集成缓存和Step模块状态属于进程级服务，不复制到Context。

`ScenarioRuntimeState.variables`只保存当前Scenario运行时产生、供后续Step消费的临时值。
`actions/variable_actions.py`拥有变量名、空值、覆盖和缺失值规则，并组合既有元素读取动作；
`BasePage.save_text()`、`save_attr()`、`set_variable()`和`get_variable()`只负责locator解析与
参数转发。变量名区分大小写，值保留原始类型。该存储不复用Feature级`data`、公共YAML或
进程级字典，Scenario结束后整体释放。

Recorder不增加第二个变量Runtime。Plan 4.1仅在operation上声明生产者
`result_binding`和消费者`source=runtime.<binding>`：AI根据完整Scenario与F9业务含义
选择关系；Proof/Plan-to-Code只校验F9 Action、同Scenario闭包、顺序、唯一性和真实调用。
相同值、相邻Step和continuity hint都不能自动授权绑定；`get_variable()`是实现辅助，
`set_variable()`继续不向生成开放。

`PROCESS_TRACK_MODE=snapshot` 时，`before_scenario` 只保存应用启动前的 PID 基线；首个 Step
的 `before_step` 额外等待 1 秒后取第二次瞬时快照并计算新增 PID，再进入 Step 函数，后续
Step 不重复采样。没有 Step 或首个 Step Hook 未完成采样时，`after_scenario` 会在清理应用
前兜底完成快照。清理时重新展开已跟踪 PID 当前仍关联的子孙进程，去重后叶子优先终止，
等待并有限重试；首个 Step 时冻结的 `psutil.Process` 创建身份贯穿清理，PID 被复用时不
终止新进程。单个进程消失或失败不跳过同树的其他进程，最终残留写入日志。

`root` 只记录启动 PID，`none` 不记录进程，两者均在应用启动后立即完成，不执行等待或
全局 PID 快照。场景清理 `root` 时会处理当时仍挂载的子孙进程；启动器退出或派生进程
脱离父进程的场景使用 `snapshot`。首个 Step 后才由既有服务独立拉起或更换 PID 的进程
不属于冻结快照，必须由宿主专用 Stop 或有明确身份范围的生命周期回调清理。

## 资源加载

`before_all` 会加载公共 data：

```text
Bdd/data/public_data.yaml -> context.autowork_run.public_data 模板
```

页面对象初始化时加载页面资源：

```python
class MainWindowPage(WindowPage):
  root_locator_file = "main/window.yaml"
  root_locator = "main_window"
  data_file = "main_window_data.yaml"
```

加载规则：

- 每个 Feature 的 locator 容器从空状态开始，WindowPage 窗口包不发布到 Feature
  locator 容器；BasePage 和 ScriptPage 只加载显式声明的 locator 文件。
- 每个 Feature 从公共 data 模板 fork 独立 data 分层，页面 data 优先于公共 data。
- 页面资源和 Page Object 不跨 Feature。
- 声明的 locator/data 文件不存在时立即报错。
- 空 YAML 当作空字典。

## root 缓存

`context.autowork_scenario.windows` 使用 `RootStore`：

```python
context.autowork_scenario.windows.set("Notepad_window", root)
context.autowork_scenario.windows.set_last(root)
context.autowork_scenario.windows.get("Notepad_window")
context.autowork_scenario.windows.last()
```

用途：

- 缓存顶层窗口。
- 没有指定 `root` 的普通定位可以回退到 `last_root`。
- OCR/PIC 的 `region` 可引用普通 Child/XPath locator，避免全屏识别。

RootStore 每个 Scenario 创建一次，随 Scenario Context 出栈整体释放，不复用上一场景的窗口句柄。内部使用 `RootEntry` 保存命名 root 的状态。YAML/locator 链中的顶层 root 首次成功确认后会补全 `handle` 和 `process_id`，进入 `hot` 状态；后续优先按 handle 复用并校验 process 与原始 criteria，避免 HWND 被系统回收后指向错误窗口，同时不重复桌面全局查找。失效或身份不符的 handle 会降为原始 criteria lazy root；读取视觉 monitor 时发生的 hot Root 竞态允许当前调用重绑一次。

`set_root()` 显式设置的 root 仍然可用于临时调试，但属于 legacy 缓存。长期窗口必须写成 locator YAML；Recorder 生成策略会拒绝新增的 `set_root()` 和 inline locator，同时通过生成前基线保留已有手写调试代码。

## 定位等待

动作层默认不再统一使用较重的 `ready` 等待。`BasePage` 暴露的点击类动作默认 `wait_type="visible"`，输入类动作默认 `wait_type="enabled"`，确实需要可见且可用时显式调用 `wait_ready()`。详细 API 见 [3.动作参考](../3.动作参考.md)。

### Runtime 定位收敛计划

当前 Runtime 保留多种后端的必要差异，但内部目标表示、等待 owner、Root 生命周期和
错误分类尚未完全统一。收敛采用兼容迁移，不改变宿主脚本：现有 Feature、Step、
Page Object、locator/data YAML、`BasePage` 公共方法签名、参数默认值和返回行为均为
迁移不变量。每个阶段只替换内部实现，并以现状特征测试证明脚本可观察语义不变；不得
要求宿主脚本增加显式等待、改写 locator 或切换 Page API 才能通过。

目标内部链路为：

```text
Page / Action
  -> WaitCoordinator（唯一 deadline 与重试 owner）
   -> TargetResolver.probe_once（单次查询，不等待）
    -> RootResolver（唯一 Root 恢复、身份复核和 stale owner）
    -> Child / XPath / OCR / PIC / POS backend
   -> ResolvedTarget（统一 wrapper、wrapper list 或坐标目标）
  -> InteractionAdapter（点击、输入或 UIA Pattern）
```

内部协议逐步引入，不一次性替换现有 Runtime：

1. **冻结现状**：为各定位方式记录返回类型、超时、状态检查、异常和 Root 行为；保留
  当前 XPath 动态目标等待与安全点击适配器，不继续横向扩展 `locator.py`。
2. **统一目标表示**：新增内部 `ResolvedTarget`，封装目标类型、值、候选元数据、来源和
  Root 结果；公开 API 暂时继续返回旧值，由兼容适配器维持脚本行为。
3. **统一等待策略**：新增内部 `WaitPolicy` 和 `WaitCoordinator`；backend 只实现一次
  probe。先迁移 Child/XPath，再迁移显式 `wait_*`，最后迁移 dropdown 和语义控件动作。
4. **统一 Root 生命周期**：把 restore、identity、stale 和 rebind 收口到 `RootResolver`；
  窗口动作不再维护独立的缓存句柄信任路径。
5. **接入视觉后端**：OCR/PIC 保留截图、匹配、缓存和调试图，但总 deadline 与 required
  语义接入协调器；POS 仍是无状态坐标投影，不伪装成 UIA 等待。
6. **退役兼容层**：`default` 隐式 OCR fallback、`last_root`/`set_root()` 和无前缀临时
  locator 先标记 legacy，再提供迁移诊断；新生成代码只使用窗口包、显式 `by` 和显式
  `root`/`region`。

当前迁移状态：阶段1已冻结公开Action签名、Page参数转发、编译元数据和现有后端返回
形态；阶段2已引入内部`ResolvedTarget`兼容适配器，并只迁移`_do_click`的目标分类。
阶段2的第二切片已迁移`_target_to_wrapper`分类，并由旧行为特征测试确认空列表、列表
首项、坐标、wrapper和lazy spec语义不变。`get_element()`及全部公开Page方法仍返回和
接收旧值。阶段3已引入不可变`WaitPolicy`并接入XPath现有等待循环；wait type别名、
负超时、`none`单次probe、interval和required语义保持不变。显式`wait_*`的正常重试、
否定等待和`wait_ready`内部参数转发现状也已由特征测试冻结。阶段4已抽取共享布尔轮询器
并迁移`wait_exists/not_exists/visible/enabled/exposed`；零超时、调用次数、deadline cap、
负interval旧错误和返回值保持不变；`wait_ready`也已在保持异常视为未就绪和内层
bounded wait参数不变的前提下接入同一协调器。下一阶段只设计“返回控件并保留last_error”
的value polling协议。阶段5已迁移语义控件和dropdown状态等待：语义控件保留
`TypeError/ValueError`立即失败、其他错误作为最终`TimeoutError` cause和负interval钳制；
dropdown保留全部错误延后为Timeout cause及负interval原样失败。两者返回wrapper语义不变。
locator backend的第一层`probe_once`边界已在XPath落地：`ProbeResult`携带
`ResolvedTarget`、Root结果和查询错误，供同一等待循环消费。default、Child、OCR、PIC和
POS若包装后只会立即解包，则直接保留旧backend返回值，不为协议外观增加无收益对象；
`get_element()`及脚本可见返回不变。OCR/PIC仍由原backend拥有既有timeout、region、
candidate与调试行为。
Child的lazy `WindowSpecification`明确保留pywinauto自身的bounded wait：pywinauto已负责
状态解析、控件重取、retry interval和deadline，外套协调器会形成双层重试并改变既有节奏。
这里只冻结调用和异常契约，不强行迁移等待owner；Root生命周期仅迁移下述窄切片，公开
返回仍不改变。

Child的wrapper-root分支已完成第一刀：每轮descendants查询和状态筛选仍由Child拥有，
deadline与sleep改由共享`poll_value`协调；歧义和backend异常立即传播，超时仍返回原来的
`None`或空列表。XPath也已由同一协调器拥有deadline与sleep，每轮仍重新解析Root并执行
单次XPath查询和状态检查；最终LookupError、状态TimeoutError、required返回以及hot Root
stale规则保持不变。Root restore/identity/rebind尚未抽成新的owner对象，但handle路径的
第一层安全边界已收口：每次复用hot/stale handle前都校验process和root criteria，失效、
HWND复用或身份不符时降为criteria lazy Root，不继续信任旧handle。窗口动作也复用同一
身份复核和`root_cache_name`，不再只凭`IsWindow(handle)`维护第二套缓存信任路径。
其中`found_index`是发现阶段的候选选择规则，`visible_only/enabled_only`是动态状态过滤，
三者不作为持久窗口身份；Child元素查询仍正常执行可见性和可用性过滤。

XPath当前只把精确的普通`LookupError`分类为动态目标暂未出现并允许重试；`LookupError`
子类、XPath解析产生的`ValueError`以及未知backend异常均立即透传，不转换成“未找到”。
该规则由`is_transient_lookup_error()`显式命名，但暂不引入完整异常类型层级。

OCR/PIC engine的正向查找和否定等待也已由共享`poll_value`拥有deadline与sleep；截图、
OCR/图片匹配、cache、candidate选择及最终失败debug图仍分别由原engine拥有，返回值与异常
策略不变。locator直接调用完整视觉查找，尚未上提视觉总deadline或把engine scan primitive
直接暴露给resolver，因此这里只算等待机制复用，不算视觉`probe_once`最终收口。

视觉Action对结构化OCR/PIC locator执行否定等待时，每轮继续使用`visual_timeout=0`单次
查询，deadline与sleep改由共享`poll_boolean`拥有；裸文本/图片条件仍返回内部哨兵并交给
OCR/PIC engine，避免叠加两层视觉等待。零/负timeout仍至少查询一次，backend异常立即透传。

水平滚动条设置RangeValue后的最终值回读也复用`poll_boolean`，固定`0.05s`采样并受
`wait_timeout`总deadline约束；RangeValue读取异常仍立即包装为原Runtime错误，超时消息继续
携带期望值和最后一次实际值。滚轮和拖动等物理输入本身不交给等待协调器重复执行。

所有共享等待拒绝`NaN`和正负无穷的timeout/interval，避免deadline永不成立或无限sleep；
有限的正interval始终按剩余deadline截断。负interval仍按各迁移前契约处理：未钳制路径
保留原sleep错误，显式钳制路径继续使用零延迟。

OCR正常完成但没有匹配候选时仍返回`None`，由locator按“未找到”处理；criteria错误、模型
不可用、截图或推理异常则保持原异常透传，显式OCR和default OCR fallback均不得把backend
故障伪装成未识别。PIC原路径同样保持backend异常透传。

legacy default locator仍按auto_id、title、OCR顺序fallback，但只有前一级正常返回空结果时
才继续；Child歧义、无效条件或backend故障均立即透传，不能静默降级到更弱的OCR目标。

最终目标缺失在`required=true`时统一抛标准`LookupError`并保留原消息，`required=false`时
返回原兼容空值。目标正常缺失不代表顶层Root失效，因此不标记hot Root stale；Root访问
失败或目标已取得但状态确认失败仍保留各自的stale路径。

声明Root的default/OCR/PIC若无法取得有效窗口矩形，会标记hot Root stale并原样失败，
不得以`monitor=None`降级到全屏视觉搜索。显式region同样要求有效且唯一；多匹配抛
`ElementAmbiguousError`，缺失、错误类型和零尺寸矩形均在视觉backend执行前失败。
若hot Root在身份复核后、读取monitor前发生竞态失效，当前调用只允许重新`_switch_root`
一次，取得有效monitor后才执行一次default/OCR/PIC backend；第二次失败原样抛出。Child
和XPath状态等待已经消费自己的总deadline，不追加同调用完整重试，以免把超时翻倍。

统一错误分类至少区分 NotFound、Ambiguous、NotReady、RootStale、VisualNotFound 和
InvalidLocator。Backend 或未知编程异常不得被转换成“未找到”或布尔成功；Assertion 层
只负责把已分类 Runtime 失败转换成业务断言失败。Recorder Inspector 继续作为证据候选
生成与安全验证边界，不与 Runtime 查询器强制同构。

每个迁移切片必须同时满足：旧脚本零修改、公开签名兼容、聚焦行为测试通过、Root/异常
负向测试通过、相关 Runtime 回归通过。若无法证明兼容，保持旧路径为默认并回退该切片。

Recorder冻结Toggle、SelectionItem、ExpandCollapse和RangeValue的客观effect/after_state。
Semantic Pack内部可保留operation hypothesis用于审计、复用和模型测评，但Brief默认投影不
暴露operation名、数值分值或排序。AI先依据业务意图与冻结事实形成候选，再按输入顺序查询
点名operation。Action Knowledge物理区分capability facts、可能不完整或错误的maintainer
guidance和非Runtime证明的static assessment，不自动扩展或排名候选。Plan只拒绝已证明
`incompatible`的目标/runtime组合；`unknown`交由AI调查和runtime验证，静态`compatible`也
不代表Runtime已证明。Item类接口仍使用录制目标本身的locator，Slider保留冻结Range边界。
Action Knowledge从Brief与Registry即时派生，只读、不落盘、不修改Workflow、不进入默认
上下文，也不是新的状态源。

## runner 结构

统一 runner 在 `autowork_core/runtime/behave_runner.py`：

| 函数 | 作用 |
| --- | --- |
| `temporary_settings(**overrides)` | 临时覆盖 settings，结束后自动恢复 |
| `build_behave_args(feature_path, tags=None, verbose=True, formatter=None)` | 构造 Behave 参数 |
| `run_behave(feature_path, settings_overrides=None, tags=None, verbose=True, formatter=None, clear_screenshots=True)` | 准备目录、临时配置、执行 Behave |
| `main()` | 正式入口，运行 `Bdd/features` |

runner 使用 Behave 入口 `Bdd/environment.py` 和自定义 `FeatureScopedRunner`。目录运行只创建一个 Behave Runner，因此 `before_all`/`after_all` 各执行一次，每个 Feature 正常执行自己的 `before_feature`/`after_feature`。Feature 解析后、formatter、产物清理和 `before_all` 之前，runner 按 Behave tags 和框架 skip 标签选出实际运行的 Scenario，再按 Feature scope 导入对应 step 文件，并用 Behave 1.3.3 的真实 matcher 检查无效、歧义和未定义 Step。预检失败不会清理上一轮产物，也不会启动 Hook、OCR 或被测应用。

预检成功后会保存每个 Feature 的 matcher 快照；执行时只切换 Step Registry，不再次导入 step 模块。scope 优先使用 Feature 顶部的 `@stepfile:<相对路径>` 标签，未写标签时按文件名自动推导对应的 `*_step.py`。不同 Feature 可以保留同名业务 Step，同时不会共享 matcher 或模块状态。无导入副作用的静态检查也由 `autowork_core/runtime/step_validation.py` 提供。

薄入口：

| 文件 | 作用 |
| --- | --- |
| `Bdd/runner.py` | 正式入口，运行 `Bdd/features` |
| `Bdd/local_runner.py` | 本地入口，运行 `Bdd/test_features` 或指定 feature |
| `autowork_core/runtime/behave_runner.py` | 正式执行编排和入口实现 |
| `autowork_core/runtime/local_runner.py` | 本地 runner 实现 |

## runtime 模块边界

`autowork_core/runtime/` 按以下职责维护，避免把新逻辑继续堆入 `environment.py`：

| 分类 | 模块 | 职责 |
| --- | --- | --- |
| 执行编排 | `behave_runner.py` | 单 Behave Runner、Feature 前 Step scope 切换、正式入口 |
| 本地调试 | `local_runner.py`、`single_step.py` | 本地入口、`@single` 解析、临时 feature 生成 |
| Step 选择 | `step_scope.py` | feature 收集、标签解析、feature 到 step 文件映射、安全路径解析 |
| 运行状态 | `run_state.py` | step scope 环境变量及上下文恢复 |
| Step 加载 | `step_loader.py` | scoped step 模块动态加载和模块缓存重置 |
| 标签决策中心 | `tag_manager.py` | 统一注册框架标签，并按运行时、Step scope、Single 预处理阶段生成专用决策 |
| Hook 门面 | `environment.py` | 保留 Behave 标准 hooks 和生命周期调用顺序 |
| Run 生命周期 | `context_runtime.py` | `AutoworkRunState`、公共 data 模板、录屏器、Reporter 和日志 |
| Feature 生命周期 | `feature_runtime.py` | `FeatureRuntimeState`、页面缓存及 Feature 独立 locator/data 分层 |
| Scenario 生命周期 | `scenario_runtime.py` | `ScenarioRuntimeState`、RootStore、APP_PATH 启动、进程追踪、录屏和项目 Hook 顺序 |
| 项目场景准备 | `Bdd/application.py` | `prepare_scenario(context, scenario)`完成可选依赖启动和页面就绪，`cleanup_scenario(context, scenario)`释放项目资源；函数缺失时为空操作 |
| 宿主应用启停 | `Bdd/application.py` | `APP_PATH=runtime` 时必需的 `start_application` / `stop_application`；产品进程清单不进入 Core |
| 状态分类 | `status.py` | passed/failed/skipped 等执行状态和失败产物保留 |
| 报告 | `reporting/spark.py` | Spark 数据采集和 HTML/JSON 输出；environment 直接分发 Hook |

`environment.py`只作为Behave hook门面继续保留，`Bdd/environment.py`仍是一行导入适配器。
状态按生命周期放入`context_runtime.py`、`feature_runtime.py`、`scenario_runtime.py`；Core在
APP_PATH启动并发出`after_app_start`后调用`Bdd.application.prepare_scenario`。场景收尾先
调用`cleanup_scenario`，再清理Core追踪的进程。两个场景函数均为可选，空项目无需定义
页面或外部资源；只有选择`APP_PATH=runtime`时，宿主启停函数才是必需契约。执行选择逻辑
放入runner，报告逻辑放入`reporting/`。

## 标签处理边界

所有框架标签规则集中在 `tag_manager.py`，但调用方按阶段使用不同入口和不可变决策，避免 Hook 处理不属于自己的标签：

| 标签类型 | 示例 | 所属模块 | 处理阶段 |
| --- | --- | --- | --- |
| 运行策略 | `@skip`、`@rep`、`@api`、`@maint` | `resolve_runtime()` → `RuntimeTagDecision` | Behave feature/scenario hooks |
| 宿主资源 | 项目自定义 tag | `Bdd/application.py` | 项目依赖启动与就绪阶段读取 `effective_tags` |
| Step scope | `@step:`、`@stepfile:`、`@step_file:`、`@steps:` | `resolve_step_scope()` → `StepScopeTagDecision` | 执行计划或直接 Behave 加载前 |
| 单步调试 | `@single:previous:2:example=1.2` | `resolve_single_step()` → `SingleStepTagDecision` | 本地 runner 调用 Behave 前 |
| Behave 过滤表达式 | `@smoke and not @skip` | Behave 自身 | runner 通过 `--tags` 原样传递 |
| 报告展示 | feature/scenario 原始 tags | `reporting/spark.py` | 报告采集阶段，保留原始文本 |

`environment.py`只调用`resolve_runtime()`；`@single`在`local_runner`调用Behave之前解析，
`before_scenario`不参与Single Step选择。框架运行策略标签可以放在Feature、Rule、Scenario/
Outline或Examples，Hook使用`effective_tags`继承；标签自身的位置合法性仍按声明节点校验。
`@maint`、`@skip`、`@rep`是最高优先级跳过标签，对应范围不会启动应用、项目资源或录屏；
未跳过时，`@api`阻止托管UI初始化。Core不注册或解释项目资源标签；项目实现直接读取
`scenario.effective_tags`，且只在框架通过skip/api门后运行。具体资源标签与外部控制对象
属于项目配置。`status.py`只负责执行状态；`step_scope.py`只处理Step文件路径；
`single_step.py`只处理Scenario/Examples选择及临时Feature生成。Behave`--tags`表达式仍
原样交给Behave 1.3.3，不由框架重新解释。

## 输出产物

| 目录 | 内容 |
| --- | --- |
| `artifacts/logs/` | loguru 日志 |
| `artifacts/screenshots/` | 普通失败截图、OCR/PIC 调试图 |
| `artifacts/recordings/` | 失败录屏、ffmpeg 日志和临时分片 |
| `artifacts/recording_sessions/` | Feature Step Recorder 的逐 Step 证据、历史 Run catalog、能力索引和 AI 输入包 |
| `artifacts/reports/` | Spark HTML/JSON 报告输出目录 |

Spark 报告由 `context.autowork_run.reporter` 收集，`reporting.dispatch_report_hook()` 负责空值处理、调用对应 Hook 和隔离报告异常；`environment.py` 只保留 Behave Hook 及分发顺序，没有本地报告辅助函数、HookManager 或多 Reporter 注册层。失败步骤会挂截图和 OCR/PIC 调试图；截图保存失败不会中断报告生成，会写入失败步骤的 `errorDetail`。连续录屏使用项目内置 ffmpeg，不再走 mss；`failed` 模式会挂载最近 `BUFFER_SECONDS` 秒滚动录屏，`all` 模式会挂载完整场景录屏。`after_scenario` 会补齐因前置失败而未执行的步骤，并按 Background + Scenario 原始顺序排序。

## 维护原则

- 业务逻辑优先放 Page Object，不放 actions。
- actions 保持函数式通用动作，不引入业务类封装。
- locator/data 优先 YAML 化，减少硬编码。
- 视觉定位优先限定 `region`。
- 新增 `BasePage` 公开动作时，必须同步在 `AI_CAPABILITIES` 中显式且唯一分类为
  Plan可用、框架辅助、仅调试或策略禁止；漏注册会使Generation Contract构建失败。
- `plan_enabled=False` 的框架辅助API仍可供Page实现调用，但不能作为独立Plan operation；
  仅调试和策略禁止API不进入生成可用接口。
- 开放给AI Plan的动作需补充purpose、适用/避免条件、替代项及必要的值证据、控件类型
  和validator信息；这些知识用于引导，只有客观不兼容才形成安全门。
- 新增可被 Page Object 调用的动作时，同步更新 [3.动作参考](../3.动作参考.md)及
  Runtime、Registry/Contract和Plan-to-Code测试。
- 运行入口或配置规则变化时，同步更新 [1.快速开始](../1.快速开始.md) 和
  [4.定位器与配置](../4.定位器与配置.md)。
