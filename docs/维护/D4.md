```text

2. publish_compilation_from_projection() 改为：
   result = build_compilation_from_projection(...)
   write_evidence_compilation_result(...)

```

shadow 模块只做：

```text
load authoritative evidence-compilation.json

调用同一个 build_compilation_from_projection()

```

报告路径建议：

```text
take/shadow/evidence-compilation/report-<hash>.json
```

不写 `current-*` 指针，不参与 Request。

比较字段只比较稳定事实，不比较 `created_at/result_fingerprint` 这种每次会变的字段：

```text

```

整个 D 阶段计划，核心不是“再加一个异步优化”，而是解决这个产品问题：

```text
用户正常录制真实软件后按 F10，
系统既不能因为证据分析太重而卡住/失败，
也不能在证据还没真正完成时让生成吃到半成品。
```

说人话就是：**录制保存要稳，生成证据也要真。**

现在的矛盾是：

```text
旧同步链路：
F10 -> 同步 materialize / evidence-compilation -> Request / Brief / Job
优点：证据闭环完整，生成吃到的是确定结果
缺点：真实复杂软件里 UIA tree、window evidence、projection、compiler 可能让 F10 慢、卡、甚至失败

错误异步链路：
F10 -> 先返回 -> 后台再补证据
优点：看起来不卡
缺点：如果没定义好状态，生成会吃半成品，旧 Request 会复用脏证据，用户看到“录完了但生成坏了”
```

所以这个计划要解决的产品问题不是一个代码 bug，而是一个用户旅途问题：

```text
用户录完以后，到底什么时候算“录制完成”？
什么时候可以点生成？
如果证据还在分析，界面怎么表达？
如果后台分析失败，用户应该怎么恢复？
旧的 Request / Brief / Job 怎么失效？
```

D1-D3 的意义是先证明“异步/后台这条路能不能算得和同步主路径一样”。它们不改变产品行为，只生成 shadow report。也就是说：

```text
同步主路径仍然是权威
shadow 只是旁路对照
matched 才说明未来有资格替换
mismatched/failed 只证明异步路径还不能上主路径
```

D4 才是真正的产品语义设计阶段。D4 要回答的是：

```text
如果将来真的让 F10 先返回，
F10 返回代表什么？
是“动作已保存”，还是“证据已可生成”？

生成按钮什么时候可用？
是看到 Take 就能生成，还是必须 evidence-compilation terminal？

UI 要怎么显示？
录制完成 / 证据分析中 / 可生成 / 证据失败，不能混成一个状态。

后台失败怎么办？
是提示用户重录、证据修复、还是系统自动重算？

Request 怎么处理？
证据变化后旧 Request 必须失效，不能继续复用。
```

所以完整计划最终想达到的产品状态是：

```text
复杂真实软件录制时，F10 不被重型证据分析拖死；
但生成入口仍然只消费完整、自洽、当前的证据包；
用户不会因为内部 pending 状态被误导；
系统不会把证据不足推给 AI 猜；
失败时能明确告诉用户是录制证据问题、后处理问题，还是生成问题。
```

它不解决、也不应该顺手解决这些事：

```text
不解决 child-window View routing 这个具体 bug
不恢复全桌面 discovery
不放宽 evidence fail-closed
不让 AI 用媒体/猜测补证据
不把 D4 直接变成主路径异步改造
```

一句话总结：**D 阶段是为了把“录制保存不卡”和“生成证据可靠”这两个目标同时成立；D4 是在决定未来异步化进入产品主路径前，重新定义用户能看到、系统能保证、失败能恢复的完整产品语义。**
