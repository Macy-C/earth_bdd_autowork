# 5. 资产迁移与知识维护

本章面向维护者，说明 AI 资产、Recorder Run、项目知识和跨机器交付的所有权、保留与
恢复规则。它不替代当前代码、测试或冻结 Recorder evidence；发生冲突时以它们为准。

## 资产边界

| 位置 | 所有者与用途 | 生命周期 |
| --- | --- | --- |
| `ai/` | 框架的 Context、Prompt、Instruction、Schema 和 Policy | 随框架版本化，可整体替换 |
| `.github/` | VS Code 发现适配器和小型确定性 Hook | 随框架版本化，不复制 canonical 正文 |
| `Bdd/ai/` | 当前项目的身份、advisory knowledge 和 portable knowledge | 跨 Run 保留，不被框架同步覆盖 |
| `artifacts/recording_sessions/<run>/` | 原始/有效证据、Request、Plan、Transaction 与媒体 | 短期工作集；按完整 Run 归档或退役 |
| Copilot memory、聊天和复用索引 | 本机或派生缓存 | 可丢失，不能成为唯一事实源 |

框架更新只能替换顶层 `ai/` 和对应 `.github/` 发现适配器，必须保留项目的 `Bdd/ai/`。
`.github/copilot-instructions.md`、`.github/prompts/`、`.github/instructions/` 和 Hook 位于 VS Code
固定发现路径；其正文规则仍以 `ai/` 为权威，不能维护两套细则。

`artifacts/recording_sessions/` 必须被 Git 忽略。不要通过 `git add .`、普通代码远端或选择性
删除媒体维护 Run；需要审计时归档完整 Run，并用组织批准的访问控制保存。

## 知识与协作记录

Recorder 自动维护 `Bdd/ai/knowledge`；不要手工改写其 JSON 或 JSONL。该目录可以保存确认的
Plan、Capability、生成结果和用户反馈，但不保存原始视频、截图、UI tree、按键事件或 PIC 模板，
也不能替代当前 runtime evidence。

`knowledge_audit.py` 是只读检查：它检查 manifest、Capability、memory、Collaboration、Shadow、
旧 Work Package、隔离资产和隐私边界，但不初始化、迁移、修复或删除。发现 invalid 记录后，先用
`knowledge_maintenance plan-quarantine` 生成无写入计划；隔离、catalog 重建和恢复都需要当前请求的
明确确认。quarantine 保留原始字节和恢复回执，默认不进入 Portable Knowledge。

Collaboration Review/Promotion 采用“只读复盘 -> 明确批准 -> 最小晋升”：

- Review/Promotion 只由框架维护者显式调用，不能由 SessionStart、会话数量、时间或项目活动触发。
- Review 只产生候选，保存简短证据摘要和回合引用；不得存完整聊天、私有路径或凭据。
- Promotion 只接受当前请求中明确批准的候选 ID，并只改一处最小持久化目标。
- Review 和 Promotion 回执是本地知识，受 `Bdd/ai/knowledge/.gitignore` 保护，默认不进入 Git。

## Run 保留与退役

当前Recorder运行时只接受当前协议集合，包括Session 2.1、Annotation Model 3.0、
Projection 5.7、Evidence Context 2.3、Semantic Pack 6.1、Brief 4.4、Decision Pack 5.8、
Answers 5.1、Plan 4.2、Implementation Manifest 1.12、Job Result 1.2和Run Result 1.3。
运行时只接受上述当前协议，不读取、复制、升级或迁移其他协议资产。资产维护、归档和
跨机器交付也只处理当前协议的完整Run；不得通过修改版本号或手工搬运派生文件伪造当前资产。

“原始 evidence 不可变”表示保留 Run 时不得挑删事件、图片、视频、UI tree 或事务文件；它不要求
每个 Run 永久存在。合理生命周期为：

```text
record -> reconcile -> decide/plan -> generate/validate
       -> optional feedback -> distill knowledge -> retire whole Run
```

只有同时满足以下条件，才可退役一个 Run：

- 没有活动录制、补录、写锁或 running generation transaction；
- 需长期保留的确认 Plan、Capability、结果和反馈已提炼到 `Bdd/ai/knowledge`；
- 不再需要该 Run 复现、审计 PIC 或重新生成；
- 产品数据和组织保留策略允许删除。

误录、重复录制或无学习价值的 Run 可不提炼直接丢弃。确认经验可用于后续 advisory candidate，
但来源 Run 被删除后不能再证明历史或当前 runtime 事实。使用 Recorder 的退役服务整 Run 删除并
同步 catalog；任一步失败都保留原 Run。

## Portable Knowledge 与跨机器交付

`Bdd/ai/project-identity.json` 必须随项目 Git 保留。Portable Knowledge 位于
`Bdd/ai/portable-knowledge/`，导出和导入前会验证 identity；它保存内容寻址的 advisory record，
不会自动注入上下文、stage、commit 或 push。

同步前先生成只读计划：

```powershell
python -B -m autowork_core.utils.debug_tools.portable_knowledge plan-sync
```

确认 record ID、来源 Capability 和 fingerprint 后，才执行：

```powershell
python -B -m autowork_core.utils.debug_tools.portable_knowledge sync `
  --plan-fingerprint <fingerprint> --user-confirmed
```

更新框架或换机器时：

1. 保留 `.github/`、`ai/`、`Bdd/ai/project-identity.json` 和经确认同步的
   `Bdd/ai/portable-knowledge/records`。
2. 运行 Knowledge Audit，只把 active durable knowledge 放入恢复集，排除 quarantine、Shadow、
   旧 Work Package、锁和可重建状态。
3. 在新位置恢复仓库与批准的恢复集，再重建 Python、ffmpeg、OCR 模型和所需 MCP。
4. 重建代码复用索引并运行风险相称的 Recorder 回归。

需要保留录屏历史或审计证据时，额外归档整个 `artifacts/recording_sessions/`，并保存仓库 commit、
时间、文件数、总字节与 SHA-256 manifest。原始 Run 与 `Bdd/ai/knowledge` 可能含业务或个人数据，
不得未经组织审查推送到普通远端。

## 恢复与按需路由

新会话以 [AI 协作上下文](../../ai/context/project.md) 的长期架构宪法和当前 Git/code/test/evidence
为准；本章只在资产生命周期、备份、知识维护、交付或同步任务时读取。不要复制 VS Code
`workspaceStorage` 作为长期恢复方案，因为 workspace identity 和内部格式不稳定。

Recorder 生成架构的临时修复计划应放在关联 Issue 或 PR，而不是 `ai/context`。Issue/PR 关闭后，
保留代码、测试和维护文档中的长期结论，删除临时计划或将其留在远端历史中。
