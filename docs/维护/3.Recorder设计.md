# 3. Recorder 设计

本文是框架维护者的 Recorder 协议入口，不是普通录制用户的完整手册。普通用户只需要
阅读[编写自动化脚本：录制并交给 AI](../2.编写自动化脚本.md#录制并交给-ai)和
[故障排查：Recorder](../5.故障排查.md#recorder-录制问题)；只有修改 Recorder、排查协议失效、
维护生成链路或确认长期边界时才需要继续读本文。

按读者选择阅读范围：

| 读者 | 只需要读 | 不需要先读 |
| --- | --- | --- |
| 录制用户 | 开头六个任务、启动和录制、录制任务与历史复用 | Evidence Graph、Plan、Transaction、PIC、测试矩阵 |
| 业务脚本维护者 | 启动和录制、时间线校正、F9、AI 可分析程度 | Job lease、上下文预算、内部版本字段 |
| Recorder 维护者 | 全文，尤其是生成 Profile、Plan、AI 契约和当前边界 | 宿主项目真实产品验收账本 |
| AI/Agent 规则维护者 | Recorder Generation Agent、AI 生成契约、Decision Pack、回归测试 | 用户操作步骤的重复解释 |

Feature Step Recorder 用于按 `.feature` 中的 Scenario 和 Step 采集人工操作证据。调试器
只提供一个“Recorder 工作台”入口，工作台分为四个页签：

- **Feature与录制**：管理当前 Feature 的场景录制覆盖和录制资料交接；录制是可选动作。
- **录制任务**：跨 Feature 接收录制资料、搜索已保存录制、继续录制、打开处理/生成并删除不再需要的录制资料。
- **修复与生成**：只展示当前用户任务，推荐直接生成、回答用户权威/授权问题或最小补录。
- **录制内容**：只在已打开当前录制时启用，负责忽略误录和补录插入。

“Feature与录制”和“录制任务”会随工作台一起装载；没有当前任务或可用录制时，“修复与生成”和
“录制内容”页签保持禁用，不显示可点击空页。`open_recorder_tool()` 和
`open_recording_library()` 都打开同一个工作台。

真实产品的录制、校正、AI 生成和 Behave 质量验收账本由各宿主项目维护；框架文档只
定义通用协议、命令和质量门。

## 当前成功生成设计现状（2026-09-08）

Recorder Generation 当前只有一条产品旅途：Workbench 准备并 claim 一个 Job，Copilot/Agent
执行 `advance-job`，系统在同一个 Job 内收敛 typed patch、生成完整候选、通过私有 staging
预检后交给宿主原生编辑，最后由 Transaction/Job Result 给出终态。简单 Job 和复杂 Job
走同一条线；复杂度只能增加 typed batch 或候选文件数量，不能增加 Agent 自由调查、隐藏
fallback、外部文件审批或多轮问题重组。

现行 owner 边界如下，维护和排障时先按这张表定位，不要从对话经验猜测：

| Owner | 拥有的事 | 明确不拥有 |
| --- | --- | --- |
| Workbench / RequestService | 用户触发、重新生成、创建/claim Copilot Job、复制命令 | AI 可判断的业务歧义、技术选择、候选源码、哈希修复、手写 Answers |
| Reconciler / Decision Pack | 把问题分为 user-authority、AI-authority、evidence-required；冻结用户权威/授权 option batch 并编译已提交 Answers | 把所有业务问题都交给用户；把证据缺失伪装成答案 |
| Copilot / Agent | 在 `advance-job` 返回的 `business_answers_required` 批次中调用一次 `vscode_askQuestions` 并通过 `submit-business-review-answers` 提交 option/freeform；根据完整 typed patch batch 提交 AI-authority 选择和稳定命名 | 无当前 `business_questions` 时提问、运行 `submit-business-review`、写 answers JSON、读取 chat resource/外部输出、哈希调试、换行修复、删除重建候选 |
| WorkflowState / GenerationJobService | Job claim、phase/epoch CAS、重新生成新 attempt、替换前归档 frozen Brief、终态 Job Result | 复用已失效 current Job；让 retired Job 依赖可变 request Brief |
| Manifest / Materializer / Candidate Preflight | 完整 system-owned bundle、Page binding、候选文本边界、SHA、私有 staging 预检 | 把无效系统候选交给 Agent 手改或重放 |
| Transaction / File Lease | 写入范围、file lease、scope/PIC/Plan-to-Code、完成 diff、释放或 supersede 过期/替换事务锁 | 让 retired/superseded transaction 持续占用目标文件 |
| QueryService / Review UI | 只读 DTO、当前待办、结果/失败摘要和 changed-files review | 解析底层 JSON 推进状态或自行判定生成成功 |

当前已闭合的代表性静态生成是 Console-SRS.22793 的 `job-3dd645c271106b21`：
`transaction-20260908-022056-704014-b622e994` 完成，`candidate_preflight=passed`，
`workspace_candidate_audit.matches=true`，14 个 `Bdd/` 目标文件生成，Job Result 为
`static_validated/runtime_not_run`，无 warnings、无 active transaction、无 file lease 残留。
这证明当前链路的静态交付闭合，不证明真实产品 runtime 或独立 Oracle 已通过。

这些规则是本次事故后的硬边界：

- “重新生成 Copilot 请求”在任意阶段都可显式创建同一 Request 的新 attempt；旧 Job 必须先
  退休，旧 frozen Brief 必须归档，旧 committed file lease 必须释放或标记 superseded。
- Job-bound Decision Answers 只承载用户权威、授权或安全类问题。`window_closed_during_take` 的
  `expected_close` / `workflow_transition` 属于 AI-authority Plan 选择；非硬阻断的
  close 不确定性在全场景生成期应转为 `generate_issue_placeholder` / 低置信 Review，
  不再要求用户先修复或补录。
- `next_user_interaction`、`submit-job-answers`、answers draft、`submit-business-review`、
  Chat media fallback 都不是当前产品路径；用户权威 Answers 只能在当前 Job 返回的
  `business_answers_required` 批次中通过一次 `vscode_askQuestions` 展示，并用
  `submit-business-review-answers` 命令提交。
- 候选交付的字节规范属于系统：Materializer 输出平台换行和稳定末尾换行，并把 SHA 绑定到该
  交付文本。Agent 只复制候选内容；不能用终端、Python、`Get-FileHash`、删除重建或换行归一化
  来修 candidate mismatch。一次原生编辑后仍 mismatch 是宿主交付缺陷，应停止并报告。
- 系统候选必须先完整预检再暴露给宿主；`system_candidate_invalid` 在写 `Bdd/` 前终态失败，
  Agent 不得查询、手改或重放该候选。
- 全场景生成进入 Job 后，只有身份、完整性、授权、安全范围、写入租约或系统候选内部错误等
  超级问题可以终止。其他定位、复用、窗口关闭、实现或业务建模不确定必须生成占位或低置信
  实现，并在最终 Job Result/Review 中集中说明；不要中途要求用户补录、重录或回答第二轮问题。

用户可以完全不使用Recorder而直接手写自动化脚本。选择Recorder时，只需理解六个任务：

1. 正常录制当前 Step。
2. 用 `F7` 暂停并完成不应生成代码的准备操作。
3. 用 `F9` 标记检查结果。
4. 在校正页忽略误录动作。
5. 在缺失位置补录动作，并确认整段插入。
6. 回答系统和 AI 都不能决定的业务问题。

默认“录制内容”页不要求用户编辑动作类型、技术角色、raw binding、merge/unmerge、逐Action补录
或事后技术备注。系统负责可确定的事件派生、窗口过滤、revision、指纹和完整性校验；
Copilot负责动作组合、技术角色、target/value、输入来源、owner、复用、locator和可验证断言
实现；用户只保留误录排除、缺失动作补录、F9结构化检查意图，以及系统和AI都不能决定的
业务真值、pause归属、待确认跨进程窗口归属、Data Table业务用法、规格冲突和PIC风险授权。
证据缺失不能由系统或AI猜测，必须返回补录。
类型、角色、raw binding、merge/unmerge、技术备注和逐Action补录在默认用户界面中均无
写入口；底层协议仅保存当前的排除/恢复、键盘片段、整段补录、target repair和撤销/重做。
发现缺少typed替代的必要能力时必须失败关闭并由维护者补齐替代，不能把技术属性重新交给
普通用户填写，也不保留旧技术编辑的读取或物化路径。

正式版工作台把“修复与生成”组织为一个用户任务工作区：顶部显示范围、录制质量和
下一步；左侧按Step显示当前录制状态，右侧默认只显示“问题与处理”。当前录制包含F9时按需
显示“F9检查”；生成或真实运行发生后才显示“本次生成”；成功结果才显示“确认结果”。
View只消费Query Service DTO，不直接解析Request、Decision或transaction JSON。

## 启动和录制

```powershell
python -m Bdd.debug_tools
```

1. 点击工具栏“选择 Feature”，打开项目内一个`.feature`文件。工作台不递归加载目录，
  也不承担多Feature管理；显式打开时才在缺少标记时原子写入`recorder-feature-id`。
2. 左侧只展示当前Feature及其Scenario/Examples行，每行显示`未录制`、`未完成`、
  `已录制`、`需更新`或`需处理`；该树是唯一场景选择源。
3. 首次录制默认包含当前Scenario的全部Step。Step表只显示状态、当前行和Step内容，
  不再让普通用户维护抽象的Step范围；已有未完成Run会继续其缺失Step。
4. 选择一个Step；只有Feature没有表达清楚且用户掌握确定的业务事实时，才填写一段
  “业务补充（可选）”并显式保存。不要填写locator、API、等待或动作类型；补充按Step
  独立保存，不会被F7、F9或F10消费。
5. 点击“开始录制此场景”，系统创建任务并引导当前Step；任务建立后主按钮显示
  “录制当前 Step”。默认使用自动跟随窗口，不要求被测窗口提前存在。
6. 需要严格隔离其他软件时点击“限制窗口...”；普通工作台不暴露backend、输出目录、
  视频、截图、控件树深度等采集实现设置。
7. 临时准备操作可按`F7`软暂停；再次按`F7`继续。断言或检查类Step把鼠标停在目标
  控件上按`F9`：Recorder自动采集目标、保存system-inferred检查并显示一条白话摘要，
  不打断后续录制。采集仍在进行时不能再次F9或F10；回执到达后可直接继续。需要修改时
  在审阅的“F9检查”中补充业务含义；需要断言时再选择关系和Feature/Examples/Data Table期望来源。
8. 完成人工操作后，可填写只用于维护追溯的“本次录制说明”，再按`F10`保存。
  说明不会写入Take证据或AI生成上下文。按`Shift+F11`以固定原因放弃本次录制；普通
  `F11`只提示防误触。菜单放弃与跳过各自询问可选原因，不复用本次录制说明。
9. 依次录制、重录或跳过 Step；主按钮会按阶段切换为“保存当前 Step”“完成录制并审阅”和“审阅并交给 AI”。
10. 在审阅中心查看当前Scenario和Step状态。选择Step只用于当前录制证据和局部修复；
  历史部分范围Run仍可读取，但普通新任务不再创建主动排除Step的范围。

录制主操作区常驻提示：录制数据不会自动脱敏，只能使用测试数据，不能输入真实密码、
令牌、患者或其他敏感信息。`StepUserContext 2.0`只保存单一`business_context`；显式保存后
进入Request和Brief。与Feature出现
可证明的相反业务结果时，系统生成无预选业务确认，补充本身不能修改Plan。F9默认Intent
authority为`system_inferred_intent`；用户在Review修订后才成为`user_declared_intent`。
修订绑定原Step/Take或Supplement/event/revision，使旧Request与Capability stale，并在
running transaction期间拒绝。当前观察值不能自动提升为业务期望；无Feature/Examples/
Data Table来源时必须由用户确认或返回修改。F7只保存pause边界、前后状态和差异；F10只消费独立Take总结，
取消与跳过各自拥有可选原因。Run和Take不写通用`note`字段。

### Data Table 语义

Data Table 始终作为 Step 的原始业务数据保存。Recorder 不根据表格形状自动猜测循环，
GenerationPlanV4.2 必须明确声明 `each_row`、`whole_table` 或 `scenario_state`，以及列、
顺序和重置约束。每行需要不同应用初始化、交互路径不同、存在累计依赖或需要独立重试
时，应使用 Scenario Outline/Examples。生成代码禁止硬编码表格行，也禁止调用已删除的
`run_case_matrix`入口。

窗口范围属于每个 Step/Take，不属于整个 Scenario。窗口模式有两种：

- `auto`（默认）：可以零窗口启动；第一次有效业务操作所在窗口成为主窗口。同进程和子进程中新出现的窗口自动纳入。
- `strict`：只采集预选窗口及其所选进程，适合需要严格隔离其他软件的场景。

自动模式下：

- 同一进程或子进程窗口不再由全桌面后台扫描发现；只有真实点击、滚轮、键盘或F9观察等业务事件触达后，才记录 first-seen 截图、控件树和生命周期证据。
- 无进程关系的新窗口不会丢弃，标记为 `provisional`，录制继续，桌面顶层提示“发现待确认窗口”。
- 录制结束后，由 Reconciler 自动判定；证据无法区分时在一次 Decision Pack 中确认该窗口属于业务流程还是无关噪声。
- 事件触达的 owned popup、菜单或对话框如果 `owner_chain` 指向已知业务窗口，Reconciler 先按 WindowView 归属处理；没有 owner 事实且具备独立稳定业务身份时才成为新的 WindowPage 候选。
- 主窗口、显式选择窗口或承载有效时间线动作的窗口在 Step 中关闭时，会记录
  `window_closed_during_take`；无业务事件的自动次要窗口只保留生命周期证据，不产生
  复核提示。窗口关闭不会因为无法获取 after 截图直接判定采集失败。
- 正常窗口关闭含义由 AI 在 Job 内通过 typed patch 或 Plan 选择：`expected_close` 表示
  点击后的预期关闭，`workflow_transition` 表示进入下一业务阶段。无法可靠判断且不属于
  身份/完整性/安全超级问题时，不应中断全场景生成，而应生成可审阅占位并在结果中说明；
  只有系统和AI都不能确定且需要用户权威时，才进入 Job-bound Decision Answers。
- 主窗口用于 `screenshots/before.png`、`after.png` 和 `ui/` 控件树。
- 其他窗口证据写入 `windows/window-XXX/`；生命周期由 `take.json.window_lifecycle` 索引。

UIA/Win32后端、输出目录、视频、截图和控件树等采集实现由项目配置和历史Run profile
管理，不在普通录制旅程中成为每次决策。默认在录制开始前最小化调试器；桌面右上角会
显示非激活、始终置顶的“准备中 / 录制中 / 已暂停 / 保存中”状态条和可用热键。该状态条
不抢占目标应用焦点，也不会进入录制事件流。

录制中每次`MouseMove`都直接使用Recorder同款`ElementFromPoint`解析鼠标下的控件，只读取
控件身份和`BoundingRectangle`，随后用青色边框显示该控件范围。没有停留等待、定时采样、
点击变色、缓存框或第二套目标判断；解析忙时只保留最新鼠标坐标。鼠标离开当前控件范围
立即清框，滚轮会强制重解析当前坐标。边框非激活、点击穿透，不显示控件文本或Value。

悬停解析使用一个录制期持久worker，结果通过Win32消息直接交给高亮窗口，不经过Recorder
面板轮询。MouseMove只进入视觉通道，不写入raw/canonical event、窗口范围、Action或
artifact；暂停、保存、丢弃或关闭时立即清除。只有Windows确认高亮窗口可从桌面捕获中
排除时才启用，因此边框不会进入截图或视频。

录制期间的输入与证据处理分为独立通道。Windows Hook先完成事件分类和稳定ID分配，将
不含私有target binding的原生事件送入journal与边界帧队列；对`mouse_down`和滚轮，再在
输入交给目标应用前冻结元素、事件所在UIA窗口和必要交互祖先。正常UIA延迟不再受15ms
正确性预算限制；500ms只是不允许UIA提供程序永久卡住低级Hook的安全看门狗，触发后保留
原生事件、写入 `target_observation` 负证据并继续录制；同一Take后续目标探测会按健康状态跳过，
避免反复等待慢UIA。提交事件只刷新runtime identity、Value、enabled和visible等状态，不在点击后
重新猜测目标，也不会逐个从Root回查结构XPath。窗口first-seen树/截图仍由独立通道处理，无业务
事件的自动次要窗口不扫描完整UIA树。

按 F10 后先封存 `raw-events.seal.json`，再等待输入、窗口证据、媒体和时间点采集记录收敛，
写入 `EvidenceCompilationResult` 的 `not_started` 状态，然后由Workbench后台触发
`EvidenceCompiler` 物化 Projection、Evidence Graph、Semantic Pack 和 readiness。结构 locator
只使用同一 HWND 的完整、未截断 before/after 树离线验证；缺少完整树、窗口身份不明或跨窗口冲突时
保持 unresolved，由现有 forensic 门禁处理。控件树采集使用有界进程；超时写入 tree snapshot 负证据，
但主录制Session后续Step仍会重新尝试采集，不能让一次慢UIA污染整段证据；补录片段内的树采集
只在该片段范围内记录负证据。`capture-completion.json`
必须证明 raw 与 canonical event ID、数量和顺序完全一致；raw journal、事件富化、窗口证据发布或
媒体通道停止超时、seal 不匹配或迟到回调都失败关闭，不能把部分快照保存为 completed Take。

任务栏和录制器自身事件不进入业务事件流。完成或取消后会恢复窗口，并自动选择下一个
待录制Step。已完成Step再次录制会新增内部Take；旧Take永久保留用于维护追溯、审计和
必要回退。普通审阅UI不暴露旧Take选择，最新完成录制自动成为当前生成证据；维护者
确需回退时只能通过内部owner API切换selected Take。内部取消Take会保留诊断产物，
但不会替换selected Take。

## 录制任务与历史复用

打开调试器工具栏中的“Recorder 工作台”，切换到“录制任务”页。该页只服务录制任务生命周期：
导入录制资料、搜索已保存录制、继续未完成录制、打开处理/生成，以及删除不再需要的录制资料。
View通过`RecorderLibraryQueryService`读取离线Run状态，不解析catalog/detail、不自行验证Bundle，
也不暴露Capability、receipt、catalog或Take版本等内部概念。

选择已保存任务后，页面显示是否可删除；正在录制、正在保存、补录中、写锁占用或running
generation transaction时禁用删除。删除需要用户确认，执行底层整Run原子删除服务；成功后只提示
录制资料已删除，已生成到项目中的脚本不受影响。

历史复用流程：

1. 在“录制任务”中按 Feature、Scenario、Step、路径或 Session ID 搜索。
2. 双击任务或点击主按钮。未完成任务进入“继续录制”；已完成或需处理任务进入“修复与生成”。
  打开历史会话不会创建新 Run，也不会启动 Hook；只有继续录制才重新打开录制运行时。
3. 选择Step后，只查看当前录制证据、问题和局部修复入口；历史Take选择不出现在普通审阅UI。
4. 维护诊断确需回退到旧Take时，通过`FeatureRecordingSession.select_take()`等owner API
  切换selected Take。其他Take不会删除；旧Request保持不变，对应Workflow State变为`stale`。
5. 使用审阅中心显示的唯一主操作：

| 主操作 | 适用情况 | 用户动作 |
| --- | --- | --- |
| `交给 Copilot` | 当前完整或显式部分Scenario范围已完成；即使存在用户权威或授权问题也可进入生成前批次 | Copilot 在 `advance-job` 后一次性展示 option 问题；用户回答后通过 Job-bound 命令继续同一个生成任务 |
| `检查并忽略误录` | 检测到外部进程、孤立鼠标边界或Shell切换等可疑录制动作 | 用户确认是误录后忽略；保留时交给AI或证据门处理 |
| `校正或补录` | 缺少生成所必需的真实证据 | 按右侧具体问题只修复或补录当前Step |
| `查看本次生成` | 生成已完成或未完成 | 查看修改文件、检查结果和首个失败原因 |

后台Workflow状态只投影为用户动作：可交给Copilot、Copilot自动核对录制事实、生成前需要确认用户权威/授权问题、
缺少必要证据或正在更新。自动准备失败时才显示“重试准备”；问题页的AI可处理项只显示
“Copilot会自动处理”，不创建第二个Copilot入口。

生成完成或失败后才显示“本次生成”，列出最近transaction状态、修改文件、失败检查和建议动作。
结果区分三个单调层级：`code_generated`表示已有输出但门禁未闭合；
`implementation_validated`表示静态事务和代码快照有效；`runtime_verified`只在绑定同一Request、
Plan、Transaction和代码快照的真实Behave Scenario通过时成立。Recorder不会为了升级结果层级自动
启动目标产品。

成功且检查通过后才显示“确认结果”：`可以使用`、`我已修改结果`或`不采用`。确认只用于后续复用
已验证实现，不代表在线训练模型。真实Behave运行仍由用户明确启动；运行结果是生成后验证的独立
证据桥，不写入或改写原始Take、Timeline、Evidence Graph或Request。

审阅中心的“问题与处理”只消费白名单化`IssueDTO`：普通UI显示白话标题、Step、当前录制、可定位
操作和标准动作；原始code、selected Take、绝对证据路径、event/HWND/PID/pause ID和repair steps只在
维护诊断、artifact和详细报告中出现。系统不会仅凭 `capture_error`、`tree_not_comparable` 等code要求
重录，而是先生成 `ai/recovery/<request-id>.json` 盘点可用动作、事件、媒体、窗口生命周期和树差异。
恢复分流为：

- **校正时间线**：噪声动作、孤立鼠标边界、任务栏切换、范围外进程动作。
- **V5 证据协调 / 结构化决策**：业务意图、OCR/POS fallback、目标证据冲突、AI可处理的窗口关闭含义、待确认跨进程窗口，以及仍有动作/事件/媒体支撑的采集或树缺口。
- **最小补录当前 Step**：manifest 无法识别 Step、selected Take 目录不存在、结构化事件/动作与所有可视媒体同时缺失、证据文件损坏到无法解析。

可再生派生产物会在准备Request前自动重建，结果写入 `ai/repairs/latest.json`。原始 `events.jsonl`、
截图和视频永不修改；只有 `recovery.hard_blocker=true` 才最小补录当前 Step。AI默认读取Evidence
Context中的action、target、text change、media summary和tree delta；原始events、完整树、图片和
视频只在默认事实不足或矛盾时按Evidence ID展开。

### 自动准备 Copilot 任务

请求维护采用“自动准备、人工触发生成”的边界：

- Step 保存、selected Take 切换或时间线校正后，旧 Request 文件保持不变，对应 Workflow State 立即转为 `stale`。
- 工作台按 Scenario scope 去抖，由有界 `OperationCoordinator` 按 key/revision 取消旧
  任务，只接收与全部目标 Step 当前证据匹配的新 request；Tk 主线程不自动发送聊天，
  也不自动修改业务脚本。
- 任一目标 Step 尚未完成或没有 selected Take 时不物化 Scenario 请求。任一 Step 的
  Take、时间线或证据变化都会让整个 Scenario Workflow stale，但修复仍保持 Step 粒度。
- Request ID 覆盖 selected Take、timeline、Graph、结构化 artifact 哈希、完整 contract、审阅信号和当前 target 可见的结构化经验 revision；无关 Feature/Step 的 journal 追加不改变 ID，重复刷新幂等复用同一不可变文件。
- 最新指针持久化在 `ai/requests/index.json`，重开录制库后不依赖窗口内存恢复。
- 最终执行生成时，`inspect` 读取唯一 Workflow State，`prepare` 冻结 revision/Brief/Plan 并开启事务；“更多”中的复制命令用于诊断和手动重试。
- 自动准备失败时，主按钮切换为“重试准备”；成功后重新读取权威Query投影。该按钮不是
  正常流程的必经步骤。

复制到剪贴板的Job路径形如；用户选择`Recorder Generation` Agent后粘贴：

```text
"<run>/ai/generation-jobs/<request-id>/job-<fingerprint>.json"
```

请求绑定以下版本事实：

- selected Take ID。
- `timeline_revision`。
- `evidence_fingerprint`。
- `evidence/graph.json` 的 graph/source fingerprint；源清单覆盖 events、frames、screenshots、UI tree、视频和所有稳定派生产物。
- `ai/evidence-context/<request-id>.json` 的 context fingerprint 和最小决策 Evidence IDs。
- `generation_contract_version` 和 `contract_hash`。
- 从当前 `BasePage`/页面工厂真实签名计算的 `api_signature_hash`。

任一事实变化后，旧 Workflow/Plan 不能继续用于生成；旧 Request 仍作为不可变审计记录保留。

### V2 Evidence Graph 与覆盖

每个 completed Take 会生成：

```text
<take>/evidence/graph.json
<run>/ai/evidence-context/<request-id>.json
```

Evidence Graph 不替换 V1 artifacts，而是可重建索引：

- 为所有稳定源文件记录 `artifact_id`、SHA-256、大小和类别。
- 为每个 effective action 建立 raw events、目标身份、唯一 locator、文本变化、动作媒体、状态变化和 provenance 包络。
- 将 `structural_role` 与 `interaction_confidence` 分离。
- 排除 `evidence/` 自身和按需抽取帧，避免递归指纹或因查看视频而让 request stale。

Context Broker 提供五类可计算覆盖：

| 覆盖 | 含义 |
| --- | --- |
| integrity | 稳定源 artifacts 是否全部有哈希 |
| event | 原始事件是否进入 action 或明确保留为未关联 |
| action | 每个动作是否具有完整证据包络 |
| context | 最小决策证据是否进入 AI 默认上下文 |
| decision | 每个生成 claim 是否引用有效 Evidence ID |

默认选择的 Evidence ID 必须逐项记录为 claim 引用、`evidence_used`，或带原因的 `evidence_skipped`；报告中的 `context_consumption_coverage` 必须为 `1.0`。最小决策 ID 不能只声明“看过”，必须真正出现在 claims 中。

完整视频不要求每次播放。结构化证据和关键帧充分时，视频显示为 deferred，并记录原因；发生矛盾、动画、拖拽或中间状态缺失时，AI 再按时间戳抽取片段。

### V3 Generation Brief 与风险路由

V3 是唯一生成路径；forensic 仍使用同一个 Reconciler、Plan 和 Transaction，只按需展开更多 Evidence。每次 Request 生成：

```text
ai/reconciliation-reports/<request-id>.json   # 后台完整分类与冲突审计
ai/generation-briefs/<request-id>.json        # AI 默认读取的有界紧凑上下文
```

| 风险 | 条件 | 用户/AI 行为 |
| --- | --- | --- |
| `fast` | 动作闭包完整、结构目标唯一、输入和断言范围明确、无冲突 | 零交互，直接生成 |
| `clarify` | 存在必须由用户决定的业务归属、业务真值或高风险授权 | 一次回答 Decision Pack 的结构化问题 |
| `forensic` | 存在 AI 可解释的目标、窗口、实现或媒体歧义 | AI 只展开命名证据并提交 typed choice 或 Plan；生成期非超级问题转占位/低置信实现，无需用户先处理技术提示 |
| `blocked` | hard blocker、revision 漂移、分类覆盖不完整 | 停止并最小修复/补录 |

Reconciler 必须分类 100% 的默认 Evidence；AI 不再逐项读取或手工回报几十个 Evidence ID。最终报告仍保留 claim provenance、Evidence audit、generation policy 和 Plan-to-Code audit。

Brief 4.6 的`agent_tasks`只列出目标Step、有效Action类型、typed ambiguity和可用调查
工具，不包含规则生成的operation。默认先读紧凑Brief；仅当某个目标、值、gap或Take差异
可能改变Intent时，才用`generation_workflow evidence`或`compare-takes`展开对应事实。

发生过补录或merge的Action会额外携带有界`correction`来源；普通Action没有该字段。
完整路径、媒体、时间线edit记录和merge快照不进入Brief，需要时再查询effective evidence。

Brief 通过 `scenario_intelligence` 给 AI 四类有界上下文：Feature/Rule/Background/Outline/
Examples 形成 `feature_declared` specification；当前 Take 形成 `runtime_observed`
demonstration；现有代码和 Capability 形成带质量画像的 `code_verified` references；
ambiguity/conflict 形成保留原路由的 gaps。四类来源不能互相冒充。Brief 仍只携带每个动作
最终选中的 locator、稳定性摘要和必要 provenance；完整控件树、全部 locator 候选和媒体
留在后台 artifact。Scenario Intelligence 1.1 的`coverage_manifest`确保每个有动作的目标
Step、gap引用Action和每个含gap Step的轻量索引进入默认上下文；被省略的普通Action、
gap与结构化Observation列出稳定ID及展开来源。位置 XPath 会显式标记为
`positional_fallback`。

当 scoped Step 文件声明 `before_app_start`、`after_app_start` 或 `after_app_stop` 时，代码
索引会按当前 Scenario effective tags 提炼 `environment_dependencies`：phase、required
tags、引用的数据 key、helper 调用和质量画像。它用于告诉 AI 许可证/配置等前置与恢复并
不在录屏中；`generation_allowed=false`，不能被当成授权去生成任意文件或进程副作用。

### Generation Profile 与闭合任务

本节只保留当前生成路径的不变量；字段全集、fingerprint细节和恢复实现以
`workflow_service.py`、`generation_job.py`、`generation_contract.py`、Transaction报告和对应测试为准。

- 所有生成必须经 Workbench admission 创建 `Generation Job`；不能从 Request 直接写 Plan 或
  开启 Transaction。
- 当前唯一开放 Profile 是 `generation_first`（界面显示“全场景生成”）：问题前置，Job开始后
  只做有界技术收敛，不中途询问技术问题。
- Profile 只控制 Job 编排，不进入 Request identity，也不能改变 Evidence、Decision、Plan、
  Transaction、Runtime 或 Oracle 的权威边界。`Execution Profile` 仍单独拥有启动/attach和运行授权。
- Workbench 主入口幂等：未完成 Job 默认继续推进，仍有效的终态结果直接进入审阅；用户显式
  “重新生成 Copilot 请求”可在任意阶段为同一 Request 创建新 attempt，并退休旧 Job。
- “维护已有步骤（暂未开放）”只是 UI 占位，不属于 Profile registry，也不会进入 Request、Job、
  Plan 或 Transaction。

#### Admission与Evidence Readiness

普通用户点击生成前由 Generation application service 执行 admission。它只判定是否允许创建
Job，不代表性能、运行或业务质量已经通过。Admission重验：Request/selected Take/revision/目标
Step范围、完整Scenario范围、readiness与Brief覆盖、Decision Answers、Generation Contract、
并发Job/Transaction和Profile注册状态。

拒绝结果只投影到Workflow/UI：用户权威/授权问题进入Decision Pack，证据问题返回校正或补录，stale要求
重新物化Request；此时没有Job，也没有“生成失败”终态。通过时才写入`status=passed`的receipt并
发布不可变Job：

```text
ai/generation-jobs/<request-id>/job-<fingerprint>.json
```

Job是Design前的不可变任务包，只保存内容寻址引用、Profile lease、admission receipt和策略身份；
不复制Evidence正文，不替代Brief、Plan或Implementation Manifest。AI默认读取紧凑
`AIContextEnvelopeV1`，完整Brief/Job/Contract仍是backend identity或按需查询依据。AI Context
Budget只是效率诊断，超过目标给出警告或评估失败；只有真实容量无法容纳最小必需上下文时才
以`framework_capacity_defect`失败关闭。

所有权分层保持不变：`workflow_service.py`编排admission、Job claim、阶段迁移和终态发布；
Job repository只做canonical校验与不可变I/O；`request_service.py`只做Workbench facade；
Transaction、Run Result和Oracle各自拥有结论；`query_service.py`只读DTO，不推进状态。

#### 状态与租约

Workflow State 5.0 是唯一运行状态源。它保存当前Job pointer、phase/epoch/claim、当前
Plan/Transaction pointer、只读 timing 账本、已终止attempt历史和最后Job Result指针。状态语义为：

```text
draft/needs_adjustment/blocked/stale
  -> admission passed -> ready(current Job, not claimed)
  -> start Job        -> running(design)
  -> Plan accepted    -> running(implementation)
  -> static complete  -> running(runtime/oracle) or terminal
  -> completed | failed
```

`forensic`是允许进入Job的命名调查范围，不是要求用户处理。Workbench复制命令前claim Job并
开始计时；Agent Hook只绑定同一已claim Job。Job-bound option Answers最多一次批次；Answers不能携带
operation、locator、ownership或其他技术Plan字段。证据缺口必须在Job创建前拦截，不能在生成期
临时转成用户补录问题。

所有mutation都在RunWriteLock内做CAS校验：调用者必须提交Job identity、claim和expected epoch；
成功后epoch单调递增，过期调用不写入。Plan、prepare、finish重验current Job和上游lease；
Contract或Profile变化会退休Job/Plan，但不改写Request或仍有效Answers。替换Job前必须归档旧
Job的 frozen Brief；退休或 superseded 的 transaction 不得继续持有 file lease。需要新业务权威、扩大
Job scope、绕过安全门或维护框架时必须结束Job，不能靠更多模型轮次继续。

#### Job终态结果

Transaction report拥有实现、scope、PIC、Plan-to-Code、receipt和静态完成结论；Run Result与
Oracle分别拥有运行和独立业务验证。Job结束时写入不可变`GenerationJobResultV1`，只引用并验签
这些owner artifact，统一投影category和next action，不回写或升级原结论。静态成功但未授权运行时
以`static_validated/runtime_not_run`终态；必需Runtime/Oracle失败或不可得必须给出明确失败category。

唯一公开入口是用户选择`Recorder Generation` Agent并提交Workbench复制的Job命令或路径。正常路径
优先执行`advance-job`；`inspect-job`、`settle-job`和`generate-job`只作为诊断、兼容或底层调试入口。
公共命令清单以`generation_workflow --help`和`ai/prompts/recorder-generate.md`为准。

交互式实现交付必须走宿主原生编辑：`candidate_files`按`files[].operation`创建或整文件替换，
但只有完整system-owned bundle才进入产品交付。系统先用Capsule封存的Feature/Bdd源码在事务私有
staging root重建候选，并复用Python、locator、Step scope与Plan-to-Code验证；通过后才创建
Transaction/file lease并暴露紧凑候选索引。宿主从项目内`native-edit-sources`读取每个源文件一次，
在一个assistant turn提交独立原生编辑；仓库不伪称拥有VS Code原子WorkspaceEdit API。
候选文本边界由Materializer负责，使用平台换行和稳定末尾换行；Agent不得哈希调试、删除重建、
归一化换行或手工修复candidate mismatch。一次按候选原文原生编辑后仍 mismatch，应报告宿主
交付缺陷并停止。
`system_candidate_invalid`在写工作区前终态失败，Agent不得手改、重放或查询该候选。显式
headless/debug路径才允许Transaction在file lease下物化。finish阶段
继续拥有Python、locator、Step scope、revision、策略、PIC、证据、ambiguity和Plan-to-Code验证；
scope、journal或lease失败都保持失败关闭。用户撤销由宿主负责，Python不得后台抢回或重写。

`inspect-job`返回默认AI上下文、预算和当前`job_transition`；下一条CAS命令必须使用返回的phase、epoch、
claim和next action。Prompt只描述工作流，BDD instructions独占生成规则；系统不通过截断事实满足预算。
AI Capability Registry提供动作知识与真实签名，Action Knowledge是按需只读投影，不进入默认上下文，
也不推荐、扩展或重排候选。静态`compatible`不是Runtime证明。

### Decision Pack

Decision Pack 替代自由文本 interview 和总体调整。系统只展示需要用户权威的业务归属、业务真值与高风险授权问题；AI-authority 的业务歧义进入 Job，由 AI 基于冻结 facts/candidates 在 typed patch 或 Plan 中选择。Decision Pack 5.11 按“哪个Step、看到什么、为何不确定、是否有依据的倾向、每个选项会如何影响脚本”展示白话`presentation`，并排除只有系统默认拒绝结果的伪授权问题。它同时拥有提交后权威检查中的 `value_authority`，用于 Step 文本业务值与录制输入值冲突。Review Query按问题已有的Action/Evidence锚点投影动作前后帧并在内存中标记目标，让用户先看到问题现场；每帧路径必须位于Take、Session和Project边界内，内容摘要在投影及实际预览或打开时都要复核。显式只读的`generation_workflow decision-media <request> [--question-id]`复用同一投影，返回Request revision、Context fingerprint、验签后的相对帧路径及仅在可证明时的目标/点击覆盖层；`blocked`/`stale` Request、越界、缺失或篡改帧都失败关闭或明确降级。该查询不进入默认`inspect`上下文。截图不进入Pack指纹、不替代业务事实，无可信动作媒体时退化为规格文字。Data Table问题只确认独立行、连续行、整表或供后续Step使用的业务关系，不向用户暴露shape、consumer、列角色或context key；AI提交完整技术`table_usage`，系统只校验它不违背用户outcome。pause问题展示新增、删除、变化节点和受影响窗口计数，不复制完整控件树。纯业务真值、pause归属和有效PIC授权不预选，同一Action的AI实现ambiguity也不能排除有效PIC授权问题。展示与option一起进入Pack fingerprint。自由回答只固化为业务事实，不能直接修改技术Plan字段。

- 没有用户权威问题：跳过Decision，AI直接完成Intent。
- 仅有建议但不影响代码：显示摘要但不阻塞。
- 会改变代码且有验证候选：阻塞一次 Decision Pack 批量回答。
- 没有可验证 option 的证据缺口：进入 forensic 或最小补录，不生成空问题。
- hard blocker：Decision Answers 不能放行。

Decision Pack 5.11、Answers 5.3 和 Plan 4.4 都与 Request revision 绑定。Plan 还绑定
Answer fingerprint、Brief basis、Design identity、Generation Contract lease和Job lease。
Take、timeline、Semantic Pack、audit 或 contract 变化后自动失效。5.11编译器不接受
`operation`、`binding`、`role`或完整`table_usage`技术patch。

Decision Answers 只承载用户权威和授权问题，并复用同一验签媒体投影。Workbench 提交前只拦目标 Step 未完成、hard evidence/readiness blocker、刷新中和 Job 创建失败；普通用户权威问题不再阻止复制 Copilot 命令。正常路径由Workbench
创建并claim Job；`advance-job` 在完整生成前返回 `business_answers_required` 问题批次、
`vscode_askQuestions` payload 和提交契约。用户回答后，Agent 只运行 Job-bound
`submit-business-review-answers` 命令，后端持久化 Answers 并继续同一生成动作。
AI-authority 业务歧义留在 claimed Job 中由 typed patch 或 Plan 选择解决；
已claim Job 若仍有未回答 Decision Answers，必须停在 pre-generation option batch，不能进入完整生成；
Agent 不得在无当前 `business_questions` 时调用 `vscode_askQuestions`、写答案草稿、
运行已退役的`submit-job-answers`或`submit-business-review`、读取
`chat-session-resources`或外部terminal-output，也不得用终端、PowerShell、Python `-c`、
here-doc或here-string重建问题。
PIC只有在审计通过、同时存在“授权”
和“不授权”两条真实路径时才进入用户批次；只有 `deny-pic` 时由系统执行默认拒绝并继续其他
locator或typed placeholder。简单与复杂Job共享“零或一次Job-bound option Answers批次 -> 一次typed batch ->
一次原生候选编辑 -> 一个终态结果”的外部旅途。

用户体感预算单独作为产品门：必须由用户处理的 option Answers 在 `advance-job` 返回后应立即可见；
中途外部文件审批为零。静态Job仍遵守300秒/大Job 1800秒目标，
但不能用该宽松总预算掩盖问题展示、答案提交或失败收口延迟。

点击“补录或重录”会把已有当前Run恢复到录制工具，自动定位对应Step，并使用`auto`窗口模式。再次保存只会增加`take-XXX`，不会覆盖已有证据。

复用历史录制的内部维护原则：

- **复用证据**：重新打开已有当前Run，由维护者通过owner API切换Take、校正或重新生成RequestV3。
- **更新能力**：在同一 Run/Step 下新增 Take；普通UI使用最新完成录制，维护者必要时才调整selected Take。
- **跨 Feature 复用**：优先复用已经生成并确认的 Step Definition、Page Object 和 locator，不要把旧视频当作运行脚本。

## 已确认能力

工作台不再提供“已确认能力”页签或“打开能力文件”按钮。Capability仍由生成和反馈链路自动维护，
仅作为后续AI复用候选；用户在录制任务页不管理能力文件。

用户明确确认的 PlanV4.2 可以直接发布能力。对于 AI 自动生成结果，“认可生成结果”先分为
`accepted_static_only`、`accepted_runtime_verified`和`accepted_oracle_verified`。静态认可只作为
advisory反馈，不进入强正向Capability候选；只有runtime或oracle verified的accepted反馈才可形成
复用候选。第二个 transaction 必须来自不同 transaction、Request 和录制Session，且出现相同业务
Step 模式、窗口 owner 与有序 operation 契约并再次获runtime/oracle verified认可后，
系统才生成：

```text
Bdd/ai/knowledge/capabilities/capability-<id>.json
Bdd/ai/knowledge/capabilities/catalog.json
```

能力detail文件包含发布时已确认的Plan、源Step、selected Take、timeline revision、request
和plan fingerprint，并保持不可变。当前`confirmed/stale`状态由单个原子catalog投影；
`load_capability()`将catalog状态合并到detail事实，避免多文件更新产生半状态。机器自动闭合
的Plan不冒充用户确认能力；一次成功案例也不自动升级为共享抽象。后续AI生成优先复用
已有Page Object/locator，再决定是否生成新实现。

accepted transaction发布能力前重算completion/result fingerprint，并要求完整生成根代码
snapshot与finish时一致；`completed_no_changes`复用的既有代码同样受该门约束。
能力记录保存发布时snapshot fingerprint；代码变化后业务确认事实仍可作为advisory参考，但复用候选不再声明
当前`runtime_verified`，当前代码和文件hash始终优先。

时间线、F9、selected Take或重录改变后，旧Workflow State会stale；Capability按源Run、
Step、Take和timeline revision精确失效，不影响同Step的其他Take能力。RequestV3和
Capability detail保持不变用于追溯。

## 项目经验记忆

Recorder 会在多次录制和生成之间积累项目经验，让后续 AI 不再从零理解项目：

```text
Bdd/ai/knowledge/project-memory/events.jsonl
<run>/ai/memory-context/<request-id>.json
```

经验事件来源分级：

| authority | 含义 |
| --- | --- |
| `user_confirmed` | 用户确认的 PlanV4.2 或生成反馈，优先级最高 |
| `code_verified` | 当前代码和确定性验证可证明的事实 |
| `generation_result` | 某次生成的结果、修改文件和验证状态 |
| `historical_case` | 可供参考的历史案例 |
| `ai_inferred` | AI 提炼的候选洞察，确认前只能作为 provisional |

每次生成前，框架会按当前 Feature、Step、业务文本检索相关经验，并把它们分成：确认知识、已接受结果、历史纠正、生成历史和 provisional 洞察。Request ID、Memory Context 和 Brief 使用同一次目标快照；Brief 中的 `memory_digest` 最多 4096 bytes、6 条，只保留允许的结构、摘要和哈希，不带任意 payload、绝对路径、原始媒体或敏感值。

AI 可在 Plan 顶层声明 `memory_trace.applied/dismissed`，每侧最多 6 条，每条只含当前 Digest 的 `memory_id` 和短原因。未知 ID、同一 ID 同时采用/拒绝会在 Plan 提交时拒绝；未声明 trace 不阻塞生成，但 transaction 报告会记录 warning。报告只从冻结 Plan 派生 `memories_used/rejected`，不接受 finish 参数自报。

生成成功且检查通过后，工作台按需显示“确认结果”：

- **可以使用**：把这次实现记录为正向案例；首次形成候选，第二个独立同构案例再次确认后才发布confirmed Capability。
- **我已修改结果**：记录用户最终修改后的文件快照和说明。
- **不采用**：作为负面案例，后续AI不应直接复用。

确认可以重复提交；新确认会supersede同一生成报告的旧确认，但旧事件仍保留用于追溯。
它用于以后复用已验证实现，不代表在线训练模型。项目经验目录属于“更多”中的维护入口。
首次构建Request时记忆不可用可降级；新Request一旦绑定相关revision，事务前无法纯读取复核
会fail-closed为`stale`。`running` transaction使用冻结Brief/Plan，不因journal追加中断；
完成报告仍可审阅和确认，再次prepare才要求吸收最新相关经验。

Knowledge Store 健康检查是严格只读操作，不初始化、迁移、修复或删除文件：

```powershell
python -m autowork_core.utils.debug_tools.recorder.knowledge_audit artifacts/recording_sessions
```

## 采集范围

每个 Step Take 会采集：

- 原始 Feature、Scenario/Examples 参数、Step 关键字、文本和源码行。
- 鼠标按下/抬起、左右键、滚轮和键盘按下/抬起事件。
- 滚轮原始 delta、方向和标准 120 单位换算后的 steps。
- 派生的单击、双击、右键、拖拽、滚动、键盘序列和 `F9` 观察目标。
- 操作点或键盘焦点对应控件的矩形、属性、祖先链和局部兄弟/子节点。
- Child/XPath候选先标记deferred；录制结束后只用完整、未截断且同窗口的树快照补验
  唯一性、目标一致性和跨快照稳定性。
- Step 开始和结束时的受限控件树，以及 added/removed/changed diff。
- Step 边界截图、动作边界候选帧、动作前后联系表和独立 MP4 视频。

动作边界帧由独立线程采集，不等待耗时的 UIA 控件检查。鼠标动作以按下前为 `before`，以抬起为 `commit`；键盘动作以序列首键按下前为 `before`，以序列末键抬起为 `commit`。提交后分别尝试采集 immediate、probe 和 settled 候选帧，并记录相对事件的 `latency_ms`。这避免把第一次按键或鼠标按下画面误当成操作结果。

Step 的 `screenshots/before.png` 和 `screenshots/after.png` 只表示整个 Step 的开始/结束边界，不代表任一具体动作的前后状态。分析单个动作时必须优先读取 `action-media.json`；旧 Take 没有动作边界帧时才回退到事件截图，并通过 `source: event_screenshot_fallback` 和 `stage: event_fallback` 明确标记。

控件树默认最多读取 8 层、1200 个节点。复杂应用可降低深度或节点上限；快照达到上限时会写入 `truncated: true`，不会无限遍历。

录制数据不做隐私过滤或脱敏。键盘事件、控件 Value、截图和视频按实际内容写入产物。

## 定位策略

录制器先比较结构候选的稳定性，再在同一稳定级别使用以下优先级：

```text
唯一 Child -> 唯一 XPath -> OCR + Region -> POS
```

- Child 和 XPath 必须通过框架正式定位路径回查，并确认结果唯一且指向被操作控件。
- 唯一 Child/简单 XPath 失败后，Recorder 才启动有界结构搜索：最多检查 4 层稳定祖先、
  3 层目标容器、同行/Label 兄弟及两层锚点子节点，并优先组合 `auto_id`、Value、name
  与目标列；`Row N` 和嵌套 Text 的动态显示值不会进入稳定路径。
- 结构候选最多保留 16 个，找到高分唯一候选后立即停止低价值验证，不把整棵树交给 AI。
- 每个Action最多冻结4个内容寻址的已验证结构候选。Brief只提供有界摘要；AI需要改变
  默认选择时按Action展开完整候选并提交`locator_candidate_id`，不能自由手写XPath。
  Design、Plan和Manifest都会重新验证候选属于该Action、Root一致且仍为唯一目标。
- 同一目标的重复事件提供 `repeated_unique` 信号；完整、未截断且未达到深度上限的 Step
  前后树可进一步证明 `cross_snapshot_unique`。跨树歧义候选会降级，树缺失、截断或
  达到采集上限时不作稳定性推断。
- 所有结构候选都无法唯一回指目标时，只从最佳歧义 XPath 生成一个零基 `[N]` 兜底；
  兜底会再次经生产 XPath 引擎验证，优先保持稳定表格/面板祖先范围，不直接退化成
  全桌面索引。
- OCR 只作为有可见文字时的未验证草稿，Region 指向当前顶层窗口 locator。
- POS 使用 `[x, y, source_width, source_height]` 四值契约。
- 进入全场景生成后，OCR/POS 能形成可执行兜底时不应直接阻断；系统应生成低置信实现或
  `unresolved_generation_issue` 占位，并在结果页说明定位风险。只有无法形成可执行动作、
  证据完整性坏、授权/安全边界失败或会伪造业务事实时，才返回补录/修复。
- 软件触发但无稳定criteria的特殊顶层popup，有验证过的POS候选时生成低置信坐标定位并记录
  `top_level_root_without_criteria_pos_fallback`；当该 owner 的全部生成 Action 都是冻结 POS 时，
  使用 `BasePage + pos.yaml`，不生成空 `WindowPage` root。混有 Child/XPath/OCR/PIC 或 View 时
  不适用该例外；无 POS 才占位。
- 已精确分类的非安全技术缺口也走同一路径：滚动归属审阅、unsupported assertion
  implementation、无效技术 value binding、控件最终状态不确定，都由 AI typed choice 或
  `generate_issue_placeholder` 处理。占位只覆盖其冻结 Action ID，并按该 Action 的录制顺序
  写入 `unresolved_generation_issue`；同一 Step 的其他可生成 Action 仍继续生成。未分类缺口
  仍是框架分类缺失，不能由外层 fallback 猜测。
- PIC 明确排除，不会出现在录制候选或 AI locator 草稿中。

目标证据分为相互独立的维度：

| 维度 | 含义 |
| --- | --- |
| `structural_role` | `container_like`、`leaf_like` 或 `unresolved`，只描述 UIA 树角色 |
| `locator_validation` | 是否唯一匹配并回指录制目标 |
| `locator_stability` | 单次、重复事件或完整前后树上的稳定性摘要 |
| `same_runtime_target` | 动作关联事件是否保持同一 UIA runtime ID |
| `same_native_handle_target` | runtime ID 不可用时，同一 action 的全部事件是否保持相同非空 HWND 与进程 ID |
| `same_observed_target` / `identity_basis` | 综合 runtime ID 或严格 HWND+进程证据；两者均不可用或冲突时仍 fail-closed |
| `state/media outcome` | Value、树差异或关键帧是否印证动作结果 |
| `interaction_confidence` | 综合上述证据得到 high/medium/low |

`Document`、`Canvas`、`Pane` 或空白区域不自动等于弱目标。唯一 locator、目标一致和结果证据充分时，container-like 目标仍可达到 high；只有定位缺失、目标冲突或证据包络不完整才进入复核。

## 产物目录

默认输出到 `artifacts/recording_sessions/`。目录使用“业务名称 + 稳定短 ID”：名称方便人识别，
短 ID 避免同名 Feature/Scenario/Step 混到一起；完整 id/key 保存在 manifest、catalog 和
target-index 中。当前运行时只接受当前协议版本，旧Run必须通过独立迁移或便携导入处理，不能
手工改版本号。

维护时只需要记住这些根：

| 位置 | 作用 |
| --- | --- |
| `artifacts/recording_sessions/catalog.json` | 录制Run索引 |
| `<run>/manifest.json`、`source.feature`、`feature-plan.json`、`scenario.json` | Run身份和业务快照 |
| `<step>/takes/take-*/` | 原始事件、截图、视频、窗口、暂停和派生证据 |
| `<take>/current-projection.json`或投影目录 | 当前effective timeline、locator、media和Evidence Graph |
| `<run>/ai/` | Request、Brief、Decision、Workflow、Plan、Transaction和recovery派生产物 |
| `Bdd/ai/knowledge/` | 从Run提炼出的长期项目知识，不保存原始媒体 |

RequestV3是生成入口，Workflow State是唯一运行状态。AI默认读取Brief/Plan；Reconciler在后台

### 跨机器交付录屏

普通跨项目交接使用Feature录制资料包：“Feature与录制”导出当前Feature或当前场景，
“录制任务”导入。当前Feature至少有一个有效录制即可导出；未录制Scenario不进入包，也不构成错误。每个包只包含：

- `feature-delivery.json`：Feature身份、源码/包SHA、Scenario与Run清单；
- `feature/source.feature`：带持久Feature ID的当前源码；
- `evidence/recording-package.zip`：当前已有录制的Scenario/Examples对应Run。

场景子集导出携带完整Feature快照，但证据包只包含该场景Run；它不会覆盖Feature级“最近导出”
基线。部分Run可以交接和继续录制，但不会被标为完整场景生成资料，也不能通过
`generation_first` admission。导入前必须只读验证固定成员、SHA、Feature持久ID、项目相对路径和
录制证据；本地同ID内容不同、重复ID或路径含符号链接都拒绝。源工程的Request、Brief、Plan、
Workflow、Transaction和生成代码不进入包。

Feature可在项目内移动分类；生成时ScopeBinding只在原路径不可用或身份不符时查找唯一同持久ID的
当前Feature，并再次比较完整业务指纹。当前Feature没有生命周期总状态，只投影场景录制状态与真实问题。

源机器完成并关闭录制后，可以直接导出整个录屏库：

```powershell
python -m autowork_core.utils.debug_tools.recorder.recording_portability export `
  artifacts/recording_sessions recorder-evidence.zip
```

模板和结构化Data Table录制证据，并用逐文件SHA-256清单防止传输损坏；机器路径相关的
Request、Brief、Plan、Workflow和Transaction不进入便携包。导出读取期持有短期快照租约，录制、
补录或时间线校正正在写入时失败关闭。

```powershell
  recorder-evidence.zip artifacts/recording_sessions
```

导入先在临时目录校验ZIP和全部SHA-256，拒绝路径越界、符号链接、同名Run或重复Session；通过后
才原子放入录屏根，重定位`output_root`、重建AI投影和catalog，并为已完成Run重新物化目标机器
Request。目标机器仍需通过Workbench admission创建Generation Job。工具界面的最近导入/导出活动
只用于审计和恢复，不属于Run evidence，也不进入便携包。Feature/Scenario/Step稳定ID规则与录制
目录一致：注释、空行和源码行号移动不改ID；路径或业务文本变化会生成新ID。

## F7 软暂停

F7 使用软暂停，不卸载 Hook，也不停止 ffmpeg：

- 暂停期间的鼠标和键盘不进入业务动作。
- 视频保持连续，避免多次启停造成画面和时间轴缺口。
- 写入 `pause_start` / `pause_end` 原始边界事件。
- 主 Take 保存 `pauses/pause-XXX/start.png`、`end.png`、前后树和 `tree-diff.json`；补录保留同一 Hook 的暂停边界事件和连续视频。
- Recorder不采集Pause文字；`start_note`和`end_note`保持为空。
- 暂停期间目标窗口发生状态变化时，readiness 产生 `pause_state_changed`，要求确认它是前置准备、当前 Step 业务动作还是无关变化。

F7 不会撤销被测应用中的真实操作。撤销/重做仅针对录制后的时间线校正。

## 时间线校正

时间线采用非破坏性、revision-addressed 证据投影：

```text
events.jsonl             原始输入事实，只读
actions.auto.json        自动推导动作，只读
supplements/             独立补录片段，只读
timeline-edits.jsonl     人工校正记录，append-only
current-projection.json  当前完整 revision 的原子指针
p/<base32-revision>/      新 Take 的 effective events/actions/locator/media/Graph
```

Take不在根目录双写 `actions.effective.json`、`timeline-state.json` 等派生文件；revision全部通过pointer发布。

校正窗口默认只显示自然语言录制内容和以下任务：

- `忽略错误动作` / `恢复动作`：内部追加`exclude/include`编辑，原始证据不删除。
- `补上缺失动作`：先选择插入位置，再录制片段；完成后一次确认将全部Action按原顺序
  插入。取消确认时片段保留，但不影响effective evidence。
- `撤销` / `重做`：只操作append-only校正记录。
- `完成校正`：返回审阅并使用最新revision。
- 右侧只读查看操作前、操作后、差异和视频帧，不提供技术字段写入口。

普通生成直接使用未整理的有效Action。AI负责动作组合、技术角色、输入来源以及
target/value Action选择，并可在Intent中把明确的焦点或窗口transport Action列入
`ignored_action_ids`。系统只接受冻结transport角色、用户Decision授权，或被紧邻同目标
输入操作吸收且没有独立效果的Edit焦点Action；其他Action必须由operation或既有行为覆盖。
系统从AI选择确定性派生provenance并校验完整覆盖；不得要求用户先改类型、设角色、绑定
数据或merge，才允许进入生成。

Timeline协议继续支持排除/恢复和撤销/重做，不物理删除原始事件。在工作台“录制内容”页补录
缺失片段时，补录与主 Take 共用 Hook、视频和时间同步运行时，并继承原 Run 的截图、
监视器、窗口模式、进程过滤、目标窗口身份和“录制时最小化”。通常无需重新选窗；
`auto` 模式可由第一次业务操作确定窗口，只有 `strict` 且原窗口无法恢复时才要求选择。

- 补录启动后使用与主录制相同的右上角非激活状态条、颜色和提示；同样支持 `F7` 暂停/继续、`F9` 标记观察目标、`F10` 完成和 `Shift+F11` 丢弃。
- 默认补录完成后只允许一次确认整段插入到冻结锚点前或时间线末尾；取消时保留片段但
  不影响当前 Graph、readiness 或 Request，确认插入后才参与生成。用户不能从补录片段
  逐Action挑选或重组；动作组合由AI在Intent中完成并由系统校验。
- 在 `操作前`、`操作后`、`差异`、`视频帧` 四种动作视图间切换；默认显示操作后。
- 图片预览使用可滚动 Canvas；支持 `+`、`−`、`适应`、`100%`，以及 `Ctrl + 鼠标滚轮`，缩放范围为 25%～400%。缩放只改变显示，不修改原始图片。

Timeline协议只接受`exclude/include`、完整按键片段、整段补录和系统验证的target repair。
Raw证据仍逐条保存`key_down/key_up`，但普通检查页将匹配的一对事件显示为一个按键；
忽略或恢复一次按键时原子处理这对事件，不允许用户留下半个按键序列。缺少down或up的
异常证据仍显示为一条“记录不完整”的按键，交给证据门处理。
PlanV4.2直接用`target_action_id`、`value_action_ids`和`ignored_action_ids`组合原始Action，
并由Proof Compiler及Transaction校验完整覆盖和忽略依据。

每次校正会：

- 更新 `timeline_revision`。
- 重新物化 effective events/actions/locator 和 action-media。
- 立即重建 Evidence Graph，而不是等到 Request 准备时再被动修复。
- 重新计算 readiness 和 catalog。
- 保持旧 RequestV3 不变，并将引用该 Take 的 Workflow State 转为 `stale`。

校正命令先携带窗口当前的 `timeline_revision`，再在短期 Run 写租约内检查 revision、
追加 edit、物化投影并刷新 Session/AI 派生产物。其他窗口已提交新 revision 时，旧命令
失败关闭并重新载入最新投影，不覆盖对方修改。耗时工作统一由 `OperationCoordinator`
执行；切换Take、提交业务确认、保存反馈、Request准备和Job admission不得在Tk回调线程
读写或哈希产物。Request、Job和Command使用各自精确的operation key消费结果，不能用公共
前缀混取；同Request、同Profile、同Contract的ready Job重复admission直接复用现有Job。
执行，完成后直接消费已物化 state，不再重复物化；操作超过约 200 ms 才显示不定进度
提示。busy 期间禁用冲突编辑并阻止普通关闭，Tk 主线程仍可重绘和响应窗口。

新的business-v1 Request ID覆盖selected Take、timeline、Graph、结构化artifact、审阅
信号、target-relevant memory revision、Execution Profile和目标Step的`StepUserContext`
revision，但不包含Framework Contract。同一个Step
更换Take、修改时间线或保存新业务说明后不会复用旧Plan；未修改的另一个Step说明不会使
当前单Step Request失效。Plan 4.4单独冻结当前Generation Contract
lease；Contract变化保留同一Request和Decision，只退休旧Plan并要求重新Design。

### 简单旅途综合发布门

`framework_validation.evaluations.simple_path_evaluation`只读评分fresh生成Artifact，不进入
生产运行协议。它同时检查正确性、用户成本、可维护性、安全、执行真实性和效率，而不是只
追求速度或测试数字。默认目标为一个Request、一个Plan、一个Transaction、零重复业务问题、
稳定公开命名、仅业务文件、默认上下文不超过50 KiB、Transaction不超过180秒、Request到
静态完成不超过300秒；100到600个BDD Step的大任务静态完成目标不超过1800秒。有Execution授权时必须绑定真实Run Result和框架注册的独立业务
Oracle；无授权时只接受静态验证且`runtime_not_run`。没有可信回执的模型调用次数和整机
无关进程数标记`not_measured`，不能自报为通过。600 BDD Step本地基线、Manifest、候选与
静态验证门只证明确定性Python执行面；真实宿主命令到完整diff的30分钟端到端仍必须在可调用
模型与原生编辑宿主中单独验收。

## GenerationPlanV4.2

所有生成都必须有一份 revision-bound `GenerationPlanV4.2`：

```text
ai/plans/<request-id>/plan-<fingerprint>.json
```

- Reconciler 只生成事实、候选和 typed ambiguities，不自动物化或确认 Plan。
- AI提交GenerationDesignV1，只负责业务概念、ownership/reuse、operation、target Action、
  value source、table/runtime关系和实现策略。系统保存原Design并计算独立指纹，再编译
  Scenario Model、路径与完整Plan证明；相同编译结果但不同Design仍拥有不同身份。
- `needs_adjustment` 时，用户一次回答 Decision Pack；AI 再完成受这些回答约束的完整计划。
- `forensic` 时 AI 只检查命名证据，并在 `ambiguity_resolutions` 中提交声明过的 AI outcome；evidence-required outcome 要求补录，不能由 Plan 放行。
- AI 必须声明 `scenario_model.model_version=1.0`、摘要、候选 `states`、按 Feature 顺序覆盖
  全部目标 Step 的 `steps`，以及可选的前向 `transitions`。Step 角色固定映射为
  Given=`precondition`、When=`business_action`、Then=`business_assertion`。
- 每个 state、Step 和 transition 都必须用 `support` 引用 Brief 内已知 ID，并明确标记
  `feature_declared`、`runtime_observed`、`code_verified`、`user_confirmed` 或
  `ai_hypothesis`。框架只验证引用、范围、状态 ID 和前向顺序，不自动创造业务状态或因果。
- 完整且只有一个目标Step、无Data Table时，可以声明`mode=single_step_intent`：保留Step
  角色、reason和support，states/transitions及状态消费产出必须为空。多Step、部分范围和
  Data Table仍使用完整状态模型。
- 当前新Plan的`source.plan_origin`必须是`external_ai`、`deterministic_surrogate`或
  `human_authored`，并进入Plan fingerprint；来源与confirmation source不一致时拒绝提交。
- 精确 Gherkin Step 只作为候选；AI 检查函数体后，才能用冻结 candidate ID 和明确 `covered_action_ids` 声明行为复用。
- 每个有效 action 必须被有序 operation、冻结的既有行为覆盖，或由已验证的
  `absorbed_by`关系覆盖；`activation_for`和`transport_for`只解释关系，不能省略物理
  operation。`ignored_action_ids`仍只接受冻结transport、用户Decision授权或当前同目标
  输入吸收安全门，不是动作组合机制。
- `locators[].evidence_name` 可把机器化录制名称映射为长期业务名称；映射目标必须是同一
  operation覆盖Action的冻结Root或locator，不能借此更换目标或绕过断言候选校验。
- 既有 WindowPage 的 Locator 复用由系统自动准备：只有旧 `child/xpath` Locator 在当前
  完整控件树中唯一命中同一录制目标时，才复用旧业务 key。复用记录绑定 Step、Action、录制
  目标、WindowPage owner、Locator 文件哈希与 key 结构指纹；即使同一 YAML 同时新增其他
  控件，旧 key 也不能被生成流程改写。多个旧 key、同名 key 无法证明、候选文件已变化或
  自动后缀命名冲突时，相关 Step 生成 typed placeholder，并在“本次生成”中显示待维护项；
  这不是要求用户重新录制，普通界面也不展示 XPath、YAML 或哈希。
- 每个 operation 记录 target、parameters、value/source、action/evidence/effect/decision IDs、confidence、uncertainty 和 reuse reference。
- 普通系统F9是中性Observation；AI可把有typed intent与冻结target的observe Action选择为
  `save_text`或`save_attr`生产者，并声明唯一`result_binding`。一个或多个后续operation用
  `source=runtime.<binding>`消费；相同值和相邻Step只提供advisory线索，不能自动连线。
  每个binding必须同Scenario内先生产后消费且至少有一个consumer。`get_variable()`只作为
  直接值参数或既有Page方法参数的实现辅助，`set_variable()`不得由Recorder生成。
- runtime source与明确的Feature/Examples/Data Table/Step参数来源冲突时不得静默覆盖。
  Plan-to-Code核对producer、consumer、跨Page方法形参和相对Transaction基线新增的变量调用；
  producer只能选择F9冻结为可读的文本或属性；含Examples参数的consumer必须显式声明
  `parameters.argument`为参数名或`null`。合同不保存运行时原值，也不模拟真实控件读取结果。
- Intent中的每个operation必须声明`target_action_id`和`value_action_ids`。系统从这些
  选择派生`action_ids`、`evidence_ids`和冻结的`target_fingerprint`；AI提供不一致机械
  字段时拒绝提交。只有target Action可以授权locator；value Actions只证明值，不能借出
  目标。同一Action同时证明目标和值时可同时承担两个角色。
- Intent中的每个Step必须把Brief `annotation_snapshot.required_annotation_ids_by_step`原样
  写入`annotation_ids`；无Annotation时写空列表。AI不得提交`annotation_trace`或scope、
  revision、authority、fingerprint等proof字段。系统派生无自由文本的Plan trace，缺失、
  额外、stale、跨Step、跨Take或跨event ID均拒绝。
- Plan 与 Request revision seal及Annotation snapshot绑定；Take、timeline、Graph、
  Annotation或contract变化后失效。Transaction prepare冻结Annotation lease，finish重算并
  输出`annotation_lease_audit`。
- 失败事务的`inspect.revision_context`严格绑定Workflow的`last_result`、原Intent和Plan；
  事务报告还必须通过覆盖validations/errors的`result_fingerprint`。外部AI可读取可信失败
  检查后显式提交一次完整修订Intent，Recorder不会自动重试模型。
- 可选 `memory_trace.applied/dismissed` 只能引用冻结 Brief Digest，并由 Plan fingerprint 一起封存。
- 只有用户确认的 Plan 才发布 `plan_confirmed` 记忆和 Capability；机器 Plan 不冒充用户决定。

## AI 生成契约

生成约束不是只写在说明文档中。每个会话都会生成机器可读的 `ai/generation-contract.json`，它明确规定：

- 证据读取顺序和优先级。
- 录制动作到框架 API 的映射。
- Child、XPath、OCR、POS 的选择条件，以及 action/revision/template-hash 绑定的受控 PIC 授权。
- Step Definition、locator、Page Object 和 data 的输出职责。
- 哪些证据可判定为高置信，哪些必须人工复核。
- 生成后必须执行的 Python 编译、locator 编译和 Behave 检查。
- 当前允许生成代码调用的 `BasePage`/页面工厂真实签名，以及对应 API hash。
- `$name`、`$loc:name`、`$data:name`、`$$name` 的资源引用规则。
- Feature 只加载一个 scoped Step 文件以及 `@stepfile:`/文件名推导规则。

AI 生成入口顺序为：

```text
immutable RequestV3
-> ai/workflow/<request-id>.json
-> ai/generation-briefs/<request-id>.json
-> ai/decisions/<request-id>/decision-*.json
-> ai/decisions/<request-id>/answers-*.json（仅有问题时）
-> ai/generation-jobs/<request-id>/job-*.json
-> ai/plans/<request-id>/plan-*.json
-> 现有 Step / Page Object / locator / data / capability
-> required_forensic_evidence（仅按需）
-> GenerationTransaction 3.1
```

证据优先级为：当前Decision Answers与PlanV4.2 > effective action envelope > 录制事实 > deferred raw/media > 项目经验。契约要求AI复用现有资产，不允许凭视频猜业务值，也不允许把歧义Child/XPath当作已验证定位。控件结构类型本身不触发复核。

### 生成质量等级

`generation_quality_gate`只读核对Request、Plan、Transaction和正式内容寻址Run Result：

- `protocol_e2e_passed`：生成协议、文件、Code Manifest身份/绑定与事务验证通过；允许deterministic surrogate，不能据此评价AI理解质量。
- `ai_quality_passed`：在上一等级基础上，Plan来源为`external_ai`，且匹配Feature、Scenario/Outline、Examples和全部目标Step的真实运行均通过；高风险时还要求独立Oracle/Runtime Matrix通过。
- `failed`：冻结身份、事务或必需验证不闭合。Run Result被篡改时在指纹层拒绝，不读取其中状态。

字段语义保持分离：`single_run_passed`只表示绑定Run Result中的目标场景运行通过；
`oracle_passed`只表示独立业务Oracle/Runtime Matrix通过；`quality_passed`表示最终运行质量门通过。
Capability runtime verification只从Job Result的Runtime/Oracle阶段派生。

Run Result 1.3保存`generation_provenance`和失败Step的结构化Runtime Diagnostic。只有使用
`python -B -m Bdd.runner <feature> --generation-transaction-report <report>`
显式绑定已完成Transaction时，Reporter才会复核Request、Plan、完成报告、result
fingerprint以及全部生成根代码快照，并发布可用于当前验证的结果。Query和质量门要求
完整provenance精确一致；普通未绑定运行不能满足当前Job的`single_run_passed`、`quality_passed`或
`ai_quality_passed`。同秒发布的多个Run Result按`published_at`、`started_at`、`run_result_id`
和文件名稳定排序，避免把文件系统遍历顺序当作最新结果。

该来源字段用于审计和防止测试辅助Plan误报，不是远程模型的密码学身份证明。

### 一键模拟测评

`python -B -m framework_validation.evaluations.simulation_evaluation`
按UJ-01至UJ-07顺序执行真实Windows自动化边界，并在
`framework_validation/output/simulation-*`生成JSON、Markdown与逐项日志。入口在失败或
超时后继续其他旅途，且每个子进程只开启自己的环境门。它不运行模型、不提交surrogate
Plan，也不把自动边界通过写成`ai_quality_passed`；清单中的Request/Brief/Decision指针供
用户回答与Copilot external-AI接续。命令参数使用`--help`查看；具体产品来源、测试矩阵
和验收结论由宿主项目文档维护。

复杂组合入口为
`python -B -m framework_validation.evaluations.complex_evaluation`。该维护者工具位于生产包之外，只能
单向依赖Recorder。每组必须同时有
成功、对抗、失败关闭检查，以及Request、Brief、external-AI Plan、completed Transaction
和签名Run Result的source-backed指针；组能力从冻结artifact机械计算，不能由标签声明。
当前评测必须校验framework contract。只有同一次评测的live manifest绑定当前源码、
Bundle/raw integrity、selected Take/revision、Evidence Context、
Observation Receipt、external-AI Plan、Transaction和本次重跑Behave后才能报告
`validated`。通用矩阵不拥有Vela/Gantry设备链；该宿主产品门和L4仍保持blocked。每次运行结论位于
`framework_validation/output/complex-*`。

Live评测使用同一目录完成三个阶段。第一阶段运行机制检查并冻结当前源码、framework
contract和每条检查日志：

```powershell
python -B -m framework_validation.evaluations.complex_evaluation `
  --group G6 --output-dir framework_validation/output/<evaluation>
```

完成该组本次external-AI Plan、Transaction和Behave后，把三次真实命令输出保存到上述
目录，并用指向本次五个成功artifact的evidence JSON封存：

```powershell
python -B -m framework_validation.evaluations.complex_evaluation `
  --seal-live-group G6 `
  --output-dir framework_validation/output/<evaluation> `
  --success-evidence framework_validation/output/<evidence>.json `
  --plan-log external-ai-plan.log `
  --transaction-log transaction.log `
  --behave-log behave.log
```

最后只复核同次manifest，不重跑或拼接另一轮机制检查：

```powershell
python -B -m framework_validation.evaluations.complex_evaluation `
  --output-dir framework_validation/output/<evaluation> `
  --finalize-live-manifest g6-live-manifest.json
```

机制检查后任何执行源码、API签名、成功artifact、attempt日志、selected Take、Graph、Context、
Receipt或raw integrity变化都会使seal/finalize失败；必须从第一阶段重新运行。manifest是
内容寻址证明，不是新的工作流状态源，也不替代`ai/workflow/<request-id>.json`。

### 受控 PIC

PIC 只作为结构化定位失败后的 action-scoped fallback：

- 新录制必须保存 frame monitor geometry，并记录一个唯一可执行的 Child/XPath 父容器作为 Region。
- projection 从 before frame 裁剪模板，在至少两个独立 frame 的 Region 内验证恰好一个命中，并封存模板和 audit hash。
- Decision Pack 默认提供“不授权”；只有 audit passed 才提供“授权当前 Action”。
- `prepare` 重新校验 Request、Semantic Pack、audit、模板 hash、Action、Step、Region 和 Plan target，并把结果冻结在 `pic_authorization_audit`。
- AI 只能逐字节复制 `template_source` 到 `Bdd/data/<target_data_path>`，生成冻结的 PIC/Region locator，并通过普通 Plan action 使用该 locator。
- 授权Region必须引用PIC operation所属Window owner的唯一top-level Root；Root别名不一致的Plan在事务前失败关闭。
- `finish` 拒绝未授权 PIC、直接 PIC API、模板改写、Region/threshold 偏离和过期授权，并输出 `pic_usage_audit`。

正式 top-level Root 和元素必须写入 locator YAML。框架仍保留 `set_root()` 供旧手写调试代码使用，但 Recorder 的允许 API、Prompt 和增量 AST 策略都会阻止新增 `set_root()` 与 inline locator。

`ai/readiness.json` 给出两个独立结论：

- `bundle_valid`：协议版本、必需文件、媒体路径和 PIC 禁令都有效。
- `recording_complete`：至少有一个完成 Step，且范围内没有待录制 Step。
- `semantic_ready`：确定性校验器没有发现审阅信号；这只是 Reconciler 输入，不拥有运行状态。
- `capture_generation_candidate`：会话级采集候选摘要；真正能否生成只看 Workflow/admission。

`review_required` 会列出阻止自动生成的具体代码和证据，例如：

- `tree_not_comparable`
- `weak_step_semantics`
- `orphan_mouse_boundary`
- `external_process_action`
- `dynamic_root_variants`
- `fallback_ocr` / `fallback_pos`
- `weak_target_quality`

可以手动重新校验证据包：

```powershell
python -m autowork_core.utils.debug_tools.recorder.bundle_validator <会话目录>
```

`bundle_valid=false` 或 `recovery.hard_blocker=true` 会阻止 Workflow。其他 review 信号由 Reconciler 路由到 fast、needs_adjustment 或 forensic，不能由 UI/Prompt 自行放行。

### Recorder Generation Agent

用户显式选择`.github/agents/recorder-generation.agent.md`定义的Agent并提交Job路径；内部
Skill位于`.github/skills/recorder-generate/SKILL.md`，权威流程位于
`ai/prompts/recorder-generate.md`。它不会仅凭自然语言直接写代码：

```powershell
python -m autowork_core.utils.debug_tools.recorder.generation_workflow advance-job <job-path>
```

技术证据修复和admission在Workbench创建Job之前完成；需要用户权威或授权的 option Answers
在用户粘贴 `advance-job` 后、完整生成前一次性提交。claim后只允许 pre-generation option batch、
AI-authority typed patch、候选原生编辑和验证推进，不能合并答案草稿或让Agent发起自由业务问答。Job状态含义：

| 状态 | 行为 |
| --- | --- |
| `ready` / `phase=ready` | 仅为尚未提交给Agent的持久状态；Workbench提交前CAS claim |
| `running/design` | `advance-job`必要时返回 pre-generation option Answers 或 typed patch；AI-authority业务歧义在Job内选择，系统baseline优先，完整GenerationDesign产品入口已退役 |
| `running/implementation` | `advance-job`推进Transaction子租约，只修改Manifest允许文件 |
| `running/runtime` | 静态事务已完成，等待完整provenance绑定的Run Result |
| `running/oracle` | Risk Policy要求独立runtime matrix/Oracle，未完成前不报告成功 |
| `completed` / `failed` | 只读取内容寻址Job Result；再次生成只能来自用户重新触发Workbench主操作 |

成功静态终态仍会从Transaction冻结基线生成内容寻址`implementation-<sha256>.diff`用于审计。
用户可见代码交付是绑定宿主原生编辑产生的修改文件与diff审阅；不得把完整源码或unified diff
粘贴进对话冒充该体验。`job-code-diff`只用于审计、重建和排障。

内部prepare阶段冻结Job/Request revision、Brief、Plan和policy baseline；finish阶段只结束静态
Transaction阶段，再由Job coordinator根据Execution Profile和Risk Policy决定终态。报告写入：

```text
<run>/ai/generation-transactions/transaction-*/report.json
```

报告强制检查：

- 只能修改 `Bdd/steps/**`、`Bdd/page_obj/**`、`Bdd/locators/**`、`Bdd/data/**`。
- 修改 Python 必须通过编译。
- 修改 locator YAML 必须通过结构解析和 `compile_locators`。
- 修改 Step Definition 必须通过目标 Feature scope 的重复/未定义检查。
- 完成时重新计算 revision seal；生成过程中证据或框架契约变化会记为 `stale_during_generation`。
- 经验 freshness 只决定事务前是否需要新 Request，不加入证据 lease seal；`running` transaction 不因 journal 或外部 evidence 追加/漂移而丢失冻结 Request，但 `finish` 仍重算 lease revision，且完整 Request fingerprint 始终拒绝文件自身篡改。
- 每个 decision claim 引用的 Evidence ID 必须存在，且 claims 合计覆盖最小决策证据；结果写入 `evidence_audit`。
- 每个 operation 和 ignored action 都必须解析为 Evidence claim，最小决策覆盖率必须为 100%。
- 生成前保存 Bdd Python 策略基线；拒绝新增的未绑定 placeholder stub、固定 `sleep`、直接 pywinauto、`set_root()` 和 inline locator，不误伤基线中已有的手写调试代码；精确 Action 的 `unresolved_generation_issue` 由 Plan-to-Code 单独验证；结果写入 `generation_policy_audit`。
- 只有 `completed` 或 `completed_no_changes` 可以作为完成结论。

生成报告还保存 AI 的 `decision_trace`：从冻结 Plan 派生的采用/拒绝记忆、实现理由和未解决的不确定点。成功生成会自动追加结果项目经验；`insights` 当前保持为空，不自动持久化 AI 自报洞察。

实际启动目标应用的 Behave 执行不是默认自动步骤；只有用户明确允许时才执行，避免生成
阶段意外操作业务环境。运行完成后的 Spark 失败证据会通过只读 run-result 索引回到审阅
页，但不会自动触发改码或重跑。

## 视频和截图联动

`media-index.json` 把同一个 Take 内的证据统一到毫秒时间轴：

- `events[].event_ms`：输入事件相对输入采集开始的时间。
- `events[].video_ms`：该事件在 `step.mp4` 中的估算毫秒位置。
- `events[].screenshot`：该事件对应的关键帧截图。
- `events[].screenshot_video_ms`：关键帧实际抓取时刻对应的视频位置。
- `events[].evidence_latency_ms`：事件发生到控件检查和截图完成的延迟。
- `contact_sheet.frames[]`：联系表每个格子对应的原始截图和事件 ID。
- `actions[]`：动作级 `before`、`commit`、`after`、`context`、稳定性和结果索引。
- `action_contact_sheet`：每个动作一行、操作前后两列的联系表索引。

`action-media.json` 是分析单个动作的首要静态媒体入口。每个动作包含：

| 字段 | 含义 |
| --- | --- |
| `before` | 当前动作提交前的界面；鼠标为按下前，键盘为序列首键前 |
| `commit` | 动作语义提交边界及其 `event_ms`/`video_ms`；鼠标为抬起，键盘为序列末键抬起 |
| `after_immediate` | 提交后最早候选帧，用于观察即时响应 |
| `after` | settled、probe、immediate 中可用的最晚优先结果帧 |
| `context` | 下一动作开始前的界面；没有下一动作时等于 `after` |
| `stability` | probe 与 settled 的视觉差异；`visual_stable` 表示平均像素变化比不超过 `0.012` |
| `outcome` | 是否检测到窗口关闭、关闭动作候选或普通可视状态 |

`before`/`after` 都带 `stage`、`source`、`captured_ms`、`event_ms`、`latency_ms` 和可用时的 `video_ms`。`action-contact-sheet.png` 把每个动作的 before/after 成对展示，不能与事件级 `contact-sheet.png` 混用。

视频同步使用同一进程的单调时钟，属于毫秒级估算，不声明帧级精确。Step 前截图发生在视频和输入采集启动前，Step 后截图发生在二者停止后，这一关系也会写入媒体索引。

AI 应优先读取 JSON/YAML 和 PNG。只有静态证据不足以判断动画、拖动过程或中间状态时，才按媒体索引从 MP4 提取目标帧：

```powershell
python -m autowork_core.utils.debug_tools.recorder.media <take目录> --event event-00001
```

也可以直接指定视频毫秒位置：

```powershell
python -m autowork_core.utils.debug_tools.recorder.media <take目录> --video-ms 1250
```

因此后续 AI 不需要具备直接播放 MP4 的能力：它先读 `action-media.json` 和 `action-contact-sheet.png` 判断操作前后，再读事件证据；只有静态图不足时才使用内置 ffmpeg 按 `video_ms` 抽帧。完整视频仍保留给人工复核和需要连续动作上下文的情况。

## F9 观察目标回执

F9 使用异步两阶段反馈，避免按键时 UIA 尚未完成就误报成功：

1. 桌面非激活 overlay 立即显示“F9 正在采集目标”。
2. UIA 富化完成后显示目标名、control type、最近 Window/Pane 范围和 locator validation。
3. 唯一 Child/XPath 为绿色；OCR/POS、未验证或范围过宽为黄色；失败为红色。
4. 成功或warning回执先保存本event的system-inferred Intent并显示白话摘要，不弹出编辑器、
  不阻塞继续录制。集合、属性和Region文字等内部typed focus由Provider根据冻结目标自动
  派生，不作为普通用户的技术选项。
5. Recorder状态栏保留最近一次F9摘要，内部Timeline和审阅投影仍保存完整observe证据。

审阅页按当前录制显示有效主录制与Supplement F9。用户可把系统摘要修订为自动核对、
显示文字、当前值、是否可见、是否可用或窗口标题，并选择关系及Feature/Examples/
Data Table来源；也可定位到录制内容并忽略该检查。修订append-only写回原Session或Supplement
annotation scope，旧Request/Plan保持不变但Workflow转为stale。文字和值禁止把当前观察
内容直接当作业务期望；collection/property/visible/enabled等observed-state候选只有在
用户明确确认后才能成为业务断言。

overlay 延续 `WS_EX_NOACTIVATE`，不会抢走被测应用焦点；提示结束后自动恢复此前的“正在录制”或“已暂停”状态。

普通F9统一使用“观察此处”，Inspector通过Observation Provider注册表自动路由；目标满足
结构化集合能力时由`uia_collection`读取直接子项，最多200项。它与其他F9观察使用同一
目标和事件边界，不要求用户识别控件或Provider类型。结果写入
`observations/observation-*.json` 内容寻址 receipt；canonical observation 只保存
provider、相对路径、大小和 SHA-256。Semantic Pack 6.3校验receipt后把item names/
values的有界摘要交给Scenario Intelligence，并只根据typed
`ObservationIntent`选择候选；窗口标题必须显式选择`window_title`及关系，并引用
Feature/Examples/Data Table来源。Take的note不参与候选。完整、未截断、内容寻址且具有唯一locator的集合receipt可
形成有序`assert_collection_equal`候选。`get_collection_items`只读取结构化集合的直接子项、
排除ScrollBar chrome并限制最多200项；断言按顺序精确比较。receipt篡改、截断、目标不唯一
或超限均失败关闭；不要用它递归采集整个窗口树，也不能替代DICOM、日志或图像语义Provider。

普通F9不暴露Canvas/OCR技术菜单。Inspector通过统一Observation Provider注册表按目标能力
自动选择采集方式；Canvas-like目标使用`canvas_ocr`，在同一次冻结capture context内保存
Root、Window owner、Region、OCR items、置信度和内容寻址Receipt，内部Intent使用
`region_text`，普通UI只显示业务选项“显示文字”。OCR当前识别值只是运行时事实；期望值只能
来自Feature、Examples或Data Table。
只有完整、未截断、置信度达标且与当前Action/target/owner/Region一致的Receipt才能形成
`assert_ocr_contains`或`assert_ocr_not_contains`候选。空OCR、低置信、Receipt/hash篡改、
Root/Window/Region重绑或target drift都路由`evidence_required`且没有Decision放行结果。
Plan必须逐字段绑定冻结Brief候选；生成代码只能调用既有OCR断言并传入声明式Region locator。

新Step业务补充与F9 Intent写入、Timeline mutation和Generation Transaction prepare共享
Run写锁。主录制`finalize`完成最终投影后立即释放长期锁；prepare只在冻结annotation lease、
写running report和切换Workflow的短临界区持锁，不覆盖后续Copilot改码阶段。这样避免
检查running状态后并发修改annotation的TOCTOU窗口。

## AI 可分析程度

以下证据可以确定读取和分析：

- Feature、Examples、Step Data Table 和多行文本。
- JSON/JSONL/YAML 中的事件、动作、控件属性、locator 验证和树差异。
- Step 边界 PNG、动作 before/after、动作联系表和事件证据。
- 通过 `media-index.json` 定位并从 MP4 提取的单帧。

以下内容不能保证全自动正确：

- 仅凭视觉变化推断业务意图或期望值。
- 自绘控件内部没有 UIA/OCR 证据的语义。
- 中文输入法组合过程、混合方向/零增量滚轮和缺少完整起止证据的拖拽。
- 多个候选都合理时决定业务上应选哪一个。

这些情况会保留原始证据并标记为需要复核。录制器提供的是可追溯生成协议，不是对任意桌面行为 100% 无人工确认的承诺。

## 当前边界

- Workflow 5.0只允许在活动Job的`running(implementation)` Transaction和冻结PlanV4.2范围内修改Step、Page Object、locator和data，并由`advance-job`统一审计。
- 自绘控件、远程桌面和提升权限窗口可能只有容器或坐标证据；Canvas只有在完整Region OCR
  Receipt闭合时才能生成区域文字断言，否则同样失败关闭。
- 同方向、非零滚轮事件会冻结为`scroll`的`direction`和`steps`；Plan必须与目标Action完全
  一致，runtime只接受`up/down`和非布尔正整数。混合方向、零增量或缺失参数失败关闭。
- Recorder把虚拟叶项上的滚动目标提升到最近的稳定Scroll容器，避免重放绑定离屏ListItem。
- 中文输入法等组合输入保留底层按键事件，最终文本应结合控件前后 Value 和截图判断。
- 控件树是 Step 开始/结束快照；每个输入事件保存目标控件、祖先链和局部上下文，不对每次按键重复保存整棵树。
- Take使用Evidence Graph 2.6；原始artifacts不覆盖。
- 多 Take 共识和生成后自动回放比较尚未在本阶段实现；当前可保留多个 Take，但普通UI
  只使用最新完成结果对应的selected Take。历史Take切换仅作为维护诊断/回退能力保留。

会话使用上下文和进程退出兜底关闭 Hook/ffmpeg；调试器异常关闭时，正在录制的 Take 会按丢弃处理并恢复 Step 原状态。
