# 4. Spark 报告设计

目标：做一个类似 ExtentReports Spark 的本地 HTML 报告，但结构和内容完全适配当前 BDD 桌面自动化框架。

## 定位

这个报告不替代 Behave，也不替代底层日志。它是面向测试、开发和业务查看的一页式执行报告。

## 当前实现状态

当前 Spark 报告由 `settings.spark_report` / `SPARK_REPORT` 控制，默认启用。运行结束后输出：

```text
artifacts/reports/autowork-report.html
artifacts/reports/autowork-report.json
```

最终交付报告可由多次执行结果手动合并生成，输出到不会被普通运行清理的目录：

```text
artifacts/final-reports/autowork-final-report.html
artifacts/final-reports/autowork-final-report.json
artifacts/final-reports/autowork-final-merge.json
artifacts/final-reports/assets/
```

`autowork-final-report.html` 仍按普通 Spark 报告展示最终有效结果，不显示复跑、flaky 或
尝试次数字段；`autowork-final-merge.json` 只作为内部操作日志，记录 create / merge /
delete 的来源和范围。合并时会把截图、录屏等附件快照到 `assets/`，避免下一轮普通运行
清理 `artifacts/screenshots/` 或 `artifacts/recordings/` 后最终报告断链。

推荐操作流程：先用一次全量运行创建最终报告底稿，之后对失败 Feature 或 Scenario 单独复跑，
再把复跑产生的 `artifacts/reports/autowork-report.json` 合并进最终报告。宿主项目可直接右键
运行 `Bdd/final_report.py`；该入口只保留 `ACTION` 和对应动作配置块：

```python
ACTION = "create"  # create / merge / delete / render

CREATE = {
  "report_json": "artifacts/reports/autowork-report.json",
}

MERGE = {
  "report_json": "artifacts/reports/autowork-report.json",
  "allow_add": False,
  # 报告里目标不唯一时再填写：
  # "feature_file": "Bdd/test_features/login.feature",
  # "scenario_name": "登录成功",
  # "example_id": "1.1",
}

DELETE = {
  # 默认从 artifacts/final-reports/autowork-final-report.json 删除。
  # 删除整个 Feature 时填 feature_file 或 feature_name。
  # 删除单个 Scenario/Example 时再填 scenario_name / example_id。
  # "feature_file": "Bdd/test_features/login.feature",
  # "scenario_name": "误合并的场景",
}

RENDER = {
  # 默认渲染 artifacts/final-reports/autowork-final-report.json。
}
```

传命令行参数时仍可使用核心入口，例如
`python -m Bdd.final_report merge artifacts/reports/autowork-report.json --feature-file Bdd/test_features/login.feature --scenario "登录成功"`。

合并规则使用 `feature.file` 优先、`feature.name` 兜底定位 Feature；普通 Scenario 使用名称定位；
Scenario Outline Example 使用 Outline 名称加 `exampleId` 定位。合并只替换最终报告中的可见执行结果，
不会在最终 HTML 中增加“复跑后通过”等字段；误操作可用 delete 删除 Feature、Scenario 或单个
Example 后重新 render。

已实现行为：

- 默认打开 Feature 分组执行表。固定表头为“状态 / 编号或类型 / 名称 / 执行结果 / 耗时 /
  失败 Step / 详情”，Feature 父行和 Scenario/Outline Example 子行使用同一组列。
- 所有 Feature 默认收起；所有真实 Scenario/Example 始终显示名称，名称最多显示两行并可
  悬停查看全文。Feature 内始终保持 Gherkin 规格顺序，不因场景数量、筛选或排序切换结构。
- 执行表支持状态筛选、Feature/Case 搜索、原始顺序、异常优先和耗时优先。排序只调整
  Feature 组，不改变组内 Case 顺序或身份。点击子行直接进入对应详情，返回时恢复筛选、
  排序、折叠状态、选中项和滚动位置。
- 测试详情使用两列工作区：Scenario/Example 导航与 Step/证据主体。Feature 通过顶部
  下拉切换，不再占用常驻列；窄屏默认收起 Scenario 抽屉，直接展示 Step 与失败证据。
- 按 `Feature -> Scenario / Scenario Outline -> Example -> Step` 收集执行数据。
- `before_step` 记录 Gherkin step 起始信息，`after_step` 回填状态、耗时、错误摘要、完整错误详情和附件。
- 失败步骤挂载普通失败截图；截图保存失败不会中断报告，会追加到该步骤 `errorDetail`。
- OCR/PIC 失败期间新生成的 debug image 会挂到失败步骤附件。
- 失败场景会挂载 ffmpeg mp4；`failed` 模式挂最近 `BUFFER_SECONDS` 秒，`all` 模式挂完整场景录屏。
- `before_scenario` 开始场景计时；`after_scenario` 在录屏和应用清理完成后记录可读耗时，
  并补齐因前置失败未执行的 Background/Scenario 步骤，统一按原始顺序排序。
- Scenario Outline 会在 `after_feature` 聚合为父级 outline 和多个 example。

当前未采集每个 Gherkin step 内部的 action 明细，也不在 HTML 中内嵌日志片段；需要排查底层动作时仍以 `artifacts/logs/logs.logs` 为准。Step 数按每个测试场景的
`Background + Scenario Steps` 统计，使用 Behave `all_steps` 去重，避免 Background 重复。

## 设计原则

1. 定位优先：首页用分组执行表回答异常集中在哪个 Feature、哪个 Case 和哪一段规格范围。
2. BDD 层级清楚：Feature -> Scenario -> Step。
3. 桌面自动化友好：展示 locator、root、OCR/PIC debug 图、截图、录屏、日志片段。
4. 单文件优先：第一版生成一个可独立打开的 HTML 文件，资源用相对路径链接。
5. 不深依赖第三方前端框架：减少维护成本。

## 页面结构

### Feature 分组执行表

```text
Feature 分组执行表
状态  编号或类型  名称             执行结果  耗时   失败 Step  详情
●     F01         Feature A        8/9 89%   02:31  1 个       ›
  ●   S01         登录成功          通过      00:12  —          ›
  ●   E1.2        无效口令被拒绝     需跟进    00:08  1 个       ›
```

显示：

- 项目名、执行时间和总耗时。
- 已执行场景只包含通过、失败和未知 Scenario / Outline Example；Scenario Outline 父项不重复计数。
- 场景通过率为 `passed / (passed + failed + unknown)`，只回答已执行场景中有多少通过。
- Feature 级跳过和 Scenario/Example 级跳过分开计数。Feature 跳过只记一个 Feature，
  但“未执行场景”会按该 Feature 实际包含的 Scenario/Examples 数量统计；详情显示场景数、
  Step 数和原因。
- 不展示“执行完整度”：当前运行数据没有区分永久不在自动化范围和本次临时跳过，计算
  完整度会产生无法可靠解释的比例。
- Feature 父行聚合显示 `通过数/已执行数`、已执行口径通过率、总耗时和失败 Step 数；
  状态环展示 passed、failed、unknown 和 skipped 的真实构成。纯未执行 Feature 的执行
  结果显示 `—`，不产生 `0%` 通过率。
- 子行只编码一个状态：“符合预期”对应 passed；“需跟进”对应 failed；“状态未知”对应
  unknown；“未执行”对应 Scenario/Example skipped。Scenario 使用 `S01` 顺序编号，
  Outline Example 使用稳定 Example 标识。
- 整项 Feature 跳过只显示一个真实子行，名称明确给出计划场景数和跳过原因；父行聚合仍按
  `plannedUnits` 计算未执行覆盖量，不伪造多个 Scenario 名称。
- 表头固定，展开和收起只在父行后插入或移除真实子行，不改变表头与父行几何。少量和大量
  场景使用同一结构；数据增多时在执行表内部滚动，窄屏在容器内横向滚动，不压缩列语义。
- 搜索与状态筛选取交集。命中 Feature 名时保留该 Feature 的全部子行；只命中 Case 时只
  显示命中的子行。筛选期间临时展开命中组，清除条件后恢复原折叠状态；底部显示当前
  Feature 数和测试场景覆盖数。

### 总体信息行

```text
Feature: 4  测试场景: 24  已执行: 20  符合预期: 17  需跟进: 2  状态未知: 1  未执行: 4  通过率: 85%  总耗时: 00:12:30
```

“未执行”使用场景数量：单独跳过的 Scenario/Example 数，加上整 Feature 跳过时该
Feature 包含的 Scenario/Example 数。

### 报告导航

左侧只保留稳定的一级视图导航，不放可能无限增长的 Feature 集合：

```text
报告
- 执行场景
- 测试详情
```

### 测试详情

测试详情承接分组执行表中已完成的 Feature/Case 定位，使用两列结构：

```text
← 返回执行场景    [Feature 选择器] [搜索 / 状态筛选]
Scenario / Example 导航            Step 与证据
Scenario 1                          场景摘要 / 失败摘要
Outline 2                           截图 / 录屏 / 调试附件
  Example @1.1                     Given / When / Then 时间线
```

- 顶部 Feature 选择器显示 Feature 名和独立的“需跟进/状态未知”数量；状态筛选会先排除
  不含目标状态的 Feature，再过滤所选 Feature 下的 Scenario/Example。
- Feature 级跳过在详情中显示为单一 Feature 条目，并展示包含场景数、计划 Step 和原因；
  不伪装成多个跳过 Scenario。
- Scenario/Example 与 Step/证据各自在固定视口内独立滚动；桌面端页面不因数据增多产生
  全局滚动。窄屏使用正常页面纵向滚动，Scenario 列由抽屉按需展开。
- Scenario/Example 搜索覆盖名称、Feature、文件、tag、Step 文本和已有 action 信息。
- 状态筛选位于详情顶部；Scenario/Example 搜索与状态筛选取交集。切换状态时自动选择
  第一个包含该状态的 Feature。
- Scenario Outline 默认收起；从分组执行表点击具体 Example 时自动展开父 Outline 并选中该行。

Scenario 导航行字段：

- Feature 名
- Scenario 名
- 类型：Scenario / Scenario Outline / Example
- 状态
- 耗时
- tags
- 错误摘要
- 失败错误摘要

Scenario Outline 建议展示为父子结构：

```text
▶ Scenario Outline 配置绝对延迟重建相位        failed
  Example @1.1 phase=20 mode=Absolute   passed
  Example @1.2 phase=30 mode=Absolute   failed
```

Scenario Outline 父项支持展开/收起，默认收起；搜索时可直接命中 Example。点击右侧 Scenario Outline 汇总中的 Example 行，也会跳转到对应 Example 的 Step 时间线。

失败的 Scenario / Example 导航行直接显示错误摘要。Step/证据主体先展示失败摘要和场景
附件，再展示 Step 时间线；错误信息分两层：默认显示摘要，点击后展开完整 traceback 和上下文。

### Step 详情

右侧明确展示 Gherkin Step 时间线。Scenario 信息只放在顶部摘要；附件使用无嵌套证据区，
不再放进第二层 Panel。

注意：右侧编号 `1/2/3` 表示 feature 文件里的 Given/When/Then 步骤，不是框架内部的 click/input/assert 动作。通过 Step 默认不展开动作明细；失败 Step 只展示失败的动作，例如：

```text
1  When 选择重建模式并输入延迟       passed
   通过时不展开动作明细

2  Then Phase 展示为 20ms            passed
   通过时不展开动作明细

3  Then Phase 展示为 30ms            failed
   assert_ocr_contains phase_result value=30ms   failed
```

桌面端右侧区域固定高度滚动，不因为步骤或附件过多把整页撑长。窄屏默认直接进入右侧
Step/证据，Scenario 抽屉收起；展开时列表最大高度 360px。

点击普通 Scenario 或具体 Example 后展示：

- Step 时间线
- Step 关键字：Given / When / Then / And / But
- Step 内部动作明细：通过时不展示；失败时只展示失败的 click / input_text / assert / wait 等动作
- 失败堆栈
- locator/root 信息
- OCR/PIC debug 图
- 日志片段
- 附件列表

点击 Scenario Outline 父项时展示：

- Examples 汇总
- 原始 Examples 表格：保留 feature 中的参数列，并追加状态列
- 每行状态
- Examples 表格行可点击，点击后跳转到对应 Example 的 Step 时间线
- 也可以展开中间 Scenario Outline 后，点击具体 Example 查看对应 Step 时间线

## 和框架的接入点

当前采用单一 `SparkReporter`，不写 Behave formatter，也不把数据聚合和 HTML 渲染逻辑塞进 `environment.py`。

```text
autowork_core/runtime/reporting/
  __init__.py       # 暴露 SparkReporter 和无状态 Hook 分发函数
  spark.py          # 收集数据并渲染 autowork-report.json/html
  templates/
    spark_report.html  # 正式运行时模板
```

`create_run_state()` 根据配置创建本次运行唯一的 Reporter，`environment.py` 通过报告包的无状态函数转发生命周期事件：

```python
@dataclass
class AutoworkRunState:
  # 省略其他 run-scoped 字段
  reporter: SparkReporter | None

def create_run_state():
  return AutoworkRunState(
    reporter=SparkReporter() if settings.spark_report else None,
  )

def before_all(context):
  configure_logging()
  context.autowork_run = create_run_state()
  dispatch_report_hook(context.autowork_run.reporter, "before_all", context)

dispatch_report_hook(context.autowork_run.reporter, "before_feature", context, feature)
dispatch_report_hook(context.autowork_run.reporter, "before_scenario", context, scenario)
dispatch_report_hook(context.autowork_run.reporter, "before_step", context, step)
dispatch_report_hook(
  context.autowork_run.reporter,
  "after_step",
  context,
  step,
  screenshot_path=screenshot_path,
  screenshot_error=screenshot_error,
)
dispatch_report_hook(
  context.autowork_run.reporter,
  "after_scenario",
  context,
  scenario,
  record_path=record_path,
)
dispatch_report_hook(context.autowork_run.reporter, "after_all", context)
```

`before_all` 创建 `AutoworkRunState`，其中的 `reporter`、recorder 和公共 data 模板使用同一 Test Run 生命周期；每个 Feature 会从公共 data 模板 fork 自己的 data 层，locator 由页面显式加载。`dispatch_report_hook()` 接收当前 Reporter：关闭报告时实例为 `None`，否则调用对应 Hook 并隔离报告异常。它没有全局注册表或对象状态，不是 HookManager。目录模式使用一个 Behave Runner：所有 `before_feature` 持续向同一 Reporter 追加数据，`after_all` 统一输出一次报告。当前不提供多 Reporter 插件注册能力。

`SparkReporter` 职责：

- `before_all` 初始化 report store
- `before_feature` 记录 feature
- `before_scenario` 记录 scenario 起始时间
- `before_step` 记录 Gherkin step 起始时间
- `after_step` 记录 step 状态、错误、失败截图附件和截图保存失败原因
- `after_scenario` 记录录屏附件、场景状态和耗时，补齐 missing steps，并按 Background + Scenario 顺序排序
- `after_feature` 聚合 Scenario Outline examples，并计算 feature 状态
- `after_all` 输出 `autowork-report.json` 和 `autowork-report.html`

## 附件策略

推荐：

```text
失败步骤：截图
失败场景：录屏
OCR/PIC 失败：自动挂载 step 执行期间新生成的 debug image
所有失败：logs.logs 链接
```

成功步骤默认不放截图，避免报告膨胀。

截图和录屏文件名会自动缩短并追加 hash，避免 Windows 路径过长导致失败。录屏由项目内置 ffmpeg 执行，产物写入 `artifacts/recordings/`；`failed` 模式通过分片滚动缓存保留失败前最近 `BUFFER_SECONDS` 秒，失败时合并成 mp4 并挂到报告，`all` 模式保留完整场景 mp4。即使截图保存失败，报告也会继续生成，并在失败步骤详情里展示截图错误。

## 为什么不直接用 ExtentReports

ExtentReports 的 Spark UI 很好看，但 Python + Behave 没有足够成熟的官方适配。仿它的布局自己生成 HTML，反而更适合当前框架。

## 当前落地范围

1. 生成 `artifacts/reports/autowork-report.html`。
2. 同时生成 `artifacts/reports/autowork-report.json` 方便调试和后续扩展。
3. 展示 summary、features、scenarios、steps。
4. 支持失败截图和失败录屏链接。
5. 支持简单搜索和状态过滤。
6. 支持 Scenario Outline examples 聚合。
7. 支持失败时补齐 skipped steps，并保持 Background + Scenario 步骤顺序。

后续可扩展：

1. locator/root 信息折叠展示。
2. Step 内 action 明细采集。
3. 日志片段自动关联失败步骤。
4. 历史趋势。
5. 和 Allure 报告互链。
