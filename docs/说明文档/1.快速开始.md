## 环境

本节用于首次准备或明确调整依赖，推荐 Python 3.11。需要安装的包以当前项目的
`requirements.txt` 为准；产品设备和供应商 SDK 不因框架依赖安装成功就已就绪。

以下安装命令用于首次准备或明确需要调整依赖的环境。已有可用环境先复用其解释器；
日常运行和查阅文档不要求重新安装依赖，也不要求连接 WeKnora。

安装基础依赖：

```powershell
python -m pip install -r requirements.txt
```

顶层`requirements.txt`统一声明框架及随仓库交付集成所需的Python包。产品设备、
供应商SDK和宿主专属二进制资产仍应在宿主项目文档中声明。

OCR 依赖当前验证组合：

```powershell
python -m pip install --pre paddlepaddle==3.0.0.dev20250426 -i https://www.paddlepaddle.org.cn/packages/nightly/cpu/
python -m pip install paddleocr==3.6.0
python -m pip install opencv-contrib-python==4.6.0.66 PyYAML==6.0.2
python -m pip check
```

注意：`paddleocr==3.6.0` 会拉取 `paddlex==3.6.1`。PaddleOCR 可能升级 OpenCV，但本项目同时依赖 `airtest==1.4.3`，它要求 `opencv-contrib-python<=4.6.0.66`，所以安装 PaddleOCR 后需要把 OpenCV 恢复到 `4.6.0.66`。

完成后检查 `pip check` 的实际输出；有冲突时先按依赖证据处理，不继续把环境视为可用。
该检查只验证包依赖，不启动产品，也不证明 OCR 模型和被测窗口已可正常使用。

## 同步框架到项目仓库

本节由项目维护者在同步框架资产时使用，不是每次运行用例前的准备步骤。输入是明确的
框架发布源与目标宿主仓库；先保留宿主自己的业务代码、配置和运行证据。

框架仓库和产品项目使用独立Git仓库。项目维护者拉取框架仓库后，完整替换项目仓库中的
以下框架资产：

```text
autowork_core/
config/
ai/
docs/
.github/
resources/
requirements.txt
behave.ini
README.md
.gitattributes
.gitignore
```

完整替换前，项目仓库不应修改这些框架资产。始终保留`Bdd/`和`artifacts/`；其中
`Bdd/config.yaml`保存项目运行与知识库配置，均不得被框架
替换。顶层`config/`只包含框架Python代码。`framework_validation/`只属于
框架开发仓库，不复制到宿主项目。同步后检查Git diff并运行轻量检查：

```powershell
python -B -m autowork_core.utils.debug_tools.framework_smoke --project-root .
```

该命令只检查文件、配置、关键导入和Runner，不启动应用、OCR、ffmpeg或Recorder全量
测试。只有本次同时修改了宿主拥有的`Bdd/`，才运行对应项目测试。该流程不使用跨仓库
`git merge`，也不依赖额外同步脚本。

## 运行入口

建议从项目根目录使用模块方式运行，避免脚本路径导致 `config`、`autowork_core` 等顶层包导入失败。

执行前确认 Feature 和其 Step、Page、资源文件已存在，当前解释器及宿主应用配置可用。
普通 UI 场景会按配置执行应用生命周期；不要在未知的产品或设备状态下盲目复跑。

### 正式用例：Bdd.runner

用于实际执行正式 Feature，前提是 `Bdd/features` 和宿主配置已准备好。结果进入本次
日志与普通 Spark 报告；该入口不处理本地单步标签，也不从历史报告续接现场。

```powershell
python -m Bdd.runner
```

正式入口默认读取 `Bdd/features`。当前仓库示例用例放在 `Bdd/test_features`；如果还没有创建正式用例目录，请先使用本地调试入口运行示例 feature。

### 本地用例：Bdd.local_runner

用于实际执行本地调试 Feature；可显式传路径，避免误用脚本内默认选择。仍会产生普通
运行报告，并按配置准备应用和清理普通产物，不是无副作用的静态预览。

```powershell
python -m Bdd.local_runner
```

指定要调试的 feature：

```powershell
python -m Bdd.local_runner Bdd/test_features/test_debug.feature
```

正式入口和本地入口都会实际执行选中的测试，不是静态检查。执行后查看控制台失败步骤
及 `artifacts/reports/autowork-report.json/html`；报告通过表示所执行断言通过，不自动
证明未覆盖的产品行为。

### IDE 运行和调试

`.vscode/`、`.idea/`、`.copilot/` 均由 `.gitignore` 忽略、不随框架仓库提交。

- **推荐方式**：在 PyCharm 或任意终端中从项目根目录使用模块入口运行（`python -m Bdd.runner` / `python -m Bdd.local_runner`）。
- **如需在 VS Code 中右键运行/调试深层 `.py` 文件**：将 `bdd_autowork` 作为独立工作区文件夹加入，并在本地 `.vscode/settings.json` 与 `.vscode/launch.json` 中自行配置 `cwd` 与 `PYTHONPATH` 指向 `${workspaceFolder}`（之后执行一次 `Developer: Reload Window` 并重启终端）。

只定义类或函数的文件运行后没有输出属于正常现象；要调试其中逻辑，需要测试或入口实际调用它。

### 直接使用 Behave

需要自行选择 Feature 路径、标签和 formatter 时，也可以从项目根使用 Behave：

```powershell
python -m behave Bdd/features --no-capture --no-capture-stderr --no-logcapture --verbose
```

## 本地调试入口

本节只适用于 `Bdd.local_runner`。输入是实际 Feature 路径和可选的场景/Example 选择，
输出仍是普通运行报告；局部执行不能替代完整场景回归。

命令行传入的 Feature 路径优先于本地默认值：

```powershell
python -m Bdd.local_runner Bdd/test_features/test_debug.feature
```

需要固定应用路径、backend、日志或录屏模式时，使用本地 runner 的
`settings_overrides`；字段和示例见
[4.定位器与配置：settings_overrides](4.定位器与配置.md#settings_overrides)。

### 完整复跑 Scenario / Example

前提是目标场景能在当前环境重新执行；复跑不是从旧报告中的失败位置续接。包含有副作用
动作时，先确认当前对象、数据和重复执行是否允许。

本地 runner 支持只复跑一个完整 Scenario 或 Scenario Outline 的 Example，复跑后仍生成普通
Spark 报告 `artifacts/reports/autowork-report.json/html`，可继续用最终报告合并入口合并。

在 `Bdd/local_runner.py` 中填写：

```python
scenario_name = "计算相加"
example_id = None
```

普通 Scenario 只会执行该 Scenario。Scenario Outline 不填写 `example_id` 时执行该 Outline
下全部 Examples；填写 `example_id` 时只执行对应行：

```python
scenario_name = "计算 <a> 加 <b>"
example_id = "1.1"
```

完整复跑会保留 Background 和目标 Scenario 的全部 Step。生成的临时 Feature 在正常结束后自动删除；
调试进程被强制停止时，下一次通过本地 runner 启动会先清理这类遗留文件。报告中的 Feature
路径仍映射回原始 `.feature` 文件，便于最终报告按原路径合并。

### 可选的报告 Skill

原有 [最终报告脚本](../../Bdd/final_report.py) 和函数继续独立使用。也可以通过
[Report Merge Skill](../../.github/skills/report-merge/SKILL.md) 表达本次动作：

```text
/report-merge 用本次运行报告生成最终报告
/report-merge 把本次新报告合到最终报告
/report-merge 用我指定的运行报告创建最终报告，保存到我指定的位置
/report-merge 只预览本次合并，不修改文件
/report-merge 分析这份报告的失败原因，不进行合并
/report-merge 从最终报告中删除指定 Feature 或场景的结果
/report-merge 删除指定 Outline 中 Example 1.2 的结果
/report-merge HTML 丢了，用最终 JSON 重新生成 HTML
```

指令中的指定路径优先，未指定则复用项目脚本已有默认路径，不修改项目配置。
Skill 的日常合并逐结果回填，默认保留未复跑场景和 Example；明确要求整组替换时才
整体替换。核心为此提供可选的 `preserve_unmentioned=True` 和 CLI 的
`--preserve-unmentioned`，原有函数及手动入口的默认语义不变。

删除只作用于报告内明确指定的结果，自动更新 HTML 和操作日志，不清理原始报告、
截图、录屏或 assets。只重建 HTML 时不需要本次运行报告，不修改最终 JSON、
日志或附件；范围不清楚时先询问，不把“删掉报告”理解成删除整个文件。

### 单步调试

用途是缩小执行范围，不是自动恢复先前场景状态。输入为目标 Scenario 上唯一的
`@single:` 标签；省略的前置操作必须由当前环境或所选模式满足。

本地 runner 支持通过一个 Scenario 标签选择目标 Step。普通 Scenario 使用：

```gherkin
@single:background:3
Scenario: Verify scan
```

Scenario Outline 还需要选择第几个 `Examples` 及其中第几条数据行：

```gherkin
@single:previous:2:example=1.2
Scenario Outline: Verify scan with <phase>
```

标签格式为 `@single:<mode>:<step-index>[:example=<examples-index>.<row-index>]`。
序号从 `1` 开始。模式含义：

| mode | 执行内容 |
| --- | --- |
| `previous` | Background、目标前的 Scenario Steps、目标 Step |
| `background` | Background、目标 Step |
| `none` | 仅目标 Step，界面和数据状态由使用者负责 |

整个本地运行只能存在一个 `@single:` 标签；Outline 必须提供 `example=组.行`。
正式 `Bdd.runner` 不处理这个调试标签。

### 控制台输出格式

formatter 只改变 Behave 文本输出，不改变测试范围、断言或框架日志：

| formatter | 效果 |
| --- | --- |
| `"progress2"` | 当前推荐，输出简洁进度，控制台仍保留框架日志 |
| `"null"` | 不输出 Feature/Scenario/Step 文本，控制台最安静 |
| `"pretty"` 或 `None` | 输出完整 Feature/Scenario/Step 文本，适合核对步骤顺序 |
| `"progress"` | 输出简短进度符号 |

## 输出产物

普通运行报告表示最近一次执行；最终交付报告和运行知识采集是不同产物。复跑或启动
下一次本地运行前，先确认需要保留的证据不只存在于会被清理的普通输出目录。

| 目录 | 内容 |
| --- | --- |
| `artifacts/logs/` | loguru 日志 |
| `artifacts/screenshots/` | 失败截图、OCR/图片调试图 |
| `artifacts/recordings/` | 失败场景录屏和 ffmpeg 临时分片 |
| `artifacts/recording_sessions/` | Feature Step Recorder 的逐 Step 录制会话 |
| `artifacts/knowledge-captures/` | 开启运行知识采集时的观察、原始 PNG 和自动导出的场景 Markdown |
| `artifacts/reports/` | 报告输出目录 |
| `artifacts/final-reports/` | 最终交付报告及其附件快照，使用方法见第 6 份指南 |
| `artifacts/run-results/` | 与生成事务绑定的内容寻址运行结果 |

本地 runner 默认清理上一轮截图、普通录屏和报告。Recorder 会话位于
`artifacts/recording_sessions/`，不会随普通用例运行自动清空；知识采集与最终交付报告
也不是这项普通产物清理的对象。采集证据清理条件见
[7.运行知识采集](7.运行知识采集.md#审阅和清理)。

`artifacts/`只保存当前宿主项目的运行产物。框架测试通常写入操作系统临时目录；维护者
评测及历史验收工作区写入Git忽略的`framework_validation/output/`，不会混入这里。

Spark 报告默认输出：

| 文件 | 说明 |
| --- | --- |
| `artifacts/reports/autowork-report.html` | 可直接打开的本地 HTML 报告 |
| `artifacts/reports/autowork-report.json` | 报告原始数据，便于排查步骤顺序、截图附件和状态聚合 |

## 框架文档哈希与同步检查

第 1-7 份指南头部的“文档哈希（SHA256）：”字段用于上传版本标记。正文修改后，
刷新、检查、上传和更新比较统一先刷新本地哈希；无需再单独确认这一步。
下面的独立刷新命令不连接知识库、不上传文档：

```powershell
python -B -m autowork_core.knowledge.document_sync refresh
```

未指定路径时只处理第 1-7 份指南；指定单份文件时，将 Markdown 路径追加到 `refresh`
后。计算排除哈希字段所在整行，统一换行并忽略 BOM，保留其他空白和代码缩进。

在 VS Code 使用 `/document-sync` 并明确目标知识库，会先刷新选中文档的哈希行，再与
远端头部字段比较；检查不写远端。不同或缺字段时报告版本差异，读取失败则报告
无法核验。入口和完整边界见 [Document Sync Skill](../../.github/skills/document-sync/SKILL.md)。
该检查不证明远端正文未被独立修改，也不验证解析结果或 Wiki。

可以直接说“检查下文档是否需要更新”，无需事先知道具体文件或远端 ID。Skill 默认
检查第 1-7 份指南，沿用本次对话已选的知识库，未确定时才询问目标库。全部一致就
提示最新；有已核实差异时展示清单，询问“更新全部差异项 / 选择部分 / 暂不更新”，
并说明旧版保留、验证后删除及文档 ID 变化。明确选择后接续后台更新，不要求重复确认。
说“只检查，不继续更新”则只报告结果。远端缺失、冲突、无法核验和已有任务单独说明，
不混入更新全部，也不重复创建任务。

明确要求“上传指定文件到指定库”后，Skill 才会使用 `WEKNORA_SETTING.API_URL/API_KEY`
对应的 REST 接口上传。上传不等于替换旧版；同名异版会先确认，不自动删除或改名。
也可直接调用核心命令，库名/ID 与文档 ID 必须替换为实际值：

```powershell
python -B -m autowork_core.knowledge.document_sync upload "docs/3.动作参考.md" --kb "目标库名或ID"
python -B -m autowork_core.knowledge.document_sync status "返回的文档ID" --kb "目标库名或ID"
```

上传命令自身先刷新字段，再提交文件；`accepted` 仅表示服务端接收，不是解析成功。
处理状态可能是 `pending/processing/finalizing/completed/failed`；摘要失败会独立显示。
提交结果未知时先核查，不能盲目重传。仅查询状态不会上传、重解析或修改知识库。

要求更新时，Skill 先刷新哈希并核对远端：一致就提示“远端目前是最新状态”，
不一致才展示对应文档并请求更新确认。核心比较入口如下，远端字段与 ID 必须已核实：

```powershell
python -B -m autowork_core.knowledge.document_sync update "docs/3.动作参考.md" --kb "目标库名或ID" --document-id "远端文档ID" --remote-hash "远端字段的64位十六进制值"
```

不带 `--confirm` 的入口只比较，不写远端。明确确认后，Skill 使用当时展示的双方哈希
提交后台更新：先上传新版，再给旧文档关联“旧版保留·新版处理中”状态标签，旧文件
继续保留，标题和文件名不改；新版解析完成、已启用且原始来源验证通过，才将状态标签
切换为“待删除”并删除指定旧 ID。文档 ID 会改变，旧引用不自动迁移；标签也不会将
旧版排除出检索。不会先删旧版再上传。状态标签不存在时在同库创建，原有业务标签保留。

任务 ID 返回后无需在对话中等待解析。查询、恢复和取消入口如下：

```powershell
python -B -m autowork_core.knowledge.document_sync task-status "任务ID"
python -B -m autowork_core.knowledge.document_sync task-resume "任务ID"
python -B -m autowork_core.knowledge.document_sync task-cancel "任务ID"
```

阶段、时间、异常和状态标签清理结果保存在 `artifacts/document-updates/<task_id>/task.json`，
后台输出在同目录的 `worker.log`，不保存 API key。`running` 只是后台处理中，只有
`completed` 才表示新版验证及旧版异步删除均完成。上传或解析失败时保留旧版；标签清理
失败、两版并存、删除结果未知都会独立报告，不盲目重传或重复 DELETE。标签在界面标签
区域显示，数量较多时可能折叠；关联回读成功不代表已实测当前浏览器的显示效果。

查询任务完全只读。默认后台每 15 秒检查一次，等待超过 1 小时暂停；关机、休眠或
进程退出后可能需要显式恢复，不设置开机任务，也不保证主动通知当前聊天。取消不删
新版，且不能撤销已经提交的远端删除。详细确认边界和各类异常见 Skill 正文。
