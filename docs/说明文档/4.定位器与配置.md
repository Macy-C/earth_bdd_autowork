# 4. 定位器与配置

本文是 locator、data、Root 与运行配置的统一参考。先按结构定位规则写脚本，只在需要
改变项目默认行为时查看后半部分配置表。

本章示例中的窗口、容器和控件属性必须由当前 UI 检查取得，名称相同不证明对象相同。
定位验证只回答查询是否适用，不能替代场景业务判据。

| 需要解决的问题 | 使用章节 | 输入与判断结果 |
| --- | --- | --- |
| 资源应该由谁加载 | 目录、资源作用域 | Page/View 所属窗口、YAML 文件与严格引用的解析范围 |
| 选择定位方式 | Locator 基本格式、顶层窗口、Child/XPath、OCR/图片/坐标 | 当前属性或视觉证据形成查询，不从示例猜 `auto_id` |

| 配置运行行为 | 配置模型、应用生命周期、录屏与采集 | YAML 项目默认值与本次运行覆盖的边界 |

## Locator 工作台

输入是当前可访问的桌面窗口和待检查控件。使用控件树、属性和验证结果核对候选，不把
截图上的可见文字直接当作 UIA 类型或 AutomationId。

运行 `python -m Bdd.debug_tools` 会打开唯一的 Locator 工作台。顶部统一选择目标窗口；
左侧控件树和右侧 XPath 检查器共享同一个窗口、选中控件、框选与剪贴板状态。右侧
“验证工具”页按能力分为结构定位（Child、坐标）和视觉定位（OCR、图片），入口仍调用
各工具原有的验证实现，不维护第二套定位规则或状态。Recorder 通过标题栏中的唯一
“Recorder 工作台”入口打开，保持独立的录制任务工作区。

## 目录

先确定真实窗口 owner，再选择资源文件。文件放在同一目录不意味着任意 Page 都能读取；
下面区分正式窗口包与历史兼容资源加载方式。

| 目录 | 用途 |
| --- | --- |
| `Bdd/locators/` | 页面定位器 YAML |
| `Bdd/data/` | 测试数据 YAML 和图片模板 |
| `Bdd/page_obj/` | 页面对象；WindowPage 声明窗口包，历史 BasePage 声明 locator/data 文件 |

运行级公共资源：

| 文件 | 加载时机 | 说明 |
| --- | --- | --- |
| `Bdd/data/public_data.yaml` | `before_all` | 公共 data，所有页面都可读 |

### 正式长期脚本：WindowPage / WindowView

前提是已确定唯一顶层窗口及其 Root，输入为窗口 YAML、可选 View 文件和 data 文件。
初始化时编译资源并检查归属，不负责打开产品或自动导航。页面资源声明示例：

```python
class CustomerPage(WindowPage):
  root_locator_file = "customer/right_screen.yaml"
  root_locator = "customer_window"
  data_file = "customer_data.yaml"
```

WindowPage 初始化时会原子编译窗口包并加载 data。声明的文件不存在会直接报
`FileNotFoundError`，空 YAML 会当作空字典处理。

桌面长期脚本使用 `WindowPage`/`WindowView`。一个窗口目录可以拆多个子页面文件，
但整个窗口包只能声明一个 top-level Root；完整所有权规则见
[2.编写自动化脚本：窗口与子页面所有权](2.编写自动化脚本.md#窗口与子页面所有权)。

### 兼容与临时脚本：BasePage / ScriptPage

以下资源加载规则针对历史 `BasePage` 和 `ScriptPage`，不替代 WindowPage 的窗口包
唯一性规则。正式 Step 通过真实 WindowPage/View 编排，不因流程首次出现就改用脚本页。

历史 `BasePage` 页面较大时仍可声明多个资源文件：

```python
class OrderFilterPanel(BasePage):
    locator_files = [
        "orders/common.yaml",
        "orders/filter.yaml",
    ]
    data_files = ["order_filter_data.yaml"]
```

`locator_file` / `locator_files` 都是相对 `Bdd/locators/` 的路径；`data_file` / `data_files` 都是相对 `Bdd/data/` 的路径。子目录用 `/` 写即可。加载顺序是先加载列表属性，再加载单文件属性；同名 key 后加载的会覆盖先加载的。因此也可以这样写公共 + 子页面：

```python
class OrderFilterPanel(BasePage):
    locator_files = ["orders/common.yaml"]
    locator_file = "orders/filter.yaml"
    data_file = "order_filter_data.yaml"
```

临时调试或维护兼容脚本时，可以使用通用脚本页并在运行时声明资源：

```python
from autowork_core.page import get_script_page


def step_impl(context):
    ui = get_script_page(
        context,
        locator_files=[
            "orders/common.yaml",
            "orders/filter.yaml",
        ],
        data_file="order_filter_data.yaml",
    )
    ui.click("$loc:status_filter_dropdown")
    ui.assert_ocr_contains("Active", region="$loc:status_filter_options")
```

通用脚本页适合临时动作、一次性断言、录制回放或还没沉淀成 WindowPage 的脚本。
它不能绕过窗口归属不确定性；稳定复用的业务能力应进入 WindowPage/WindowView。

`get_script_page` 会复用同一个 `ScriptPage` 实例，并按调用参数增量加载资源。若要重建实例并重置已加载记录，可传 `refresh=True`。

## 资源作用域

本节决定 `$loc:` 和 `$data:` 到哪里查找。输入为已声明资源与当前 Page/Feature，
未知引用应立即暴露；不能通过加载别的窗口文件、改用裸字符串绕过拼写或归属错误。

`context.autowork_feature.locators` 和 `context.autowork_feature.data` 都是 `Stratify`
对象。每个 Feature 的 locator 容器从空状态开始，由 Page 或脚本页显式加载；data
容器从 RunState 的公共 data 模板 fork，再加载页面或 Feature data。

data 查找优先级：

```text
当前页面/Feature data > public_data.yaml > None
```

locator 没有公共回退。`WindowPage` 只解析自己的窗口包；历史 `BasePage` 和
`ScriptPage` 只解析显式加载到当前 Feature 的 locator 文件。

`BasePage` 使用显式资源引用。需要引用 locator/data 时加 `$`：

```python
self.click("$save_button")
self.input_text("$name_input", "$customer_name")
```

- `$save_button` 在 WindowPage/View 中严格查所属窗口包；历史 BasePage/ScriptPage 查当前 Feature 已加载的 locator。
- `$customer_name` 会在 data 参数中严格查 `context.autowork_feature.data`。
- 不带 `$` 的字符串不再自动查资源：locator 参数按临时 locator，data 参数按直接文本。

临时调试仍可直接传临时 locator 或直接文本；长期脚本建议把稳定 locator/data 沉淀到 YAML，并用 `$` 引用。

通过 `WindowPage` 或 `WindowView` 传入内联 locator 时，显式 `root` 和 `region` 引用在所属窗口包内解析，使用与命名 locator 相同的实际资源和 root 缓存身份。View 委托所属 Page；未知引用立即报错，不查其他窗口包或 Feature 全局资源。绑定不修改原始字典，也不改绑已有的 `CompiledLocator`；历史 `BasePage` 的临时 locator 仍使用原有 Feature 资源路径。

存在性查询区分“正常未命中”和“查询执行失败”：只有正常未命中才返回 `False` 并允许等待。root 缺失、非法配置、目标歧义和后端异常会向上传递，不能被 `assert_exists` 误报为元素不存在，也不能让 `assert_not_exists` 意外通过。

引用规则：

| 写法 | 使用位置 | 行为 |
| --- | --- | --- |
| `$save_button` | locator 参数 | 必须命中 locator `save_button` |
| `$customer_name` | data 参数 | 必须命中 data `customer_name` |
| `$success_message` | OCR 文本参数 | 自动查 locator/data；两边都命中时报歧义 |
| `$loc:success_message` | 任意支持视觉值的位置 | 强制按 locator 解析 |
| `$data:success_message` | 任意支持视觉值的位置 | 强制按 data 解析 |
| `$$100` | 任意字符串参数 | 字面量 `$100` |

## Locator 基本格式

输出是交给编译器的 YAML 条件，不是已验证控件。以下是格式骨架，`by` 应选择一种
实际方式，不能将 `child | xpath | pos` 原样作为枚举值；各方式必需字段见对应小节。

推荐使用 dict 写法：

```yaml
locator_name:
  root: some_root
  by: child | xpath | pos
  value: xxx
```

基本规则：

- `root` 只能引用顶层窗口 locator，用于限定 Child/XPath 查询所属窗口。
- `by` 表示定位方式；不写时默认按 `child` 处理。
- `xpath`、`ocr`、`pic`、`pos` 也推荐使用 dict 写法。
- 旧字符串写法仍兼容，适合临时调试和历史 locator。
- 无前缀字符串是legacy临时locator，只依次精确查询`auto_id`和Accessible Name；不会
  隐式回退OCR。视觉定位必须显式声明`by: ocr`/`by: pic`和`region`。
- Child/XPath 不支持中间 Root；容器关系应直接写进完整 XPath。
- OCR/PIC locator 不支持 `root`，需要缩小截图范围时配置 `region` 或调用时传入 region。

## 顶层窗口

适用于声明 WindowPage 唯一的桌面窗口。输入是窗口身份条件和必要的屏幕范围；结果
是用于后续定位的窗口 Root，不会启动应用。顶层窗口不写 `root`。

```yaml
calc_window:
  backend: uia
  control_type: Window
  title_re: "计算器"
```

如果窗口标题不稳定，优先使用 `class_name`、`auto_id`、`title_re` 等组合条件。

```yaml
customer_window:
  backend: uia
  control_type: Window
  auto_id: "CustomerForm"
```

顶层窗口默认只在主屏查找。单屏环境下主屏就是唯一屏幕；多屏环境下，如果同一类
窗口可能出现在多个屏幕，请在顶层 Root 上声明 `screen`，子控件 locator 仍只通过
`root` 归属到该窗口。

```yaml
screen2_window:
  top_level: true
  backend: uia
  control_type: Window
  class_name: MyAppWindow
  screen:
    id: 2
```

`screen.id` 对应 Windows 显示器编号，例如显示设置中的屏幕 1、屏幕 2。也可以显式
声明主屏或全桌面查找：

```yaml
main_window:
  top_level: true
  backend: uia
  control_type: Window
  class_name: MyAppWindow
  screen:
    role: primary

any_screen_window:
  top_level: true
  backend: uia
  control_type: Window
  class_name: MyAppWindow
  screen: all
```

如果指定屏幕上没有匹配窗口，或同一屏幕上匹配到多个窗口，框架会报错而不是随机
选择。窗口启动后会缓存本次运行的 handle；再次使用时会复核窗口身份和 `screen`，
窗口被拖到其他屏幕后不会继续沿用旧缓存。

## Child 定位

适用于能用 UIA/Win32 结构属性唯一描述的目标。前提是顶层 `calc_window` 已声明，
`control_type` 和 `auto_id` 来自当前控件属性；按单目标查询时多个候选是歧义，不能取首项。

```yaml
equal_button:
  root: calc_window
  by: child
  control_type: Button
  auto_id: "equalButton"
```

`by: child` 可省略：

```yaml
equal_button:
  root: calc_window
  control_type: Button
  auto_id: "equalButton"
```

常用字段别名：

| 目标 | 支持写法 |
| --- | --- |
| 文本 | `name`、`text`、`title`、`caption`、`label` |
| AutomationId | `auto_id`、`automation_id`、`id` |
| 控件类型 | `control_type`、`type`、`tag`、`role` |
| 类名 | `class_name`、`class`、`classname` |

结构定位中的`name`统一表示控件的Accessible Name。`text`、`title`、`caption`和
`label`只是历史输入别名，也按同一个Accessible Name精确比较，不表示Edit/Document
正文；`title_re`等正则同样只匹配Accessible Name。Accessible Name为空时保持为空，
属性读取失败会作为backend错误暴露，不会改读`window_text`、`rich_text`或OCR。

Child locator 不接受 `index` / `found_index`。`first_only` 属于调用方式，不属于 locator 条件：

- `first_only=True`：按 Child 条件定位单个目标；匹配多个时按单元素语义报歧义，不会静默取第一个。
- `first_only=False`：使用框架兼容分支返回全部匹配元素列表。

Child 验证器固定执行唯一性校验：先通过 `first_only=False` 统计全部候选；只有数量恰好为 `1`，并且该元素满足等待状态时才验证通过。`0` 个表示未找到，多个表示 locator 不唯一，调试器会框选并列出全部候选。需要按第 N 个目标定位时，应改用 XPath `[N]`，例如 `//Button[@name='Save'][1]`。

调试工具的 Child“超时秒”表示轮询等待上限。验证器每隔约 `0.2` 秒按当前条件重新查询，并检查所选等待状态（`exists`、`visible`、`enabled`、`ready` 或 `none`）；填写 `0` 时只查询一次。

Child 验证器直接提供 `control_type`、`auto_id`、`title` 和 `class_name`。其他核心过滤条件通过“其他条件（YAML）”填写，支持：

```yaml
title_re: "^Save"
auto_id_re: "^save"
class_name_re: "Button$"
process: 1234
handle: 5678
depth: 2
framework_id: Win32
visible: true
enabled: true
```

可用键由框架核心 `CHILD_FILTER_KEYS` 统一定义；验证器不会维护另一份定位规则。Root 和 backend 由调试器窗口选择负责，不放入“其他条件”。

示例：

```yaml
guest_button:
  root: customer_window
  control_type: Button
  auto_id: "GuestButton"
```

### selection

适用于通过 Selection Pattern 读取当前选中项。先按稳定属性定位控件，再读取选中状态；
locator 中的状态过滤与断言中对完整列表的比较是不同操作。

`selection`（来源为 `Selection.Selection`，兼容别名 `Selection.Selection` 和
`selection.selection`）读取 UIA Selection Pattern
中当前选中项的 Accessible Name，返回名称列表：单选为 `["32*0.625"]`，未选择为
`[]`，多选保留全部名称。不支持该 Pattern 时取值使用 `default`；后端读取失败遵循
现有入口的错误处理规则。该字段不是 ComboBox 的 `name` 或 `Value.Value`，也不会
自动解析选中项的子 Text。

```python
selected = page.get_attr("$loc:collimation", "selection")
page.assert_attr_equal("$loc:collimation", "selection", ["32*0.625"])
page.save_attr("$loc:collimation", "selection", "original_collimation")
```

`get_attr` 返回真正的 Python `list[str]`，不是列表格式的字符串；只有调试属性面板
会转换成显示字符串。例如名称为 `"111"` 时，返回 `["111"]`，不是数字列表 `[111]`：

```python
selected = page.get_attr("$loc:collimation", "selection")
if not selected:
  raise ValueError("未读到选中项")
selected_text = selected[0]
```

`selected_text` 是字符串，可传给需要文本的动作。需要数字运算且名称确实是数字时，
显式使用 `int(selected_text)` 或 `float(selected_text)`。`save_attr` 保存的仍是列表，
不是字符串；多选时可以迭代列表使用全部名称。

Child 和 XPath 的标量条件匹配任一选中项名称；属性相等断言仍比较完整列表：

```yaml
selected_collimation:
  root: customer_window
  control_type: ComboBox
  auto_id: "control:CtComboBox_1"
  selection: "32*0.625"
```

```xpath
//ComboBox[@auto_id='control:CtComboBox_1' and @selection='32*0.625']
```

选中值是可变状态；通常先按稳定标识定位，再取值或断言。读取只查询当前目标，
不展开下拉框、不遍历全部选项。调试器查看控件属性时显示此字段，加载控件树和
切换窗口时不预采集 Selection。

## XPath 定位

适用于需要祖先、子项或兄弟关系区分的结构目标。输入为顶层 Root 和受支持的 Windows
控件树表达式；先检查关系和唯一性，不把浏览器 XPath 的完整语法或索引习惯套用进来。

推荐 dict 写法：

```yaml
num1_button:
  root: calc_window
  by: xpath
  value: "//Button[@auto_id='num1Button']"
```

旧字符串兼容：

```yaml
num1_button_old: root = calc_window | //Button[@auto_id='num1Button']
```

兄弟级定位：

```yaml
name_input:
  root: customer_window
  by: xpath
  value: "//Text[@name='Name']/next::Edit"

query_prev:
  root: customer_window
  by: xpath
  value: "//Button[@name='Search']/prev::*[0]"
```

规则：

- `next::` / `following-sibling::` 表示后面的兄弟控件。
- `prev::` / `preceding-sibling::` 表示前面的兄弟控件。
- `prev::*[0]` 是最近的前一个兄弟。
- `prev::*[1]` 是再前一个。
- `next::*[0]` 是最近的后一个兄弟。

父级定位：

```yaml
customer_group:
  root: customer_window
  by: xpath
  value: "//Text[@name='Name']/parent::Group"
```

也支持显式 `child::`、`descendant::` 和 `ancestor::`。例如在稳定导航树分支内定位：

```yaml
license_status:
  root: preferences_window
  by: xpath
  value: "//TreeItem[@name='Settings']/descendant::TreeItem[@name='Licensing']/child::Text[@name='Status']"
```

这是面向 Windows 控件树的受控 XPath 子集，不是完整 W3C XPath。支持 `/` 子级、`//`
后代、上述父级/祖先/兄弟轴、`*`、零基正负索引、属性相等、`and` 和 `contains()`；不支持
联合表达式、任意 XPath 函数或通用布尔/算术表达式。

XPath 属性名尽量贴近 Microsoft Inspect 常见属性，支持 `framework_id`、`help_text`、`value`、`enabled`、`visible`、`offscreen`、`legacy_value` 等过滤。

```yaml
save_button:
  root: customer_window
  by: xpath
  value: "//Button[@name='Save' and @enabled='true']"

name_edit:
  root: customer_window
  by: xpath
  value: "//Edit[@value='Example Customer']"
```

## OCR 定位

适用于结构属性不足但文字在当前画面可见的目标。输入为目标文字、匹配方式及唯一的
结构 Region；正式窗口包必须有本地 Region。结果是视觉候选，不保证它是特定 UIA 控件。

```yaml
save_by_ocr:
  by: ocr
  value: Save
  region: save_panel
```

需要特殊调参时，在 locator 中只写覆盖项，未写的继续走 `OCR_SETTING`：

```yaml
small_text_by_ocr:
  by: ocr
  value: Save
  region: save_panel
  match_mode: exact
  index: 0
  det_unclip_ratio: 1.8
  det_box_thresh: 0.65
```

规则：

- OCR locator 应尽量配置 `region`；region 引用一个普通 Child/XPath locator。
- WindowPage/View 窗口包中的 OCR locator 必须有本地 `region`；旧入口的全屏能力不作为正式脚本推荐。
- 只在 UIA/child/xpath 不可靠时使用 OCR。
- 文本较短或容易混淆时，优先缩小 region 区域。
- 适合动态覆盖：`match_mode`、`index`、`det_unclip_ratio`、`det_box_thresh`。
- 谨慎动态覆盖：`det_limit_side_len`、`cache_ttl`。
- 不建议 locator 覆盖：`mode`、`warmup`、`recognition_batch_size`。
- 显式 OCR locator 失败会保存 `artifacts/screenshots/ocr_find_failed_*.png`。

## 图片定位

适用于存在可用模板、显示缩放与目标画面相容的视觉目标。输入是模板及结构 Region，
结果是匹配位置或候选；重复图标先按区域和对象证据消歧，不盲目降低阈值。

```yaml
save_icon:
  by: pic
  file: save_button.png
  region: toolbar_region
  pos: 5
  threshold: 0.75
  method: mstpl
  rgb: true
```

图片模板默认从 `Bdd/data/` 目录读取，不写扩展名时默认补 `.png`。

| 字段 | 必填 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `file` / `value` | 是 | 无 | 模板文件名或绝对路径 |
| `region` | 窗口包必填 | 兼容入口未限定时为全屏 | 普通 Child/XPath locator 名称，用其唯一目标矩形限定搜索区域 |
| `pos` | 否 | `PIC_SETTING.POS` | 返回模板上的目标点，`5` 为中心 |
| `threshold` / `confidence` | 否 | `PIC_SETTING.THRESHOLD` | 匹配阈值，越高越严格 |
| `method` | 否 | `PIC_SETTING.METHOD` | 如 `mstpl`、`tpl`、`sift`、`brisk`；空值使用 Airtest 默认策略 |
| `rgb` | 否 | `PIC_SETTING.RGB` | 是否启用颜色匹配 |
| `index` / `found_index` | 否 | 不传 | 显式传入时启用多候选选择，按屏幕从上到下、从左到右排序；不传时保持最佳命中快路径 |
| `timeout` | 否 | `PIC_SETTING.TIMEOUT` | 当前图片等待上限 |
| `interval` | 否 | `PIC_SETTING.INTERVAL` | 轮询间隔，越小越灵敏但 CPU 占用更高 |
| `scale_max` / `scale_step` | 否 | `PIC_SETTING` | 多尺度匹配参数，主要影响 `mstpl/gmstpl` 的速度和容错 |

图片 `index` 只在显式写入时启用多候选路径。默认不写时仍走单个最佳命中，不影响原有速度。需要第 N 个相同图标时，建议先缩小 `region`，再设置 `index` 或 `found_index`。

临时调试可直接指定模板及区域；`"111"` 在图片 API 中是 `Bdd/data/111.png` 的模板名，
不是 locator key。模板文件与 `Notepad_window` 区域 locator 必须实际存在：

```python
self.wait_pic_present("111", region="$loc:Notepad_window")
```

正式脚本使用 `$loc:save_icon` 引用已声明的图片 locator，不给图片条件写 `root`。

显式图片 locator 失败会保存 `artifacts/screenshots/pic_find_failed_*.png`。

## 坐标定位

仅在明确接受其显示布局依赖时使用。输入必须带来源桌面尺寸，运行时换算输出位置；
坐标落在屏幕内不证明对应业务控件正确，布局或缩放变化后需要重新核对。

```yaml
fixed_pos:
  by: pos
  coords: [570, 745, 1920, 1080]
```

字符串写法：

```yaml
fixed_pos_text: "pos:570,745,1920,1080"
```

坐标必须包含 `x, y, source_width, source_height` 四个整数，来源桌面宽高必须大于 0；两值写法会在 locator 编译阶段直接报错。运行时会按配置中的桌面尺寸做比例换算。坐标定位适合调试或无法稳定识别的兜底场景，不建议作为长期主定位方式。

可在 `python -m Bdd.debug_tools` 的“坐标验证”中填写来源桌面尺寸并验证最终换算落点。坐标窗口打开时，将鼠标移动到目标位置后按 `F4`，即可读取当前坐标；窗口未打开时 `F4` 不执行坐标读取。

## RootStore

本节解释运行时缓存的生命周期，不是让业务代码手工维护窗口句柄。输入仍是 Page/YAML
声明的窗口条件；缓存失效后重新查询，不能把历史 handle 当作当前窗口身份。

RootStore 在当前 Scenario 内缓存顶层窗口。普通 Child/XPath locator 直接引用顶层
Root；中间容器通过 locator 表达，不作为第二个窗口 Root。

```yaml
main_window:
  backend: uia
  control_type: Window
  title_re: "业务系统"

customer_panel:
  root: main_window
  control_type: Pane
  auto_id: "CustomerPanel"

search_button:
  root: main_window
  by: xpath
  value: //Pane[@auto_id='CustomerPanel']//Button[@name='Search']
```

长期用例应在 YAML 中声明顶层窗口。仅临时调试时可以显式设置当前窗口：

```python
self.set_root({"class_name": "Notepad"}, name="Notepad_window")
```

Root 缓存只在当前 Scenario 有效。窗口关闭并重开后，框架会检查缓存 handle，并在失效
时按原 locator 重新定位；业务代码不应直接读写 RootStore 或依赖其内部状态。

定位规则：

- locator 中的 `root` 必须引用顶层窗口，并优先命中 `RootStore` 缓存。
- 历史 BasePage/ScriptPage 的普通定位可回退到 `last_root`；WindowPage 窗口包中的结构定位必须声明所属窗口 Root，不能靠调用顺序补齐。
- 顶层窗口 root 建议写 `control_type: Window` 或显式 `top_level: true`，避免把普通 child 条件误当最终控件定位。
- Child 条件在顶层窗口内不唯一时，应改用完整 XPath 表达祖先关系。
- OCR/PIC 的 `region` 引用普通 Child/XPath locator；显式动作参数 region 优先于 YAML region。
- Region locator 自身可以引用顶层 root，但不能是 OCR/PIC/POS，且必须唯一定位到有有效矩形的元素；匹配多个元素时抛出 `ElementAmbiguousError`，不会静默使用第一个候选。
- 多个 YAML 文件用于组织，不形成文件级作用域。WindowPage/View 合并到所属窗口包并拒绝重复名称；历史 BasePage/ScriptPage 加载到当前 Feature 映射，不能把后者的覆盖规则套到窗口包。

窗口与子页面如何划分见
[2.编写自动化脚本：窗口与子页面所有权](2.编写自动化脚本.md#窗口与子页面所有权)。
Root 缓存实现细节见 [维护文档/2.架构设计](../维护文档/2.架构设计.md#root-缓存)。

## Data 规则

用于静态测试输入与静态预期，不存放每次运行取得的基线或新结果身份。输入为 YAML
及 Page 的 data 声明，输出按 data 参数语义解析；动态值使用 Scenario 变量。

`Bdd/data/*.yaml` 用于维护测试数据或图片模板文件。页面对象通过 `data_file` 或 `data_files` 声明：

```python
class CustomerPage(WindowPage):
  root_locator_file = "customer/right_screen.yaml"
  root_locator = "customer_window"
  data_file = "customer_data.yaml"
```

多个页面共享同一组业务数据时，可以让不同 Page Object 指向同一个 data 文件；需要组合公共数据和业务数据时使用 `data_files`。

示例：

```yaml
customer_name: Example Customer
customer_id: C0001
remark: 自动化测试数据
```

页面中调用：

```python
self.input_text("$customer_name_input", "$customer_name")
self.assert_text_contains("$customer_row", "$customer_name")
```

不带 `$` 的 data 参数会作为直接文本使用：

```python
self.input_text("$loc:remark_input", "hello world")
```

如果希望引用 data，并在 key 拼错时立即失败，使用 `$data_key` 或 `$data:data_key`：

```python
self.input_text("$loc:customer_name_input", "$data:customer_name")
self.assert_text_contains("$loc:customer_row", "$data:customer_name")
```

## 命名建议

命名用于表达已经核实的用途，不赋予控件身份或 UIA Pattern。名称中的 `_button` 不会
把一个实际 Text/Custom 控件变成 Button；保留真实查询条件与当前验证依据。

- locator 名称使用业务含义，如 `customer_search_input`、`save_button`。
- 避免只用控件类型命名，如 `button1`、`edit2`。
- 图片模板文件名和 locator 名称尽量对应，如 `save_icon.png` 对应 `save_icon`。
- data 名称表达数据含义，如 `customer_name`、`invalid_password`。
- 每个顶层窗口的 Root 和控件放入所属 `WindowPage` 窗口包。
- 同一窗口内共享的导航或区域使用 `WindowView`，locator 仍放在该窗口目录。
- 偶现但独立的顶层提示窗口也使用单独的 `WindowPage`，通过 `wait_until_open()`
  判断是否出现。

## 配置模型

本节用于确定配置写在哪里，不要求为调试覆盖整份配置。输入是项目 YAML 或本次覆盖，
结果是当前运行使用的 Settings；配置加载成功不代表外部程序、模型或设备可用。

运行配置分两层：`Bdd/config.yaml` 保存项目默认值；`settings_overrides` 只覆盖当前
本地运行，结束后自动恢复。配置加载到 `config.settings.settings`。YAML 使用分组字段，
Python 使用扁平属性名，例如 `RECORD_SETTING.MODE` 对应 `settings.record_mode`。

```yaml
log:
  file: "logs.logs"
  level: "INFO"

draw_outline_location: false
APP_LAUNCH_MODE: "auto"

APP_SETTING:
  APP_PATH: "notepad"
  BACKEND: "uia"
  PROCESS_TRACK_MODE: "snapshot"

SUB_APP_SETTING: {}

RECORD_SETTING:
  MODE: "failed"
  FPS: 5
  BUFFER_SECONDS: 8
  SEGMENT_SECONDS: 2
  MAX_WIDTH: 1280
  MONITOR_INDEX: 1
  FFMPEG_PATH: ""

RUN_INDICATOR_SETTING:
  ENABLED: true
  MAX_SCENARIO_CHARS: 28

KNOWLEDGE_CAPTURE_SETTING:
  ENABLED: false

WEKNORA_SETTING:
  API_URL: ""
  API_KEY: ""
  KNOWLEDGE_BASES:
    FRAMEWORK_DOCS: ""
    ENGINEERING_CASES: ""
    PRODUCT_DOCS: ""
    STATIC_UI_DOCS: ""

UI_INVENTORY_SETTING:
  STORE_DIR: "artifacts/ui-inventory"
  DEFAULT_LOCALE: "en-US"
  REPO_CACHE_MODE: "persistent"
  BUILD_LISTS: []
  EXCLUDE_PATH_PATTERNS: []
  REFERENCE_DLL_DIRS: []
  REPOSITORIES: []

SPARK_REPORT: true

OCR_SETTING:
  MODE: "accurate"
  TIMEOUT: 10
  INTERVAL: 0.5

PIC_SETTING:
  MODE: "accurate"
  THRESHOLD: 0.7
  TIMEOUT: 10
  INTERVAL: 0.3
```

这是配置结构示例，不要求覆盖已有项目配置。WeKnora 字段可留空，本地采集、导出和
校验仍可使用；只有显式远端操作才需要实际地址与凭据。

### 基础配置

以下字段定义 `Bdd/config.yaml` 的项目默认运行行为，右列给出 Settings 属性。需要
只覆盖本次运行时使用 `settings_overrides`，不要把 YAML 分组字段直接当 Python 参数。

| YAML 字段 | settings 属性 | 说明 |
| --- | --- | --- |
| `log.file` | `log_file` | 本 Run 日志文件名，不能含目录或绝对路径；独立工具仍使用公共日志目录 |
| `log.level` | `log_level` | `DEBUG`、`INFO` 等日志级别 |
| `log.rotation` | `log_rotation` | 本 Run 各阶段内的 Loguru 文件轮转条件 |
| `log.retention` | `log_retention` | 只作用于本 Run 本阶段的轮转段，不是整 Run 保留期限 |
| `APP_LAUNCH_MODE` | `app_launch_mode` | `auto` 启动应用，`attach` 连接已有应用 |
| `draw_outline_location` | `draw_outline` | 定位成功后是否高亮控件 |
| `APP_SETTING.APP_PATH` | `app_path` | 应用路径、命令或宿主 `runtime` Hook |
| `APP_SETTING.BACKEND` | `backend` | pywinauto 的 `uia` 或 `win32` backend |
| `APP_SETTING.PROCESS_TRACK_MODE` | `app_process_track_mode` | `snapshot`、`root` 或 `none` |
| `SUB_APP_SETTING` | `sub_app_profiles_by_tag` | 可选子项目应用；为空时保持默认 `APP_SETTING` 行为 |
| `SPARK_REPORT.ENABLED` | `spark_report` | 是否生成 Spark HTML/JSON；兼容原布尔写法 |

正常 BDD 在启动时冻结本轮日志/媒体设置，日志归档为
`artifacts/runtime-evidence/<execution-id>/logs/execution/<log.file>`；最终封存后的报告/知识日志位于
同一 Run 的 logs/delivery，派生结果位于 logs/delivery-summary.json，不再重复写公共 artifacts/logs。
业务仍调用原 logger，无需额外初始化。默认结构化日志最多 5000 条、单条 4096 字符，执行文本总量
16 MiB、交付文本 4 MiB；预算或 retention 导致缺失会明确标记，不改变测试结果。
关闭报告和知识开关不关闭基础采集。无 Collector 的独立动作工具保持自己的公共日志行为，
不自动创建运行证据目录；本轮未引入新的 YAML 分组，也不自动清理历史 Run。

### 报告失败诊断

诊断配置位于 SPARK_REPORT 内部，不是另一个平级开关。默认关闭，不连接模型或外发材料：

```yaml
SPARK_REPORT:
  ENABLED: true
  DIAGNOSIS:
    ENABLED: false
    INCLUDE_IMAGES: false
    MAX_ITEMS: 3
    MAX_INPUT_TOKENS: 60000
    MAX_OUTPUT_TOKENS: 4096
```

| DIAGNOSIS 字段 | settings 属性 | 说明 |
| --- | --- | --- |
| `ENABLED` | `report_diagnosis_enabled` | 报告启用时，同步分析失败单元；启用即允许发送筛选、脱敏后的文本 |
| `INCLUDE_IMAGES` | `report_diagnosis_include_images` | 另外允许发送已采集图片的诊断副本，默认 false |
| `MAX_ITEMS` | `report_diagnosis_max_items` | 每轮最多分析 3 个失败 Scenario/Example 或 Run 单元；0 不发请求 |
| `MAX_INPUT_TOKENS` | `report_diagnosis_max_input_tokens` | 单次输入的估算预算，默认 60000；包含提示词、文字及图片预留 |
| `MAX_OUTPUT_TOKENS` | `report_diagnosis_max_output_tokens` | 单次模型输出上限，默认 4096，传给兼容接口的 max_tokens |

旧 `SPARK_REPORT: true/false` 继续可用，但不启用诊断。报告总开关关闭时诊断也不运行。
模型地址、凭据和连接/读取超时继续取 LLM_SETTING，报告对象在创建时固定本轮有效设置。
首版同步收尾：先写基础报告，再分析并更新呈现，最后发布一次；因此开启后运行入口会等待模型。
模型错误不改变测试状态，页面会显示未分析、证据不足、失败或超时；没有后台任务或自动重试。

当前模型窗口按 256 * 1024 token 管理，额外预留 8192 安全空间；输入预算会受输出预留约束。
未绑定模型专用 tokenizer，文字以 UTF-8 字节作保守代理，最多两张 1024 像素边长的图片，
每张暂预留 16384 token；这是预算估算，不是精确计数或通用多模态容量保证。
材料优先保留异常、失败步骤与近期动作/日志，显式记录截断、省略和缺失；不截断 Collector 原件。
图片需处于选中 Run 目录且摘要匹配，仅生成缩小 JPEG 副本，不重新抓屏，不承诺图片可通用脱敏。
运行证据之外的任意文件、源码全集、完整业务输入不自动发送。

诊断结果在 `artifacts/runtime-evidence/<execution-id>/diagnostics/diagnosis.json`，必要的图片副本在
同目录 images。报告中展示摘要、原因候选、证据引用、排查建议、缺失和预算；诊断不会回写 run.json。
合并报告保留场景来源，场景被新结果替换时不继承旧诊断；纯 render 不联网或重新分析。

## 应用生命周期配置

先决定应用由框架启动清理，还是由用户/外部平台提供；再选择进程范围。输入为启动模式、
路径与宿主 Hook，结果涉及真实应用启停，不能仅为解决定位问题扩大进程清理范围。

`APP_LAUNCH_MODE=auto` 时，框架启动应用并在场景结束后清理拥有的进程；还会调用可选的
`Bdd.application.prepare_scenario()` 和 `cleanup_scenario()`。`attach` 不启停已有应用，
但仍调用这两个项目资源 Hook。

| `PROCESS_TRACK_MODE` | 清理范围 | 适用场景 |
| --- | --- | --- |
| `snapshot` | 启动前与首个 Step 前的 PID 差集，以及清理时仍关联的子孙进程 | 默认；适合启动器、BAT 或派生进程 |
| `root` | 启动命令返回的 PID 及仍挂载的子孙进程 | `APP_PATH` 直接启动主程序 |
| `none` | 不自动跟踪或清理进程 | 本地调试或外部平台管理 |

`snapshot` 在首个 Step 前等待 1 秒后冻结第二次快照；Step 内后来启动的进程不会混入。
清理时按叶到根终止并重试残留进程，但无法安全识别已脱离进程树、由已有服务后来启动
的产品进程。这类产品应使用 `APP_PATH=runtime` 的宿主 Stop。

`APP_PATH=runtime` 要求 `Bdd.application` 提供 `start_application()` 和
`stop_application()`，缺失即失败关闭。宿主 Stop 决定关闭对象；此时可把
`PROCESS_TRACK_MODE` 设为 `none`，避免无效快照。

有子项目应用时，主项目仍配置在 `APP_SETTING`，子项目放在可选的
`SUB_APP_SETTING` 中，并由 Feature 或 Scenario tag 选择：

```yaml
APP_LAUNCH_MODE: "auto"

APP_SETTING:
  APP_PATH: "C:/MainApp/Main.exe"
  BACKEND: "uia"
  PROCESS_TRACK_MODE: "snapshot"

SUB_APP_SETTING:
  sub_app_a:
    TAG: "sub_app_a"
    APP_PATH: "C:/SubProjectA/AppA.exe"
    PROCESS_TRACK_MODE: "snapshot"
```

没有 `SUB_APP_SETTING`、字段为空或当前 Scenario 没有匹配 tag 时，框架使用
`APP_SETTING`。匹配子项目 tag 时，`auto` 只启动对应子项目应用，`attach` 仍不启动
任何应用。一个 Scenario 同时匹配多个子项目 tag 会报配置错误。

## 录屏与运行提示

录屏用于保留执行现场，不改变测试预期；输入为录制模式、屏幕及质量参数，输出为对应
视频或缓存分片。提示条只是时间与场景显示，不是测试进度或业务完成信号。

| `RECORD_SETTING` 字段 | settings 属性 | 说明 |
| --- | --- | --- |
| `MODE` | `record_mode` | `off`、`failed`、`all` |
| `FPS` | `record_fps` | ffmpeg 帧率，通常 `3~5` |
| `BUFFER_SECONDS` | `record_buffer_seconds` | `failed` 模式保留失败前多少秒 |
| `SEGMENT_SECONDS` | `record_segment_seconds` | 滚动缓存分片长度 |
| `MAX_WIDTH` | `record_max_width` | 视频最大宽度，`0` 为原分辨率 |
| `MONITOR_INDEX` | `record_monitor_index` | 录制屏幕索引 |
| `FFMPEG_PATH` | `record_ffmpeg_path` | 空值使用 `resources/ffmpeg/current/bin/ffmpeg.exe` |
| `FFMPEG_PRESET` | `record_ffmpeg_preset` | x264 preset |
| `FFMPEG_CRF` | `record_ffmpeg_crf` | 越大文件越小、质量越低 |
| `FFMPEG_DRAW_MOUSE` | `record_ffmpeg_draw_mouse` | 是否录入鼠标指针 |

`off` 不录屏；`failed` 使用滚动分片并只在失败时合并最近现场；`all` 完整直录并删除
通过场景的视频。OCR、PIC 和失败截图仍使用 mss。旧的 `RECORD: true/false` 不再读取。

`RUN_INDICATOR_SETTING.ENABLED=true` 时，普通 UI Scenario 在右上角显示当前场景与整次
Run 累计时长；窗口不抢焦点且鼠标穿透。`@api`、跳过场景和禁用配置不显示，提示异常
只记录 warning。

## 运行知识采集

普通 BDD 的基础运行证据始终由 RunEvidenceCollector 记录于
`artifacts/runtime-evidence/<execution-id>/run.json`，不依赖 Spark 报告或知识开关。
失败截图和运行录屏属于本运行的隔离目录；公开报告入口不变。
下方知识开关只增加详细动作值、来源与知识相位图需求，以及知识案例投影/导出，
不会再创建第二套通用采集 owner。轻量动作调试保持不自动采集。

本节只说明开关与 Settings 映射。开启后在原有运行中保存本地动作观察与案例，关闭失败
录屏不等于关闭知识采集；REST 配置也不使采集结果自动上传。

| `KNOWLEDGE_CAPTURE_SETTING` 字段 | settings 属性 | 说明 |
| --- | --- | --- |
| `ENABLED` | `knowledge_capture_enabled` | 默认 `false`；启用后采集正常运行中的公开动作观察 |

| `WEKNORA_SETTING` 字段 | settings 属性 | 说明 |
| --- | --- | --- |
| `API_URL` | `weknora_api_url` | WeKnora REST 服务根地址；不得填 `/api/v1` 或 `/mcp/...` |
| `API_KEY` | `weknora_api_key` | REST API Key；不进入运行配置快照或错误回执 |
| `KNOWLEDGE_BASES.FRAMEWORK_DOCS` | `weknora_framework_docs_kb` | 框架文档库 ID 或名称（推荐填不可变 UUID 并用注释备注名称，供 `document-sync` 默认使用） |
| `KNOWLEDGE_BASES.ENGINEERING_CASES` | `weknora_engineering_cases_kb` | 工程案例库 ID 或名称（推荐填不可变 UUID 并用注释备注名称，供 `knowledge-assist` 默认使用） |
| `KNOWLEDGE_BASES.PRODUCT_DOCS` | `weknora_product_docs_kb` | 产品资料库 ID 或名称（推荐填不可变 UUID 并用注释备注名称，防止被文档同步或案例发布误写） |
| `KNOWLEDGE_BASES.STATIC_UI_DOCS` | `weknora_static_ui_docs_kb` | 可选静态 UI 控件参考库 ID 或名称（推荐填不可变 UUID 并用注释备注名称，供 `ui_inventory poll-sync/sync` 与生成端四库联查使用） |

上述四类知识库在 WeKnora 服务端的推荐建库参数（分块策略、索引开关、VLM 识图、Wiki 编译指令与静态 UI 防呆体检红线）统一维护在 [7.WeKnora知识库配置规范](../维护文档/7.WeKnora知识库配置规范.md)。

| `UI_INVENTORY_SETTING` 字段 | settings 属性 | 说明 |
| --- | --- | --- |
| `STORE_DIR` | `ui_inventory_store_dir` | 快照与导出缓存目录，默认 `artifacts/ui-inventory`（被 `.gitignore` 忽略，不入 Git） |
| `DEFAULT_LOCALE` | `ui_inventory_default_locale` | 主选择器文案语言，默认 `en-US`（支持 `zh-CN`） |
| `REPO_CACHE_MODE` | `ui_inventory_repo_cache_mode` | 远端浅仓缓存策略：`persistent`（默认，保留单深度浅仓并用 `git fetch --depth 1` 增量更新）或 `ephemeral`（扫完即删） |
| `BUILD_LISTS` | `ui_inventory_build_lists` | 可选发版 BuildList 文件路径列表，用于过滤非发版工程 |
| `EXCLUDE_PATH_PATTERNS` | `ui_inventory_exclude_path_patterns` | 可选扫描排除路径/目录名/glob 列表，过滤非主测工具或测试工程 |
| `REFERENCE_DLL_DIRS` | `ui_inventory_reference_dll_dirs` | 可选外置依赖（NuGet/SDK）DLL 目录列表，仅用于只读解析控件继承链、BAML 模板与卫星资源 |
| `REPOSITORIES` | `ui_inventory_repositories` | 可选监控源码仓列表（每项含 `ID`/`URL`/`BRANCH`/`ROLE`/`LOCAL_PATH`/`ENABLED`）；留空时不影响普通测试运行 |

配置好 `UI_INVENTORY_SETTING` 与 `WEKNORA_SETTING.KNOWLEDGE_BASES.STATIC_UI_DOCS` 后，可在各自宿主工程内直接无参运行 `python -B -m autowork_core.ui_inventory poll-sync` 完成增量巡检、构建导出与差量同步（也支持 `--store` / `--config` 覆盖）。

该功能与失败录屏开关独立，沿用同一 `Settings` 和临时覆盖机制，不使用环境变量开启。
开启后无需修改 Step 或插入截图语句。测试结果和采集完整性分开，产物位于独立的
`artifacts/knowledge-captures/`，不会自动上传。覆盖、隐私和真实环境验收边界见
[7.运行知识采集](7.运行知识采集.md)。

## settings_overrides

适用于只调整本次调试的行为。输入键是下表 Settings 属性名，不是 YAML 分组名；运行
结束后恢复，不把一次调试选择写成所有用例的新默认值。

临时覆盖传给 `run_behave()` 或 `local_runner.main()`，即使运行失败也不会写回 YAML：

```python
settings_overrides = {
    "app_launch_mode": "attach",
    "log_level": "DEBUG",
    "draw_outline": True,
    "record_mode": "failed",
}
```

| 常用属性 | 示例 | 说明 |
| --- | --- | --- |
| `app_launch_mode` | `"auto"` | 启动模式 |
| `app_path` | `"notepad"` | 启动命令或路径 |
| `backend` | `"uia"` | pywinauto backend |
| `app_process_track_mode` | `"snapshot"` | 进程清理范围 |
| `log_level` | `"DEBUG"` | 本次日志级别 |
| `draw_outline` | `True` | 定位成功后画框 |
| `record_mode` | `"failed"` | 录屏模式 |
| `run_indicator_enabled` | `True` | 是否显示运行提示 |
| `knowledge_capture_enabled` | `True` | 本次是否开启运行知识采集 |
| `ocr_timeout` / `ocr_interval` | `10` / `0.3` | OCR 等待与轮询 |
| `ocr_match_mode` | `"smart"` | OCR 匹配模式 |
| `pic_threshold` | `0.7` | 图片匹配阈值 |
| `pic_method` | `"mstpl"` | 图片匹配算法 |
| `pic_timeout` / `pic_interval` | `10` / `0.2` | 图片等待与轮询 |

这里必须写 `Settings` 属性名，不写 YAML 原始字段名。

## runner 参数

以下是 `run_behave()` 的关键字参数，不是 `settings_overrides` 内的属性。输入 Feature
路径、筛选及输出选项后会实际执行测试；`clear_screenshots=True` 会清理上一轮普通产物。

| 参数 | 默认值 | 说明 |
| --- | --- | --- |
| `feature_path` | 必填 | Feature 文件或目录 |
| `settings_overrides` | `None` | 本次临时配置 |
| `tags` | `None` | Behave 标签表达式 |
| `verbose` | `True` | 是否输出启动诊断 |
| `formatter` | `None` | 如 `progress2`、`null`、`pretty` |
| `clear_screenshots` | `True` | 是否先清理截图、普通录屏与报告 |

```python
from autowork_core.runtime.behave_runner import run_behave

run_behave(
    "Bdd/test_features/test_debug.feature",
    tags="not @skip",
    formatter="progress2",
    settings_overrides={"app_launch_mode": "attach"},
)
```

## OCR 和图片全局配置

以下配置控制识别模型/算法的默认策略，不承担控件身份与业务预期。先验证 Region、模板
或目标文字，再改变参数；高阈值不等于业务正确，低阈值也不能作为默认排障修复。

两类配置均按以下优先级解析：

```text
调用时显式参数 > locator 覆盖 > OCR_SETTING/PIC_SETTING > MODE 预设
```

### OCR_SETTING

输入为项目 YAML 中的 OCR 默认值，Python 覆盖使用对应扁平属性。模型、预热和批处理是
全局策略；单界面动态差异放在 locator 或受支持的动作参数中，不能假设每个字段都可传给每个 API。

| YAML 字段 | settings 属性 | 说明 |
| --- | --- | --- |
| `MODE` | `ocr_mode` | `fast`、`balanced`、`accurate` |
| `WARMUP` | `ocr_warmup` | 启动时预加载模型 |
| `CACHE_TTL` | `ocr_cache_ttl` | 动态页面建议 `0.0` |
| `DET_LIMIT_SIDE_LEN` | `ocr_det_limit_side_len` | 检测输入尺寸 |
| `DET_LIMIT_TYPE` | `ocr_det_limit_type` | 常用 `max` |
| `DET_BOX_THRESH` | `ocr_det_box_thresh` | 检测框阈值 |
| `DET_UNCLIP_RATIO` | `ocr_det_unclip_ratio` | 检测框外扩比例 |
| `RECOGNITION_BATCH_SIZE` | `ocr_recognition_batch_size` | 全局识别批量 |
| `TIMEOUT` | `ocr_timeout` | 默认等待时间 |
| `INTERVAL` | `ocr_interval` | 默认轮询间隔 |
| `MATCH_MODE` | `ocr_match_mode` | `smart`、`contains`、`exact` |
| `DEBUG_ON_FAIL` | `ocr_debug_on_fail` | 失败是否保存调试图 |

### PIC_SETTING

输入为图片识别默认值；实际模板和 Region 仍由具体 locator 确定。缩放、颜色和候选
选择参数必须以当前画面验证，不能因为一次命中就无条件用于其他页面。

| YAML 字段 | settings 属性 | 说明 |
| --- | --- | --- |
| `MODE` | `pic_mode` | `fast`、`balanced`、`accurate` |
| `THRESHOLD` | `pic_threshold` | 匹配阈值 |
| `POS` | `pic_pos` | 九宫格目标点，`5` 为中心 |
| `RGB` | `pic_rgb` | 是否匹配颜色 |
| `METHOD` | `pic_method` | `tpl`、`mstpl`、`gmstpl`、`kaze` 等 |
| `TIMEOUT` | `pic_timeout` | 默认等待时间 |
| `INTERVAL` | `pic_interval` | 默认轮询间隔 |
| `DEBUG_ON_FAIL` | `pic_debug_on_fail` | 失败是否保存调试图 |
| `SCALE_MAX` | `pic_scale_max` | 多尺度最大范围 |
| `SCALE_STEP` | `pic_scale_step` | 多尺度步长 |

先用 `region` 缩小视觉搜索范围，再调整阈值或算法。模型、预热和批处理等全局策略只放
在 `Bdd/config.yaml`；Locator 只覆盖当前界面的动态差异。
