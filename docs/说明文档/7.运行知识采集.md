# 7. 运行知识采集与工程案例发布
文档哈希（SHA256）：`624c4175f7ec70facfb84b9852d8e746e567ecb80cf805fbf472cd17f2ef564c`

运行知识采集记录 BDD 的实际运行证据：`Feature -> Scenario -> Step -> Page/View -> Action`、调用返回、UIA 目标和窗口截图。开启采集后，运行结束会自动为本次每个已记录场景生成独立的图文 Markdown，不调用 AI、不依赖 Skill 或模板、不连接 WeKnora，也不修改业务代码。

## 能力与使用边界

| 目标 | 入口与结果 | 是否需要远端 |
| --- | --- | --- |
| 保存本次运行证据和基础案例 | 开启采集后正常运行，结束时自动导出 Markdown | 否 |
| 校验已有案例或重新构建本地案例 | 核心 CLI 的 `verify` / `build` | 否 |
| 改善案例叙事 | 可选 AI 润色，生成新副本 | 否 |
| 上传指定案例、查询状态 | `publish` / `status`，始终指定目标库 | 是 |
| 确认 Wiki 或退役、清理 | 独立的 `accept` / `retire` / `clean` | 是，且各有前置条件 |

运行知识采集不是 Recorder 的逐 Step 录制任务，不要求先创建 Recorder Job。动作返回、
测试状态、采集完整性和知识库验收分别记录，不因导出或上传成功就认定业务验证通过。

## 采集开关

本节只执行本地采集和自动导出，不需要 WeKnora 或 AI。前提是已经有可正常启动的
BDD 运行入口；采集器记录执行中实际发生的公开动作，不补造未执行的流程。

在 [Bdd/config.yaml](../Bdd/config.yaml) 中开启后，通过原有 runner 正常运行用例：

```yaml
KNOWLEDGE_CAPTURE_SETTING:
  ENABLED: true
```

### 自动导出结果与失败边界

一次开启采集的运行产生一个独立目录，运行日志给出实际路径：

```text
artifacts/knowledge-captures/<run-id>/
  observations.json              # 冻结的运行事实和来源快照
  images/<sha256>.png            # 原始 PNG，按字节哈希去重
  <product>__<feature>__<scenario>__<case-id>.md
  <product>__<feature>__<scenario>__<case-id>.polish-spec.json  # 可选：结构化润色规格
```

运行完成后直接在该目录取得 Markdown，可自行在 WeKnora 前端上传，不需要调用 Skill 或先润色。运行日志会显示每个 Markdown 路径及前置摘要区字符预算占比。没有 `CASE_FILE` 参数，也不会向 `Bdd/ai/` 写案例。

失败场景或截图缺失的记录也会导出，文档如实标注测试状态、采集状态和缺失项，不冒充完整通过。单个场景导出失败不会阻止其他场景；错误保存在 `observations.json` 的 `markdown_export` 中并输出日志，不改变原测试结果、不删除证据。

### 7 章双平面单文档结构与分块/Wiki 对齐设计

导出的单文档采用 **“视图平面（第 1–4、6 章，供 Wiki 编译与首轮检索）”** 与 **“底层校验平面（第 5、7 章，供本地 `verify` 与按需精查）”** 解耦的 7 章结构，不依赖任何特定场景硬编码即可与 WeKnora `v0.8.3` 分块器及 Wiki 编译器咬合：

1. **第 1–3 章（前置摘要区，控制在 WeKnora `32,768` 字符摘要窗口内）**：
   - **第 1 章（身份、适用范围与本次状态）**：记录 `Case Key`、`Content Hash`、`Capture Case ID`、`Evidence Hash`、`Feature 身份` 与 `Run ID`；通过 AST 自动解析 `Bdd/page_obj/` 继承基类，将涉及组件显式划分为 **界面视图类 `WindowView`**、**窗口容器类 `WindowPage`** 与 **静态调用辅助类（非 UIA 静态调用）**；默认文档分类标签仅保留 `feature:<Feature文件名>`。
   - **第 2 章（完整场景声明）**：原样保留当前执行 Scenario 的 Gherkin 声明。
   - **第 3 章（测试方法、确定性执行时序与数据关联）**：包含 `3.1` Step 执行概览表、`3.2` 跨步骤变量读写与代码断言关联表、`3.3` 未作为公开 UIA 动作记录的静态调用与代码断言行号表、`3.4` 动作与观察边界说明（区分修改动作与只读观察）、以及 `3.5` 活跃源码与定位器快照索引。
2. **第 4 章（按 Step 组织的图文同块区）**：
   - 章节前设一级分界标题 `# 4. 动作与原图证据`（阻断分块器 `coalesceTinyChunks` 将第 3 章与第 4 章跨章合并），Step 标题统一使用 `##### Step k`（`H5`）。
   - 每个截图块采用单行紧凑结构：`##### Fxx <View> <phase> (Step k / Action k.m)<a id="fxx"></a> ![Fxx](data:image/png;base64,...) Action ...`，并附带 `>= 165` 字符且不含分块切点标点（`;`、`；`、`。`、`！`、`？`）的尾部保护串，单块展示文本总长严格 `<= 380` 字符。
   - 明确标注触发动作属于 `[交互动作]` 或 `[只读观察-不改变界面选中或预览]`。相同 PNG 全篇只嵌入一次，在 WeKnora `heading` 分块策略下 `100%` 沿 `##### Fxx` 边界 `1 对 1` 独立成块、零跨块重复。
3. **第 5 章（精确追溯索引）与第 7 章（来源指纹）**：
   - 第 5 章完整保留每条动作的 `action_id`、原始参数、返回值、起止时间戳、`Txx` 实际 UIA 控件属性、`Qxx` 编译后解析查询与 `Rxx` 截图窗口区域；第 7 章保留 `S01–Sxx` 全部来源文件的 `SHA256` 指纹。
   - 这两章作为单文档底层机器校验与精查数据保留，在 Wiki 编译阶段通过冲突检查规则自动剔除，不抄入任何 Wiki 页面正文，防止大表撑爆单页输出上限。
4. **第 6 章（实现与资源证据索引）**：
   - 表头自带 `({feature_code})` 上下文标识（经 WeKnora `HeaderTracker` 自动注入各表格子块）。
   - 通过 AST 静态声明建立 **源码与定位器 `1 对 1` 排他归属**（消除父容器 `WindowPage` 与子视图 `WindowView` 之间的交叉混标），完整保留活跃 `Page/View` 绑定的 YAML 定位器字典（含分组注释与同视图兄弟定位器，防止多场景跨案例更新共享 `entity/<WindowView>` 时覆盖丢失其他场景的定位器），并自动裁剪无关 Step 函数与未使用的视图注册属性；每个代码块使用 `### [Sxx]` / `### [Sxx-StepN]`（`H3`）标题与首行简明归属注释（`# Sxx: <Owner>`）。

### 动作截图与状态采样机制

每个公开 UI 动作记录单张代表状态截图（`after`），不再在每次动作进入时重复抢拍 `before` 帧。采集器可以先按已绑定的窗口声明被动查询窗口身份和范围，再截图；它不提前查找业务控件、不点击或聚焦、不恢复最小化，也不预热业务窗口缓存或改变当前窗口。首次使用窗口不需要在业务脚本中增加等待或预热操作。

为消除异步界面渲染延迟导致的抢拍与计时器跳动导致的重复图片：
1. **控件就绪时刻（`t_ready`）跨动作状态交接**：当修改动作执行后紧接同一 Step、同一视图与窗口的后续动作时，在后续动作定位到目标控件就绪的瞬间（`get_element` 成功返回）更新前序修改动作的结果图，确保输入的文本、展开的弹窗或切换后的界面已稳定上屏；若修改动作是当前步骤或视图的最后一步，则保留其动作完成时的兜底截图。
2. **连续只读/断言单次快门复用**：同一 Step、同一视图与窗口下连续执行的只读读取动作（如连续多次 `get_attr`）或连续断言动作（如连续多次 `assert_exists`）只在首个动作就绪完成时采样一次窗口底图，后续紧邻同类动作直接复用该底图引用，不受被测软件计时器或动态背景刷新影响。
3. **屏蔽调试蓝框与运行指示器干扰**：知识采集激活时自动跳过 `locator` 的 GDI 蓝色调试框绘制（`draw_outline`），并为运行指示器悬浮窗设置 `WDA_EXCLUDEFROMCAPTURE` 防截屏属性，保证原始截图零污染。

窗口不存在、匹配不唯一、隐藏、最小化或进程身份不符时，仍如实标记缺图，不改截主屏、不主动改变界面，也不影响原业务调用及其异常。历史运行中未成功生成的截图不会被此次修复补造，重新导出旧案例也不能补回当时的画面。

## 本地校验与重新构建

两个命令都不连接知识库，但输入不同，不能把结构校验理解成重新导出：

| 命令 | 输入 | 结果 | 限制 |
| --- | --- | --- | --- |
| `verify` | 已有案例 Markdown，可按需附观察文件 | 结构与引用检查结果 | 不执行测试，不证明业务正确 |
| `build` | 采集目录及可选场景筛选 | 本地重新构建的案例 | 候选选择要求完整通过，不替代失败现场的自动导出 |

以下路径是示例，替换为运行日志给出的实际文件或采集目录：

```powershell
python -B -m autowork_core.knowledge verify --markdown "C:\path\case.md"
python -B -m autowork_core.knowledge build --capture-dir "artifacts/knowledge-captures/<run-id>"
```

自动导出覆盖本次实际记录的场景，包括失败或不完整场景；`build` 的候选选择则要求
完整通过，不能用它代替失败现场自动导出的记录。`verify` 检查案例结构与引用等约束，
不证明产品行为正确，也不代替远端解析或 Wiki 验收。

## 可选的自动发布配置

本节仅适用于明确需要通过程序访问远端的任务，不会因为配置存在就自动发布。
输入包括实际服务器、受限 REST 凭据和明确的目标知识库；不要将凭据复制到案例正文。

只有使用程序或 AI 代为上传、查询远端时，才需要 WeKnora REST 连接配置。采集、导出、校验和纯润色不需要以下配置，用户仍可直接在 WeKnora 前端手动上传：

```yaml
WEKNORA_SETTING:
  API_URL: "http://weknora.example.internal:1101"
  API_KEY: "你的 WeKnora REST API Key"
  KNOWLEDGE_BASES:
    FRAMEWORK_DOCS: "BDD框架知识库_demo"
    ENGINEERING_CASES: "Earth工程案例库_demo"
    PRODUCT_DOCS: "Earth正式资料库_demo"
```

- 上述地址仅为示例；`API_URL` 使用实际服务根地址，不是 `/api/v1` 或 `/mcp/...` 地址。
- `API_KEY` 是 WeKnora REST API Key，不是 MCP Token。它需有目标库的 `retrieve` 和 `ingest` 权限。
- `KNOWLEDGE_BASES` 可按角色配置项目默认知识库（各角色不得指向同一库）：配置 `ENGINEERING_CASES` 后，案例发布可省略 `--kb`，且预检会拦截误传到 `FRAMEWORK_DOCS` 或 `PRODUCT_DOCS` 的操作。未配置时仍通过 `--kb` 明确指定目标知识库。
- 已配置的 VS Code MCP 用于阅读知识库和 Wiki，不能替代 REST 上传凭据。
- 先运行：

```powershell
python -B -m autowork_core.knowledge preflight --kb "Earth工程案例库_demo"
```

`preflight` 检查配置、认证后可访问的知识库及名称/ID 是否唯一，不生成、上传或清理
文件。它不通过试写验证 `ingest` 权限；写权限由实际写入时的服务端检查，不能把
`ready` 当成上传权限或 Wiki 可用性已验证。

失败回执包含 `code`、`stage`、`message`、`next_action`；HTTP 失败还会给出状态码和经过密钥脱敏的服务端原因。上传结果不确定时先保留文件与回执，按下文“查询状态与结果未知”处理，不盲目重传或清理本地文件。

## 独立能力与可选 AI 入口

基础能力位于 `autowork_core.knowledge`，从对应模块调用函数或运行核心 CLI；采集结束直接调用核心导出，不经过 AI 模块。AI 叙事润色和自然语言输入编排位于 `ai/tools/knowledge/`，不承担基础业务实现或转发。

| 用户要求 | 结果 |
| --- | --- |
| 只润色 | 新副本路径；不需要知识库、不联网上传 |
| 只上传 | 原样提交选定文件；不自动润色或审阅 Wiki |
| 润色后上传 | 上传新的润色副本，原件保留 |
| 只校验或分析 | 返回结果，不修改或外发文件 |

明确要求再次润色时可以继续生成副本，`.polished.` 文件名不替代用户指令。只有请求上传或远端操作时才需要指定知识库。

## 两种日常用法

先区分输入是“明确选定的案例文件”还是“需要从采集结果选择的场景”。只有当前要求
上传时才执行远端操作；两条路径都不把润色、Wiki 审阅或清理隐含串入上传。

### 1. 你已指定一个 Markdown 文件

适用于已存在的运行案例。用户选定的文件是唯一输入：仅上传不会触发润色，仅润色
不会触发上传；文件名含 `.polished.` 也不改变当前指令。

对 AI 说：

> 把 `C:\path\case.md` 上传到 `Earth工程案例库_demo`。

已有运行案例且只需上传时，也可直接执行核心 CLI；这不是任意框架文档的同步入口，
输入仍须满足案例身份和结构要求：

```powershell
python -B -m autowork_core.knowledge publish --markdown "C:\path\case.md" --kb "目标知识库"
```

此时该文件就是唯一输入。仅要求上传时，直接校验并上传该文件；明确要求润色后上传时，生成已校验的**润色副本**并上传副本；只要求润色时则到副本交付为止。都不会扫描采集目录、重建运行案例、覆盖或删除原文件。

文档内的 `Content Hash` 只是生成时记录的说明，过期不阻止上传，也不要求换路径或重做文件。发布器现场计算所选文件实际字节的 SHA256，并用它验证远端下载字节；源文件在提交前发生变化或远端字节不一致时，仍会拒绝确认。

场景默认仅生成并绑定 `feature:<Feature文件名>` 标签（例如 `CT-NMP-SSRS-Console.1007.feature` 对应 `feature:CT-NMP-SSRS-Console.1007`，不再自动派生 `工程案例` 或 `页面:<ViewName>` 标签）。前缀统一为小写和半角冒号，文件名去掉扩展名后完整保留；同一 Feature 的场景共用标签，移动目录不改变标签。不同 Feature 若在同一知识库使用相同文件名，也会归到同组；文件重命名不会自动调整历史标签。标签不用于判断重复、最新版本或删除旧文档。

新发布直接上传到知识库根级，不创建产品或 Feature 归档目录；`--remote-file-name` 只接受文件名。程序会保留其他标签并补齐必需的 `feature:` 标签，额外标签不能覆盖它。旧文档中的匹配 `需求:` 标签在上传参数中转换，冲突时在联网前报错，不改文件原文。旧归档路径只保留文件名，不再恢复目录；已有发布回执仍绑定原文档和原目录，不自动迁移、重传或清理旧标签。

手动上传时，在知识库根级上传，并选择或创建文档头提示的同名 `feature:` 标签；正文写有标签不表示知识库已经关联。程序上传则回读确认标签，失败单独报告分类待补，不因补标签重新上传文件。

### 2. 你要把采集结果生成案例后发布

适用于输入是 Feature/场景描述或采集目录、而非指定 Markdown 的任务。需要明确目标
和是否润色、是否上传；没有现成文件时才按本地采集事实构建，不能从标题猜运行结果。

对 AI 说：

> 把 `1007` 的运行采集润色成案例并上传到 `Earth工程案例库_demo`。

新采集在运行结束时已经生成基础案例。只有你明确要求润色时，AI 才选择最新且完整通过的场景，另行生成增强副本；基础文档不覆盖。每个案例的本地文件和建议上传文件名都包含稳定案例摘要，避免长场景名碰撞：

```text
<capture-dir>/Earth__CT-NMP-SSRS-Console.1007__Repeat-an-axial-scan__<case-id>.md
CT-NMP-SSRS-Console.1007_Repeat-Scan__Repeat-an-axial-scan__<case-id>.md
```

完整通过的每个采集 Scenario 都会冻结一个 `capture_case_id`。基础流程是：运行采集 → 自动生成图文 Markdown → 用户自行阅读或上传。AI 润色、自动发布及 Wiki 审阅均为后续可选操作。该 ID 只用于同一次提交的重复点击或结果未知后的重试；历史案例、标题和相似内容不会阻止用户明确选择的上传。

## 发布结果含义

本节解释远端工作流状态，不解释测试是否通过。普通 `publish` 成功返回 `uploaded`；
下列解析和 Wiki 状态需要显式查询或审阅，不能从上传成功推断。

| 状态 | 含义 |
| --- | --- |
| `uploaded` | 当前提交文件已上传且远端字节回读一致；CLI 成功退出，不要求 Wiki 验收 |
| `upload_outcome_unknown` | 请求可能已被接收；保留恢复记录，只读核实，不自动重传 |
| `verification_pending` | 已接收且已取得文档 ID，但文件回读暂时不可用；不是未上传 |
| `not_submitted` / `upload_rejected` | 尚未发出请求或服务器明确拒绝，与结果未知分开报告 |
| `processing` | 文件已回读，但 WeKnora 仍在解析 |
| `processing_failed` | 文件接收或字节校验可能已完成，但远端处理失败；查看分阶段字段，不当成文件未上传 |
| `wiki_pending` | 解析完成，但 Wiki 还未稳定生成 |
| `wiki_review_required` | 可审阅当前 Wiki；尚未接受 |
| `retirement_pending` | 新版已接受，旧版删除任务尚未完成 |
| `accepted` | 当前文件、远端原始字节和当前 Wiki 审阅均已确认 |

文件上传成功不等于 Wiki 验收成功。普通 `publish` 不查询 Wiki；显式 `status`、审阅或接受操作才检查 Wiki。标签处理失败时，`tagging_status` 为 `pending`，不改变上传结果。上传结果未知时只按同一工件恢复，不扫描历史案例或生成新身份来绕过未知结果。

结果分别提供 `upload_outcome`、`verification_status`、`tagging_status` 和 `processing`。文件已接收但字节校验未完成时，不报告已核验成功；标签超时不抹掉上传事实，解析或摘要失败也单独显示。主解析 `completed` 不代表每张图的 OCR、图注或 Wiki 均成功。

## 查询状态与结果未知

输入必须仍是原服务器、目标库和同一提交字节的文件。查询已提交工件时执行：

```powershell
python -B -m autowork_core.knowledge status --markdown "C:\path\case.md" --kb "目标知识库"
```

发布器在发送请求前就保存恢复记录，取得远端文档 ID 后立即保存，不等全部步骤成功才留回执。记录位于 `artifacts/knowledge-publications/`，绑定服务器、库、案例身份和本次实际字节，不保存 API key。存储失败会停止后续远端写入，已经接收的事实和已取得的 ID 不当作未上传。

`status` 不上传文件、不打标签、不改写本地记录。已有 ID 时核验该文档；结果未知且没有 ID 时，只读查找记录目标下身份和字节均匹配的唯一原提交。无法核实或存在多个候选时保持未知或报冲突，不发第二次上传。没有恢复记录时仍返回未找到，不能据此断言远端不存在该文件。

用户明确继续时，重新执行同一文件和目标库的原 `publish` 命令即可续办。它复用记录和文档 ID，已上传的只继续核验或补标签；未知提交无法确认时仍停止，不盲目重传。不要为恢复修改所选文件、重建案例或更换身份。只查看解析状态的 `processing-status` 保持轻量，只读报告记录和处理事实，不执行完整核实或推进发布。

`capture_case_id` 表示采集来源，回执同时区分服务器、目标知识库和提交字节。同一文件换库，以及原文和润色副本分别上传，均允许独立提交；远端文件名包含工件摘要与采集 ID。同一工件重试复用已有回执。历史回执不自动重写。

## 审阅和清理

这三项操作不是上传的隐含后续步骤，也不要求普通本地采集任务执行。分别核对各自
输入与结果，不能用 `accepted` 反推本次产品场景已通过独立业务验收。

| 操作 | 必要输入或条件 | 成功结果 | 不会执行 |
| --- | --- | --- | --- |
| `accept` | 当前文件、目标库及绑定当前 Wiki 版本的审阅 JSON | 记录当前审阅被接受 | 删除任何本地或远端文件 |
| `retire` | 当前案例已接受，且明确选择其被替代旧版 | 提交并跟踪旧版退役 | 删除本地采集目录 |
| `clean` | 明确指定的已结束 Run，全部案例已接受且无旧版待退役 | 清理该 Run 的本地采集目录 | 广泛清理其他 Run |

审阅 JSON 必须绑定当前服务器、知识库、文档 ID、文件 SHA256 和 Wiki 页面版本。页面变更后旧审阅失效，必须重新审阅。

`accept` 只记录验收，不删除任何本地或远端文件。清理是独立操作：该 Run 必须已结束、其中每个案例均为 `accepted`、没有旧版待退役。上传或解析完成时不会自动删除任何本地证据。

明确确认需要退役已接受案例的旧版时，才执行：

```powershell
python -B -m autowork_core.knowledge retire --markdown "C:\path\case.md" --kb "目标知识库"
```

`retire` 返回 `retirement_pending` 表示删除任务已被远端接受但尚未确认消失；它不会删除本地文件。

## WeKnora 工程案例库分块与 Wiki 正交编译规范

当目标工程案例知识库开启 WeKnora `v0.8.3` Wiki 功能时，导出器的 7 章元模型与知识库的分块/Wiki 配置按以下通用规范协同工作（零业务词硬编码，对任意 Feature、Scenario 与页面组件通用）：

1. **分块与后台并发配置**：
   - `enable_parent_child: true`、`parent_chunk_size: 32768`、`child_chunk_size: 384`、`chunk_overlap: 64`、`strategy: "auto"`，分隔符包含 `["\n\n", "\n", "。", "！", "？", ";", "；"]`。
   - 建议关闭文档问题生成（`question_generation_config.enabled: false`），避免入库时数十个问题生成请求与 Wiki 引用分类并发争抢大模型网关配额。
2. **四类正交 Wiki 节点路由（`extraction_instructions`）**：
   - **需求实体（`entity/<需求编号>`）**：依据第 1 章 `Feature 需求标识` 提取，仅承载第 1–2 章需求身份、Gherkin 契约、涉及组件导航及第 6 章开头的 `S01–Sxx` 来源文件索引表。
   - **主业务场景概念（`concept/<场景名>`）**：依据第 2 章 `Scenario` 提取，承载第 2–3 章步骤概览、变量读写与断言流转、关键截图证据，以及第 6 章 `Bdd/steps/` 下的全部 `Step 1–N` 实现源码。
   - **页面组件实体（`entity/<类名全小写>`）**：依据第 1 章 AST 自动标注的三类角色分别生成描述边界：
     - `界面视图类 WindowView`：承载第 4 章在该视图上执行的全部 `Fxx` 截图与动作链，以及第 6 章唯一归属该类的 `WindowView` 类定义与 YAML 定位器；
     - `窗口容器类 WindowPage`：仅承载唯一归属该类的 `WindowPage` 类定义、根窗口 YAML 定位器与子视图挂载关系；
     - `静态调用辅助类`：承载第 3.3 节记录的静态方法调用与协同职责。
   - **专项验证概念（`concept/<验证主题>`）**：承载第 3.2/3.3 节与第 4 章对应的参数比对表、断言逻辑及验证截图，不关联任何 Python/YAML 源码块。
3. **编译期冲突剔除铁律（`content_instructions`）**：
   - **全局剔除第 5/7 章底层校验表**：凡 `<new_information>` 中出现第 5 章精确追溯索引表（`#a-`、`Txx`、`Qxx`、`Rxx` JSON）或第 7 章 SHA256 指纹表，均作为底层校验附录直接丢弃（`REJECT`），不写入任何 Wiki 页面。
   - **Step 函数源码排他归属**：仅主业务场景概念页允许保留 `Bdd/steps/` 下的 `@given/@when/@then` 步骤实现代码块；任何页面组件实体页、需求实体页或专项验证概念页遇到 `def step_...` 代码块均强制丢弃。
   - **Page/View 与 YAML 1 对 1 归属**：页面组件实体页仅保留首行 `# Sxx: <本页类名>` 匹配的自身类定义与直接绑定的 YAML 定位器代码块。

## 后续演进与扩展方向

在当前“运行证据采集 → 7 章确定性导出 → WeKnora Wiki 正交编译 → AI 脚本生成”闭环基础上，面向大规模案例库与持续迭代的 5 项演进方向（其中**方向 1 已落地生效**，方向 2、3、4、5 为概念规划）如下：

| 演进方向 | 改造前的痛点 | 改造后的机制变化 | 带来的实际提升（工程收益） |
| --- | --- | --- | --- |
| **1. 非 UIA 辅助类与自定义页面方法的一等公民观测（已落地）** | 只自动拦截 `BasePage` 的 25 个内置 UIA 动作；模拟器（如 `EarthPlatformSimulatorPage.move_to_horizontal`、`scan`）只靠静态 AST 扫出代码行号，**在运行时间轴里是断层的**，不知道是在哪个 UI 动作前后执行的、传了什么动态参数、返回了什么。 | 复用 `BasePage.__init_subclass__` 与 `observe_subclass_actions`，对 `Bdd.` 命名空间下的 `BasePage`/`WindowPage`/`WindowView` 子类（或显式声明 `observe_custom_actions = True` 的类）上的公开业务方法自动挂载 `_observed_method(custom_phases=())`：不触发桌面截图，但完整记录调用时点、实参、返回值、所属 `.py`/`.yaml` 快照并写入 `observations.json`，同时自动从第 3.3 节静态缺口表中剔除已观测方法，并在第 1 章与第 6 章归入 `辅助/模拟器调用类`。 | **消除混合场景的时序盲区**：Wiki 中的辅助组件页（如 `EarthPlatformSimulatorPage`）不再只是静态行号列表，而是完整的时序调用链与类定义快照；下游 AI 生成新场景时，能精确复现“先点 `GO_button` → 调 `simulator.scan()` → 再等 `Repeat_button` 可用”的跨系统协同逻辑。 |
| **2. `Scenario Outline` 代表样本筛选与数据驱动知识提炼（规划中）** | 跑一个含多行 `Examples` 的 `Scenario Outline` 会生成多份独立案例文档（每个执行样本一份），若不加筛选全部上传会导致知识库分块膨胀；而若把多个样本轨迹强行塞入单篇文档又会在 $N \ge 5$ 时撑爆上下文窗口。 | 保持每个执行样本独立成篇（1 次 Scenario 执行 = 1 份 `.md`），后续规划在发布/采集侧支持仅挑选代表性样本入库，或仅提取跨分支新增定位器知识。 | **保持单文档体量恒定可控**：避免多组 `Examples` 轨迹撑爆单篇 Markdown 与 WeKnora `32,768` 字符摘要窗口。 |
| **3. 基于第 7 章 `SHA256` 的知识陈旧度（Staleness）自动巡检（规划中）** | 案例第 7 章虽然记了 `S01–Sxx` 源码和 YAML 的 `SHA256` 指纹，但本地改了某个定位器或重构了 `Page` 类方法名后，**没人知道知识库里哪几篇案例已经过期**，导致 AI 继续照着旧 Wiki 生成已被废弃的定位器或方法调用。 | 新增纯本地秒级巡检命令（对比知识库案例第 7 章的 `S01–Sxx` 指纹与当前工作区 `Bdd/` 下的文件哈希）：<br>1. 仅源码/YAML 注释或格式微调、不影响运行证据时，直接用原 `observations.json` + 最新源码秒级重建并更新入库，**无需重跑耗时的真机 UI 测试**；<br>2. 关键定位器或动作逻辑已变更时，精确告警需重跑采集的场景清单。 | **知识库从“一次性静态快照”变成“跟代码同步演进的活资产”**：彻底解决测试代码重构后知识库滞后腐烂的问题，日常维护成本降到最低。 |
| **4. 截图目标控件的视觉高亮框（Visual Bounding Box，规划中）** | 虽然 `observations.json` 里已经记了目标控件的屏幕坐标 `coords` 和矩形框 `rectangle`，但导出的 `F01–Fxx` 是无标注原图。遇到密集图标、无文字单选框（如 `RadioButton[0]` 体位小图标）或下拉项时，**人眼和视觉大模型（VLM）都很难看清这一步到底点在了哪**。 | 已在运行期记录目标控件的屏幕矩形 `rectangle`；后续规划在保持原始截图字节指纹的前提下，按需支持目标区域视觉定位提示。 | **提升密集无字控件的可读性**：便于审阅与视觉模型识别焦点控件。 |
| **5. 成功基线案例与回归失败现场的自动 Diff 诊断（规划中）** | 目前通过案例只用来往知识库里存，而平时回归测试跑挂了产生的失败 `observations.json` 只能人工翻日志和截图排查，**知识库里的“成功基线”没有反哺给日常排障**。 | 当某个场景回归测试失败时，自动拉取知识库中同 `Case Key` 的通过基线案例，与本次失败的 `observations.json` 做结构化逐动作比对：自动定位从第几个动作（`Step.Action`）开始出现返回值偏离（如参数读数不一致）、控件属性变化（`Txx` 找不到或置灰）或画面异常（对比失败瞬间截图与基线 `Fxx` 截图）。 | **打通“知识采集”与“故障诊断（`report-merge`）”两大闭环**：知识库不仅能帮 AI **写新脚本**，还能在老脚本跑挂时充当“黄金标准答案”，直接秒级给出根因定位结论（是测试数据变了、UI 改版了、还是模拟器没响应）。 |
