# 5. 故障排查

本文说明控制台输出、日志、截图、OCR/PIC 失败、依赖冲突和常见脚本问题怎么排查。

## 控制台输出

本地调试推荐参数：

```python
verbose=True
formatter="progress2"
```

效果：

- Behave 启动诊断显示在控制台最上方。
- 中间只输出简洁进度，不输出完整 `Feature/Scenario/Step` pretty 文本。
- 框架 loguru 日志照常输出。

启动诊断示例：

```text
Using CONFIGURATION DEFAULTS:
...
USING RUNNER: behave.runner:Runner
Supplied path: "...Bdd/test_features/test_debug.feature"
Primary path is to a file so using its directory
Trying base directory: ...
```

这段来自 `--verbose`，用于确认 Behave 实际加载了哪个 feature 和 base directory。

如果控制台中间出现：

```text
Feature: calc
  Scenario Outline...
  When...
  Then...
```

说明 formatter 还是 pretty。把本地 runner 改成：

```python
formatter="progress2"
```

如果需要核对 Behave 原始步骤顺序，可以临时改成 `formatter="pretty"`。如果只想保留框架日志和最终结果，改成 `formatter="null"`。

## 日志和产物

| 内容 | 位置 |
| --- | --- |
| loguru 日志 | `artifacts/logs/logs.logs` |
| 普通失败截图 | `artifacts/screenshots/` |
| OCR 失败调试图 | `artifacts/screenshots/ocr_*.png` |
| 图片失败调试图 | `artifacts/screenshots/pic_*.png` |
| 失败录屏 | `artifacts/recordings/` |
| Feature Step Recorder 会话 | `artifacts/recording_sessions/` |
| Recorder 历史 Run 索引 | `artifacts/recording_sessions/catalog.json` |
| 已确认能力索引 | `Bdd/ai/knowledge/capabilities/catalog.json` |
| 报告输出 | `artifacts/reports/` |
| Spark HTML 报告 | `artifacts/reports/autowork-report.html` |
| Spark JSON 原始数据 | `artifacts/reports/autowork-report.json` |

失败分析顺序：

1. 看控制台最后的错误和步骤名。
2. 看 `artifacts/logs/logs.logs`，确认 locator、root、timeout 等参数。
3. 看普通失败截图。
4. 如果是 OCR/PIC，优先看对应失败调试图。
5. 打开 Spark 报告确认失败步骤、截图附件和被阻断的后续步骤是否符合预期。
6. 确认截图区域是否正确，再调整 locator 或参数。

失败截图保存失败不会再中断报告生成。报告会在失败步骤的 `errorDetail` 中追加截图保存错误，常见原因是截图工具瞬时失败、屏幕句柄异常或路径过长；框架会自动缩短截图和录屏文件名以避开 Windows 传统路径长度限制。

## Recorder 找不到历史录制

1. 从调试器打开“Recorder 工作台”并切到“历史”，确认顶部录制根目录指向实际 `recording_sessions`。
2. 检查 `catalog.json` 是否存在对应 Session ID 和相对路径。
3. 确认 Run 使用当前 Session schema、Annotation Model 和 Projection。其他协议Run不会被
  读取、升级或迁移；不要手工复制根级派生文件或改写版本号。

## Recorder 录制开始时窗口还不存在

保持高级设置中的窗口模式为 `auto`，不需要选择占位窗口。点击录制后再启动应用或执行触发窗口出现的操作；第一次业务操作窗口会成为主窗口。同进程和子进程窗口自动纳入。

如果新窗口属于无关进程，状态条会提示“待确认窗口”，事件会保留到审阅阶段，不会静默丢弃。需要完全禁止其他进程时才使用 `strict` 并提前选择窗口。

## Recorder 窗口在 Step 中关闭

`window_closed_during_take` 不等于采集失败。Reconciler 无法由生命周期证据自动判定时，在一次 Decision Pack 中确认：

- 预期关闭：可生成关闭操作、`wait_not_exists` 或不存在断言。
- 流程切换：保留动作，不生成关闭断言。
- 意外关闭：补录当前 Step。

自动发现但没有有效录制动作的次要窗口即使在 F10 前消失，也只保留原始生命周期
证据，不显示该提示。主窗口、显式选择窗口或包含有效动作的窗口关闭仍需确认。

`capture_error` 只是采集阶段记录，不再自动等于重录。先查看该问题的 `recovery`：动作/事件和任一种可视证据仍在时，AI 会通过关键帧、联系表或视频恢复并让用户确认；只有 `recovery.hard_blocker=true` 才最小补录当前 Step。

## Recorder 证据问题如何处理

普通用户只需按界面处理录制内容，不需要理解内部证据协议或下面的诊断code。先打开
“Recorder 工作台”→“历史”→目标任务→审阅，在“问题与处理”页签中选择问题：

1. 查看具体Step、录制版本、操作、窗口和录制画面。
2. 点击“打开证据”查看对应录制画面。
3. 按提示执行“定位到录制内容”“检查录制”“交给 Copilot”或“补录当前 Step”。

普通用户到这里即可；下面内容仅供维护者定位框架问题。

### 维护者诊断

维护者可结合内部code、`take.json`、recovery库存和证据路径继续定位。默认审阅UI不会
显示原始validator消息、repair steps或下面的协议术语。

常见 code：

| code | 具体含义 | 修复 |
| --- | --- | --- |
| `capture_error` | Hook、视频、截图或保存发生异常 | 先看 recovery 库存；有动作+媒体则 AI 恢复，无核心证据才补录当前 Step |
| `tree_not_comparable` | 主窗口前后树不是可比较的一组证据 | 操作类 Step 可用动作+媒体恢复；断言缺结果证据时才最小补录 |
| `no_recorded_actions` | 没有归一化动作 | raw events + 可视证据存在时由 AI 恢复，否则最小补录当前 Step |
| `orphan_mouse_boundary` | 从半次点击开始 | 定位 event，排除孤立边界或重录完整点击 |
| `external_process_action` | 动作来自范围外进程 | 排除噪声，或用 auto/正确窗口范围重录 |
| `weak_target_quality` | 只命中容器或未解析目标 | 看事件截图；目标错则重录，目标对则在 Decision Pack 中确认 fallback |
| `fallback_ocr` / `fallback_pos` | 结构定位不足 | 优先补 Child/XPath，否则在 Decision Pack 中确认接受 fallback |
| `provisional_window` | 无进程关系的新窗口 | Reconciler 自动消解，或在 Decision Pack 中标记业务/无关 |
| `window_closed_during_take` | 窗口在 Step 中关闭 | Decision Pack 确认预期关闭、流程切换或意外关闭 |

录制画面可用 `+`、`−`、`适应`、`100%` 或 `Ctrl + 鼠标滚轮` 放大查看。动作角色和生成职责由Copilot处理；内部协议仅供维护者参考，见[维护/3.Recorder设计](维护/3.Recorder设计.md)。

判断是否真的需要补录时，以 `recovery.hard_blocker` 为准，不要仅根据review code。
Copilot恢复优先读取结构化动作/事件和静态图，必要时才按`video_ms`抽取视频帧；用户只
确认媒体无法证明的业务含义。

请求准备时会自动修复可再生文件，报告位于 `ai/repairs/latest.json`；AI 恢复判断位于 `ai/recovery/<request-id>.json`。如果 `artifact_repair.unrecoverable` 非空，先查看具体缺失文件；只有原始事件和所有可视证据都无法使用时才补录。

## Recorder Copilot任务没有自动更新

正常情况下，保存Step、切换用于生成的录制版本或修改录制内容后，状态栏会先显示
“正在更新Copilot任务”，随后显示“Copilot任务已自动更新”。普通用户只需等待主按钮
恢复；维护者需要排查时，最新内部指针位于：

```text
<run>/ai/requests/index.json
```

排查顺序：

1. 确认当前Step状态为“已完成”且已有用于生成的录制版本。
2. 查看状态栏中的自动更新异常；点击“重试准备”执行完整重试。
3. 检查 `ai/repairs/latest.json` 的 `unrecoverable`。
4. 不要修改旧Request；它是不可变事实。`stale`位于`ai/workflow/<request-id>.json`，
  应由系统准备最新任务。
5. 最终始终通过审阅页当前主操作获取最新命令，不要从历史文件夹随意选择request。

界面不会直接要求普通用户理解以下内部状态；排查日志或Prompt返回时按对应用户动作处理：

| 状态 | 处理 |
| --- | --- |
| `stale` | 返回工作台“修复与生成”页复制最新请求 |
| `needs_adjustment` | 界面显示“需要确认业务问题”；一次回答白话问题，技术实现仍由Copilot负责 |
| `forensic` | 界面显示“Copilot会自动核对录制事实”；用户无需处理Evidence或Plan术语 |
| `blocked` | 界面显示具体缺失证据和“校正或补录”；只处理对应Step，不能用回答代替真实证据 |
| `stale_during_generation` | 生成期间证据发生变化，丢弃本次结果并复制最新请求重新生成 |

## AI 技术修复耗尽后如何重新开始

如果当前Job的`validate-job-implementation`仍返回`invalid`，且允许的技术修复次数已经耗尽，不要保留
`running`事务，也不要手工删除locator、package marker或lease文件。通过工作台终止当前Job；仅在维护诊断需要时，使用当前Job的claim与epoch运行：

```powershell
python -m autowork_core.utils.debug_tools.recorder.generation_workflow abort-job <report-path> --claim-id <claim> --expected-epoch <epoch> --reason "implementation repair attempts exhausted"
```

成功时返回`status=aborted`。系统会：

- 把当前AI可编辑草稿归档为Transaction目录下的`aborted-implementation.zip`；
- 将AI与系统拥有的Manifest目标恢复到`prepare`前状态；
- 把materialization journal标记为`rolled_back`；
- 清除active transaction并释放file lease；
- 将当前Job发布为终态`failed/aborted`；需要再次生成时重新admission创建新Job。

如果发现范围外改动、baseline被篡改、lease身份不匹配或回滚不完整，abort会失败关闭并
保持`running`或`aborting`。修复瞬时问题后可使用同一Job claim/epoch重跑abort；进程在lease释放或Workflow
发布期间中断时，当前Job的恢复路径会先幂等完成旧abort。没有
`generation-baseline.json`的历史running事务不支持安全abort，只能保留为审计记录；
不能手工篡改report、baseline、journal或lock。

F9检查错误时，在当前录制的“F9检查”中选择原记录并修改业务检查、关系或
Feature/Examples/Data Table来源；保存后系统自动准备新任务。若该F9来自补录，
修订会写回原补录片段；不需要时定位到对应操作并选择“忽略错误动作”。

## Recorder 动作截图不对应操作

先在“录制内容”中选中操作，并切换`操作前`、`操作后`、`差异`和`视频帧`：

- `操作前` 应对应鼠标按下前，或键盘序列首键按下前。
- `操作后` 默认使用提交后的 settled/probe/immediate 最佳候选，不应再显示首个按键画面。
- `差异` 显示同一动作 before/after 的增强像素差异图；原图不做覆盖或修改。
- `视频帧` 按动作 `commit.video_ms` 抽取，只用于静态候选不足或需要连续上下文时。

维护者需要进一步诊断时，检查用于生成的录制版本目录下的`action-media.json`：

| 现象 | 含义与处理 |
| --- | --- |
| `source: boundary_capture` | 新版动作边界帧，按 `stage` 和 `latency_ms` 判断时机 |
| `source: event_screenshot_fallback` | 旧录制缺少动作帧，界面会明确回退；需要精确结果图时重新录制 |
| `stability.status: visual_still_changing` | probe 到 settled 仍有明显变化；结合 context 或按 `video_ms` 抽帧 |
| `before` 或 `after` 为 `null` | 查看 `events.jsonl.details.frame_capture_errors`，并检查 `frames/` 是否存在对应 PNG |
| validator 报“动作媒体不存在” | `action-media.json` 引用的帧或 `action-contact-sheet.png` 已缺失；先准备请求触发派生产物修复，原始证据不足时才补录 |

`screenshots/before.png` 和 `screenshots/after.png` 是整个 Step 的边界，不是单个动作的结果图。不要用它们判断某次点击或输入是否生效。

## AI 项目经验不正确或没有生效

如果 AI 复用了错误经验，先在“修复与生成”页对对应结果重新提交“已修改”或“不采用”
反馈并说明原因。项目经验只提供建议，不应覆盖当前代码、当前录制证据或本次明确说明。

### Portable Knowledge

Portable Knowledge属于当前项目仓库，保存在`Bdd/ai/portable-knowledge`。框架更新不会
复制或覆盖该目录；记录被篡改、越界或格式无效时，对应知识操作会直接报错并停止。

需要检查可移植知识时运行：

```powershell
python -B -m autowork_core.utils.debug_tools.portable_knowledge audit
```

需要检查本地 Knowledge Store 时运行：

```powershell
python -m autowork_core.utils.debug_tools.recorder.knowledge_audit artifacts/recording_sessions
```

这些审计命令不修改代码或知识。若需要同步、隔离、恢复或处理中断操作，不要手工编辑
内容寻址文件；按 [资产迁移与知识维护](维护/5.资产迁移与知识维护.md) 的审批流程执行。
协作反馈入口见 [维护者指南：手动协作复盘](维护/1.维护者指南.md#手动协作复盘)。

## 宿主设备或供应商集成不可用

框架只调用`Bdd.application`提供的项目生命周期Hook，不解释产品资源标签、设备协议、
供应商SDK或COM注册方式。此类错误应按当前宿主项目的集成文档排查；不要把产品注册命令、
固定路径或设备恢复步骤添加为框架通用处理。

## ffmpeg 录屏不可用

连续录屏固定使用项目内置 ffmpeg，默认路径：

```text
resources/ffmpeg/current/bin/ffmpeg.exe
```

如果开启 `record_mode="failed"` 或 `record_mode="all"` 后没有生成 mp4，先检查：

```powershell
resources/ffmpeg/current/bin/ffmpeg.exe -version
```

常见原因：

| 现象 | 处理 |
| --- | --- |
| 日志提示 `ffmpeg 不存在，录屏已跳过` | 把 `ffmpeg.exe` 放到默认路径，或配置 `RECORD_SETTING.FFMPEG_PATH` |
| 日志提示 `ffmpeg.exe 不是有效 Windows 可执行文件` | 检查路径是否指向真实 Windows 版 `ffmpeg.exe` |
| mp4 文件为空 | 查看 `artifacts/recordings/ffmpeg_*.log`，确认 gdigrab 是否能抓到当前桌面 |
| 视频黑屏或没有目标窗口 | 确认不是锁屏、UAC 安全桌面或不可捕获的远程桌面会话 |
| 录错屏幕 | 调整 `RECORD_SETTING.MONITOR_INDEX`，`1` 通常是主屏幕 |
| failed 录屏太短 | 调大 `BUFFER_SECONDS`，或调小 `SEGMENT_SECONDS` 提高时间精度 |
| 文件太大 | 降低 `FPS`、提高 `FFMPEG_CRF`、调低 `MAX_WIDTH` 或缩短 `BUFFER_SECONDS` |

`failed` 模式使用 ffmpeg 分片滚动缓存，临时分片位于 `artifacts/recordings/.recording_segments/`，场景结束后会自动清理。ffmpeg 只负责连续录屏；OCR、PIC 和失败截图仍使用 mss。

## 路径和导入失败

正常用例运行推荐从项目根目录使用模块方式：

```powershell
python -m Bdd.local_runner
python -m Bdd.runner
python -m Bdd.debug_tools
```

如果在 VS Code 中右键运行或调试深层文件，出现：

```text
ModuleNotFoundError: No module named 'config'
ModuleNotFoundError: No module named 'autowork_core'
```

按以下顺序检查：

1. 在多根工作区中，`bdd_autowork` 是否是独立 workspace folder，而不是宿主下的普通嵌套目录。
2. 是否已执行 `Developer: Reload Window`。
3. 是否关闭了旧终端并创建新终端；`terminal.integrated.env.*` 只在终端创建时注入。
4. 当前文件是否使用分配给 `bdd_autowork` 文件夹的 Python 解释器。
5. `.vscode/settings.json` 和 `.vscode/launch.json` 是否仍存在。

不要在每个业务文件中重复插入 `sys.path` bootstrap。工作区配置解决的是导入环境；文件本身如果没有调用逻辑，运行后无输出属于正常行为。

## 声明的资源文件不存在

页面对象中：

```python
class CustomerPage(WindowPage):
  root_locator_file = "customer/window.yaml"
  root_locator = "customer_window"
  data_file = "customer_data.yaml"
```

`root_locator_file`、`locator_file` / `locator_files` 会从 `Bdd/locators/` 查找，
`data_file` / `data_files` 会从 `Bdd/data/` 查找。声明文件不存在会直接抛：

```text
FileNotFoundError: 声明的 locator 文件不存在: ...
FileNotFoundError: 声明的 data 文件不存在: ...
```

处理方式：

- 文件确实需要：创建对应 YAML。
- 页面没有 data：把 `data_file = None`，不要声明 `data_files`。
- 文件名写错：修正 Page Object 声明。
- 子目录资源：声明相对路径，例如 `orders/filter.yaml`。

空 YAML 是允许的，会按 `{}` 处理。

## data 或 locator key 拼错但没有立即报错

资源引用必须带 `$`。不带 `$` 的字符串不会自动查 locator/data：locator 参数按临时 locator，data 参数按直接文本。长期脚本建议使用严格引用：

```python
self.click("$save_button")
self.input_text("$name_input", "$customer_name")
self.assert_ocr_contains("$data:success_message")
```

严格引用规则：

| 写法 | 含义 |
| --- | --- |
| `$name` | 按当前参数语义严格解析 |
| `$loc:name` | 强制 locator |
| `$data:name` | 强制 data |
| `$$name` | 字面量 `$name` |

如果 OCR 文本中的 `$name` 同时命中 locator 和 data，会报歧义；改用 `$loc:name` 或 `$data:name` 即可。

## root 未定义

常见错误：

```text
last_root 还未被定义
locator 引用了不存在的 root
```

原因通常是：

- locator 没有写 `root`，但之前也没调用过 `set_root()`。
- locator 的 `root` 名称拼错。
- root locator 不在当前窗口包或显式加载的 locator 文件中。
- root 引用的不是顶层窗口 locator。

推荐做法：

```python
self.set_root({"class_name": "Notepad"}, name="Notepad_window")
```

或在 locator 中直接引用顶层 root：

```yaml
notepad_window:
  backend: uia
  class_name: Notepad

notepad_editor:
  root: notepad_window
  by: xpath
  value: "//Edit"
```

## OCR 找不到但界面上能看到文字

先看：

```text
artifacts/screenshots/ocr_find_failed_*.png
artifacts/screenshots/ocr_*.png
```

判断方式：

| 现象 | 可能原因 | 处理 |
| --- | --- | --- |
| 图里没有目标文字 | region 截错 | 先修 region |
| 图里有文字但候选里没有 | OCR 漏检 | 调大 `det_limit_side_len`，降低 `det_box_thresh` |
| 候选里有但没有命中 | 匹配模式不合适 | 改 `match_mode` 为 `contains` 或 `exact` |
| 多个相似文字命中错 | index 不对或区域太大 | 缩小 region，或设置 `index` |
| 动态界面识别旧内容 | OCR 缓存复用 | 设置 `ocr_cache_ttl=0.0` 或 locator 覆盖 `cache_ttl: 0.0` |

优先级：先缩小截图区域，再调 OCR 参数。

## 图片找不到但界面上能看到图标

先看：

```text
artifacts/screenshots/pic_find_failed_*.png
```

判断方式：

| 现象 | 可能原因 | 处理 |
| --- | --- | --- |
| 图里没有目标区域 | region 错 | 修 region |
| 模板包含大背景 | 模板不稳定 | 重新裁剪，只保留图标特征 |
| 分辨率或缩放不同 | 模板比例不匹配 | 降低 `threshold` 或尝试 `mstpl` |
| 颜色变化明显 | RGB 匹配过严 | 设置 `rgb: false` |
| 找得很慢 | 截图范围太大或多尺度太细 | 缩小 region，调大 `scale_step` |

## OCR 或图片定位慢

优先配置 region：

```yaml
target:
  by: ocr
  value: Save
  region: dialog_window
```

或者调用时传 region：

```python
self.wait_ocr_text_present("Save", region="$dialog_window", timeout=5)
self.wait_pic_present("save_icon", region="$toolbar_region", timeout=5)
```

不要长期依赖全屏 OCR/PIC。

## 元素存在但点击失败

新Run Result会在错误详情中区分以下情况，而不是都显示为`timed out`：

| 诊断 | 含义 |
| --- | --- |
| `*_NOT_FOUND` | 在预算内始终没有结构候选 |
| `*_STATE_TIMEOUT` | 已找到候选，但未达到visible/enabled/ready状态 |
| `VISUAL_OCR_MISS` / `VISUAL_PIC_MISS` | 指定Region内视觉匹配未命中 |
| `*_BACKEND_ERROR` | UIA/Win32、截图、模型或属性读取发生真实错误 |

Recorder运行摘要会显示目标、Root、等待条件、探测次数、候选数和底层cause；详细报告仍
保留原异常与traceback。诊断用于排障，不会把所有Timeout重新解释成定位失败。

排查顺序：

1. 用 `wait_exists()` 或 `wait_visible()` 确认元素状态。
2. 打开 `draw_outline=True` 看高亮框是否圈中目标。
3. 如果是普通按钮必须等解禁，使用 `wait_enabled()` 或 `click(..., wait_type="enabled")`。
4. 如果目标是 `Text`、`Thumb`、`Custom` 等控件，不要强制 `enabled` 或 `ready`，优先使用默认 `visible` 或显式 `wait_type="exists"`。
5. 如果是 `WindowSpecification`，确认是否能 `wrapper_object()`。
6. 如果 UIA click 不稳定，可尝试 `focus()` 后输入或使用 OCR/PIC/pos 兜底。
7. 如果目标在滚动区域外，先 `scroll_to()`。

示例：

```python
self.click("save_button")
self.click("submit_button", wait_type="enabled", wait_timeout=10)
self.click("scroll_bar_thumb", wait_type="visible")
```

`wait_ready()` 比普通点击默认等待更严格，只在确实要求控件可见且可用时使用。

## root 缓存失效或窗口已重开

顶层窗口 root 首次成功确认后会缓存 handle。窗口关闭重开后旧 handle 可能失效，框架会在取区域、定位或状态等待失败时把 hot root 标记为 stale，并在下一次按原 criteria 重建。

如果仍然频繁出现 root 相关失败，优先检查：

| 现象 | 处理 |
| --- | --- |
| 顶层窗口标题动态变化 | 使用 `title_re`、`class_name`、`auto_id` 组合定位 |
| `set_root()` 后恢复不稳定 | 把顶层窗口写进 YAML locator，使用自动 hot/stale 缓存 |
| Child/XPath root 找不到 | 确认 root 直接引用顶层窗口 locator |
| OCR/PIC 区域不对 | 先确认 region locator 的矩形，再调 OCR/PIC 参数 |

## 文本读取为空

`get_text()` 会依次尝试：

1. `window_text()`
2. `texts()`
3. `get_value()`
4. `legacy_properties["Value"]`
5. `element_info.name`

如果仍为空，可以尝试读取属性：

```python
value = self.get_attr("name_input", "value", default="")
name = self.get_attr("name_input", "name", default="")
```

输入框校验优先用：

```python
self.assert_attr_contains("name_input", "value", "expected_text")
```
