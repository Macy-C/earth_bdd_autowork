# 4. Spark 报告设计
文档哈希（SHA256）：`cd65e22ab93a588286da8d72136bdc990fdaf7fb7ae5ba9a6502fc617b543b81`

目标：做一个类似 ExtentReports Spark 的本地 HTML 报告，但结构和内容完全适配当前 BDD 桌面自动化框架。

2026-10-29 实现状态：按已确认的整页预览接入正式报告，普通报告与合并报告使用同一工作区。
界面约定以“详情工作区（当前实现）”为准；后文早期方案保留设计历史，不作为当前布局或交互要求。
已有报告与原始执行证据不自动重写，新运行或显式纯渲染使用新界面。

## 定位

这个报告不替代 Behave，也不替代底层日志。它是面向测试、开发和业务查看的一页式执行报告。

## 当前实现状态

2026-10-27 起，普通 BDD 执行事实由 RunEvidenceCollector 统一采集，SparkReporter 消费快照生成
现有格式的 JSON/HTML。运行级摘要与生命周期异常单独展示，动作和日志按 Step 展开，
不改变场景通过率或 Run Result 口径。OCR/PIC 图采用显式附件登记，不再扫描目录差集猜归属。
本次采集能力由 Collector.start 单次装配；报告不安装日志或关闭媒体。执行日志封存在本 Run 的
logs/execution，报告与知识导出日志只进入 logs/delivery，不回写 run.json；交付/清理摘要为派生工件。
下文早期 Hook 采集描述以此 owner 切换为准；迁移细节和未验收外部门见
[实施记录](6.运行证据采集与失败诊断实施方案.md#9-2026-10-27-主线实施记录)。

2026-10-28 首版失败诊断已接入，默认关闭。SPARK_REPORT 支持 ENABLED 与内嵌 DIAGNOSIS，
旧布尔写法兼容且不启用诊断。开启后，封存快照 -> 基础报告先落盘 -> 同步诊断 -> 最终报告发布一次。
业务提示词、证据选择和输出校验归 reporting/diagnosis.py，复用 Analyzer/LlmClient，不改变 Collector。

首页场景行展示诊断状态及简短摘要；场景/Example 详情在 Step 前展示“AI 辅助诊断”，包含原因候选、
不确定性、排查建议、可展开证据与单请求预算。引用可打开材料并定位真实 Step，纯场景身份不伪造 Step 链接。
Run 级诊断放顶部独立折叠区，不遮盖正常详情。AI 文本以不可信字符串转义，不覆盖原异常或通过率。
状态包括未分析（数量限制）、完成、证据不足、失败和超时；关闭时不显示空面板、不创建模型连接。

失败详情默认以“失败位置 / 关键差异 / AI 主要判断 / 下一步”为核心。摘要优先取 RuntimeDiagnostic.summary，
不把完整异常/CompiledLocator/Traceback 铺到首屏；旧记录无结构化诊断时使用有界单行摘要。
主判断和下一步先展示一项，完整回答、其他候选/排除项、材料范围及预算折叠；不丢弃原结果。
引用显示“失败步骤 / 异常堆栈 / 动作记录 / 相关日志”等可读名称，机器 ID 只留在悬停和原始详情。
补充材料使用中性披露区而非红色错误块，截图未采集与已采集但未发模型明确区分。

模型输入按派生摘要组织：优先结构化诊断、每步一份有界堆栈，动作异常不重复携带同一堆栈，
省略重复 log_call 和配置转储，保留至多 40 条近期有效日志及具体省略计数。
发给模型的省略清单只列前 12 项并附剩余计数，派生记录仍保存更完整范围；组包结束后重新核对图片预留。
提示词要求主要原因与下一步优先、避免把已排除项混入原因及重复叙述，不将完整源码/控件树自动列为必要缺口。

诊断独立持久化到选中 Run 的 diagnostics/diagnosis.json，图片副本仅在显式许可后生成。
每个失败单元独立请求，默认 60K 估算输入/4096 输出，256K 总窗口中保留安全空间，不累计会话历史。
混合执行的最终报告不保留某次 Run 的根诊断；场景诊断随对应来源复制，新场景结果替换旧诊断。
纯 render 仍只渲染已有数据，不联网。真实模型质量、图片计数及运行延迟尚未验收。

当前 Spark 报告由 `settings.spark_report` / `SPARK_REPORT` 控制，默认启用。运行结束后输出：

```text
artifacts/reports/autowork-report.html
artifacts/reports/autowork-report.json
```

最终交付报告可由多次执行结果手动合并生成，输出到不会被普通运行清理的目录：

```text
artifacts/final-reports/autowork-final-report.html
artifacts/final-reports/autowork-final-report.json
artifacts/final-reports/autowork-final-merge.json
artifacts/final-reports/assets/
```

`autowork-final-report.html` 仍按普通 Spark 报告展示最终有效结果，不显示复跑、flaky 或
尝试次数字段；`autowork-final-merge.json` 只作为内部操作日志，记录 create / merge /
delete 的来源和范围。合并时会把截图、录屏等附件快照到 `assets/`，避免下一轮普通运行
清理 `artifacts/screenshots/` 或 `artifacts/recordings/` 后最终报告断链。

推荐操作流程：先用一次全量运行创建最终报告底稿，之后对失败 Feature 或 Scenario 单独复跑，
再把复跑产生的 `artifacts/reports/autowork-report.json` 合并进最终报告。宿主项目可直接右键
运行 `Bdd/final_report.py`；该入口顶部只保留默认输入/输出路径，具体操作在方法调用里传参：

```python
DEFAULT_INPUT_REPORT_JSON = "artifacts/reports/autowork-report.json"
DEFAULT_FINAL_REPORT_JSON = "artifacts/final-reports/autowork-final-report.json"

def create_final_report():
    return create(DEFAULT_INPUT_REPORT_JSON, target_report=DEFAULT_FINAL_REPORT_JSON)

def merge_final_report():
    return merge(
        DEFAULT_INPUT_REPORT_JSON,
        target_report=DEFAULT_FINAL_REPORT_JSON,
        allow_add=False,
        # 目标不唯一时再填写：
        # feature_file="Bdd/test_features/login.feature",
        # scenario_name="登录成功",
        # example_id="1.1",
    )

def delete_from_final_report():
    return delete(
        target_report=DEFAULT_FINAL_REPORT_JSON,
        # 删除整个 Feature 时填 feature_file 或 feature_name。
        # 删除单个 Scenario/Example 时再填 scenario_name / example_id。
        # feature_file="Bdd/test_features/login.feature",
        # scenario_name="误合并的场景",
    )

def render_final_report():
    return render(target_report=DEFAULT_FINAL_REPORT_JSON)
```

传命令行参数时仍可使用核心入口，例如
`python -m Bdd.final_report merge artifacts/reports/autowork-report.json --feature-file Bdd/test_features/login.feature --scenario "登录成功"`。

合并规则使用 `feature.file` 优先、`feature.name` 兜底定位 Feature；普通 Scenario 使用名称定位；
Scenario Outline Example 使用 Outline 名称加 `exampleId` 定位。合并只替换最终报告中的可见执行结果，
不会在最终 HTML 中增加“复跑后通过”等字段；误操作可用 delete 删除 Feature、Scenario 或单个
Example 后重新 render。

已实现行为：

- 默认打开 Feature 分组执行表。固定表头为“状态 / 编号或类型 / 名称 / 执行结果 / 耗时 /
  失败 Step / 详情”，Feature 父行和 Scenario/Outline Example 子行使用同一组列。
- 所有 Feature 默认收起；所有真实 Scenario/Example 始终显示名称，名称最多显示两行并可
  悬停查看全文。首页“全部”筛选下按通过、需跟进、状态未知、未执行进行逻辑排序，
  同状态内保留原始规格顺序。
- 执行表支持状态筛选、Feature/Case 搜索、逻辑排序、异常优先和耗时优先。排序只调整
  Feature 组；“全部”筛选下子行也按状态逻辑排序。点击子行直接进入对应详情，返回时恢复筛选、
  排序、折叠状态、选中项和滚动位置。
- 测试详情使用两列工作区：Scenario/Example 导航与 Step/证据主体。Feature 通过顶部
  下拉切换，不再占用常驻列；窄屏默认收起 Scenario 抽屉，直接展示 Step 与失败证据。
- 按 `Feature -> Scenario / Scenario Outline -> Example -> Step` 收集执行数据。
- `before_step` 记录 Gherkin step 起始信息，`after_step` 回填状态、耗时、错误摘要、完整错误详情和附件。
- 失败步骤挂载普通失败截图；截图保存失败不会中断报告，会追加到该步骤 `errorDetail`。
- OCR/PIC 失败期间新生成的 debug image 会挂到失败步骤附件。
- 失败场景会挂载 ffmpeg mp4；`failed` 模式挂最近 `BUFFER_SECONDS` 秒，`all` 模式挂完整场景录屏。
- `before_scenario` 开始场景计时；`after_scenario` 在录屏和应用清理完成后记录可读耗时，
  并补齐因前置失败未执行的 Background/Scenario 步骤，统一按原始顺序排序。
- Scenario Outline 会在 `after_feature` 聚合为父级 outline 和多个 example。

当前采集公开 Page 动作边界的 action 和关联日志，并在 Step 详情按需展开；不承诺覆盖任意
Python/第三方调用。文本日志保留在本 Run 的隔离归档，不再依赖公共日志目录。Step 数按每个测试场景的
`Background + Scenario Steps` 统计，使用 Behave `all_steps` 去重，避免 Background 重复。

## 设计原则

1. 定位优先：首页用分组执行表回答异常集中在哪个 Feature、哪个 Case 和哪一段规格范围。
2. BDD 层级清楚：Feature -> Scenario -> Step。
3. 桌面自动化友好：展示 locator、root、OCR/PIC debug 图、截图、录屏、日志片段。
4. 单文件优先：第一版生成一个可独立打开的 HTML 文件，资源用相对路径链接。
5. 不深依赖第三方前端框架：减少维护成本。

## 页面结构

### Feature 分组执行表

```text
Feature 分组执行表
状态  编号或类型  名称             执行结果  耗时   失败 Step  详情
●     F01         Feature A        8/9 89%   02:31  1 个       ›
  ●   S01         登录成功          通过      00:12  —          ›
  ●   E1.2        无效口令被拒绝     需跟进    00:08  1 个       ›
```

显示：

- 项目名、执行时间和总耗时。
- 已执行场景只包含通过、失败和未知 Scenario / Outline Example；Scenario Outline 父项不重复计数。
- 场景通过率为 `passed / (passed + failed + unknown)`，只回答已执行场景中有多少通过。
- Feature 级跳过和 Scenario/Example 级跳过分开计数。Feature 跳过只记一个 Feature，
  但“未执行场景”会按该 Feature 实际包含的 Scenario/Examples 数量统计；详情显示场景数、
  Step 数和原因。
- 不展示“执行完整度”：当前运行数据没有区分永久不在自动化范围和本次临时跳过，计算
  完整度会产生无法可靠解释的比例。
- Feature 父行聚合显示 `通过数/已执行数`、已执行口径通过率、总耗时和失败 Step 数；
  状态环展示 passed、failed、unknown 和 skipped 的真实构成。纯未执行 Feature 的执行
  结果显示 `—`，不产生 `0%` 通过率。
- 子行只编码一个状态：“符合预期”对应 passed；“需跟进”对应 failed；“状态未知”对应
  unknown；“未执行”对应 Scenario/Example skipped。跳过行首页名称显示触发跳过的
  标签文本，例如 `skip` 或 `manual`；详情页仍展示原 Scenario/Example 名称。Scenario 使用
  `S01` 顺序编号，Outline Example 使用稳定 Example 标识。
- 整项 Feature 跳过只显示一个真实子行，名称明确给出计划场景数和跳过原因；父行聚合仍按
  `plannedUnits` 计算未执行覆盖量，不伪造多个 Scenario 名称。
- 表头固定，展开和收起只在父行后插入或移除真实子行，不改变表头与父行几何。少量和大量
  场景使用同一结构；数据增多时在执行表内部滚动，窄屏在容器内横向滚动，不压缩列语义。
- 搜索与状态筛选取交集。命中 Feature 名时保留该 Feature 的全部子行；只命中 Case 时只
  显示命中的子行。状态筛选按 Feature 命中：只要一个 Feature 包含目标状态，展开后仍展示
  该 Feature 的全部子场景。筛选不会临时展开命中组，默认保持收起；底部显示当前 Feature
  数和测试场景覆盖数。

### 总体信息行

```text
Feature: 4  测试场景: 24  已执行: 20  符合预期: 17  需跟进: 2  状态未知: 1  未执行: 4  通过率: 85%  总耗时: 00:12:30
```

“未执行”使用场景数量：单独跳过的 Scenario/Example 数，加上整 Feature 跳过时该
Feature 包含的 Scenario/Example 数。

### 报告导航

左侧只保留稳定的一级视图导航，不放可能无限增长的 Feature 集合：

```text
报告
- 执行场景
- 测试详情
```

### 测试详情（现有布局）

测试详情承接分组执行表中已完成的 Feature/Case 定位，使用规整的两列工作区：

```text
← 返回执行场景    [Feature 选择器] [搜索] [状态筛选]
场景列表                            Step 与证据
当前 Feature                         紧凑场景摘要 / 失败摘要
Scenario 1                          截图 / 录屏 / 调试附件
Outline 2                           Given / When / Then 表格式时间线
  Example @1.1
```

- 顶部 Feature 选择器显示 Feature 名和独立的“需跟进/状态未知”数量；状态筛选会先排除
  不含目标状态的 Feature，再过滤所选 Feature 下的 Scenario/Example。
- Feature 级跳过在详情中显示为单一 Feature 条目，并展示包含场景数、计划 Step 和原因；
  不伪装成多个跳过 Scenario。
- Scenario/Example 与 Step/证据各自在固定视口内独立滚动；桌面端页面不因数据增多产生
  全局滚动。顶部筛选使用稳定网格，避免中文长 Feature 名导致工具区随机换行；窄屏使用
  正常页面纵向滚动，Scenario 列由抽屉按需展开。
- Scenario/Example 搜索覆盖名称、Feature、文件、tag、Step 文本和已有 action 信息。
- 状态筛选位于详情顶部；Scenario/Example 搜索与状态筛选取交集。切换状态时自动选择
  第一个包含该状态的 Feature。
- Scenario Outline 默认收起；从分组执行表点击具体 Example 时自动展开父 Outline 并选中该行。

Scenario 导航行字段：

- Scenario 名
- 类型：Scenario / Scenario Outline / Example
- 状态
- 耗时
- tags
- 错误摘要
- 失败错误摘要

Scenario Outline 建议展示为父子结构：

```text
▶ Scenario Outline 配置绝对延迟重建相位        failed
  Example @1.1 phase=20 mode=Absolute   passed
  Example @1.2 phase=30 mode=Absolute   failed
```

Scenario Outline 父项支持展开/收起，默认收起；搜索时可直接命中 Example。点击右侧 Scenario Outline 汇总中的 Example 行，也会跳转到对应 Example 的 Step 时间线。

左侧标题固定为“场景列表”，当前 Feature 放在弱化副标题中，避免长 Feature 名把面板标题挤乱。
失败的 Scenario / Example 导航行直接显示一行错误摘要。Step/证据主体先展示紧凑场景摘要，
再展示失败摘要、场景附件和表格式 Step 时间线；错误信息分两层：默认显示摘要，点击后展开
完整 traceback 和上下文。

### Step 详情（现有布局与早期约定）

右侧明确展示 Gherkin Step 时间线。Scenario 信息只放在顶部摘要；附件使用无嵌套证据区，
不再放进第二层 Panel。

注意：右侧编号 `1/2/3` 表示 feature 文件里的 Given/When/Then 步骤，不是框架内部的 click/input/assert 动作。通过 Step 默认不展开动作明细；失败 Step 只展示失败的动作，例如：

```text
1  When 选择重建模式并输入延迟       passed
   通过时不展开动作明细

2  Then Phase 展示为 20ms            passed
   通过时不展开动作明细

3  Then Phase 展示为 30ms            failed
   assert_ocr_contains phase_result value=30ms   failed
```

桌面端右侧区域固定高度滚动，不因为步骤或附件过多把整页撑长。窄屏默认直接进入右侧
Step/证据，Scenario 抽屉收起；展开时列表最大高度 360px。

点击普通 Scenario 或具体 Example 后展示：

- Step 时间线
- Step 关键字：Given / When / Then / And / But
- Step 内部动作明细：通过时不展示；失败时只展示失败的 click / input_text / assert / wait 等动作
- 失败堆栈
- locator/root 信息
- OCR/PIC debug 图
- 日志片段
- 附件列表

点击 Scenario Outline 父项时展示：

- Examples 汇总
- 原始 Examples 表格：保留 feature 中的参数列，并追加状态列
- 每行状态
- Examples 表格行可点击，点击后跳转到对应 Example 的 Step 时间线
- 也可以展开中间 Scenario Outline 后，点击具体 Example 查看对应 Step 时间线

## 详情工作区（当前实现）

### 用户路径与呈现

- 概览与详情共用全局导航、标题区和运行摘要，保留首页场景表的统计、筛选、排序、折叠与定位。
- 详情为场景导航、连续阅读区和按需证据查看器；结果、AI 原因候选、步骤与材料直接阅读，
  “本页”导航定位正文区段，并随定位和滚动更新当前位置，不使用固定选中线模拟内容页签。
- 主要命令、次要命令、对象选择、证据引用、只读状态和展开内容分别呈现。
  展开内容使用带箭头、标题及“展开/收起”文字的整行控件，步骤展开也显示明确状态；
  Feature 折叠按钮与场景选择分开，材料与引用均有显式“查看”入口。
- 原因候选、关键不确定性、建议核查和依据分别分组；正文限制阅读宽度。
  长判断和长建议在原位置提供完整内容展开，不要求用户到另一个泛化区块寻找。
  保留原 AI 记录，不用界面派生字段伪造结构化预期或实际值。
- 全报告关注项覆盖失败与状态未知的执行单元；场景前后切换遵循当前筛选范围，Outline 父项不计一次执行。
- 搜索与 Feature、状态筛选取交集；当前对象越出范围时确定性转入匹配项，无匹配则显示空态，
  不保留旧场景或旧 AI 内容。搜索输入、弹层、步骤展开和场景滚动分别保持状态。
- 桌面证据侧栏不遮挡正文；窄屏使用保留场景、步骤来源和记录差异的对话框。
  支持图片缩放、视频回退、日志级别、原始文本、定位步骤、打开原件和关闭焦点恢复。
- 运行结果、场景状态、采集完整性和 AI 状态分别表达。运行问题与运行级诊断在全局摘要中查看；
  AI 生成不等于测试通过，未提供信息不推导为完成，附件登记不等于文件仍可读取。
- 使用石墨导航、浅灰工作底和白色阅读区；蓝色表示交互，测试状态使用局部语义色。
  不使用整块红绿或 AI 专属色带。主要差异正文 14px，常规正文 13px，辅助信息 11～12px。

### 正式接入与边界

- [模板装配](../../autowork_core/runtime/reporting/template.py)为普通报告和合并报告内嵌相同资源；
  HTML 可离线打开，不依赖预览目录、CDN、前端服务或模型请求。
- [样式](../../autowork_core/runtime/reporting/templates/workspace.css)与
  [交互脚本](../../autowork_core/runtime/reporting/templates/workspace.js)按完整交互设计稿接入正式资源，
  不带控件状态样板、演示数据、设计标识或虚构来源；图标使用固定 Lucide 0.468.0，并随 HTML 保留许可。
- 报告 JSON、附件相对路径、Collector、Analyzer、模型提示词、Run Result 发布和合并口径不变。
  旧报告无证据 ID 时只在 UI 派生步骤定位身份，不回写执行事实。
- 验证覆盖普通/合并渲染一致、原始数据与脚本转义、空报告、无 AI、旧格式、Outline/Example、
  运行问题、缺附件、安全路径、长内容展开、区段反馈及桌面与窄屏。静态或模拟检查不替代真实产品执行，
  历史数据重新展示不代表重新诊断。

## 详情工作区早期方案（历史）

以下为早期设计记录，已由上述当前实现取代，尤其不再采用隐藏全局外壳、三个独立内容页签、
所有证据统一模态查看等约定。

### 目标、范围与不变量

正常用户目标是：从概览发现失败，进入具体执行单元，理解实际差异，查看支持证据，
再转到下一条需跟进结果。系统负责保持当前上下文、证据归属、导航状态和可识别的交互；
用户只选择对象、阅读和查证，不需要猜文字能否点击、自己找原始文件或整理多层展开内容。

本方案固定以下边界：

- 保留主页 Feature 分组场景表的列、统计口径、筛选、排序、折叠、来源身份及点击定位行为，
  不重做主页，不因为详情改造改变已执行数、跳过数或通过率。
- 改造详情工作区、控件语言、证据查看和状态展示；不重做 Collector、Analyzer、模型提示词，
  不增加服务、后台任务、前端业务框架或运行时远端资源依赖。
- 使用同一报告 JSON 与既有附件相对路径；UI 派生数据不回写执行事实，不修改 Run Result 发布契约，
  不改业务 Step、断言、locator、媒体采集、保留或 Recorder 协议。
- 旧报告、关闭 AI、没有图片或没有详细动作时仍可用。缺失、未采集、未发送、不可读取是不同状态，
  不能用一个空白占位掩盖，也不能通过现场补采解决。
- 本文是具体设计，不授权重新调用模型、重跑产品、覆盖旧 HTML/JSON 或迁移历史工件。

### 信息架构与页面骨架

报告只有两个层级，不把诊断、日志和附件再发展为多个并列产品页面：

```text
执行概览（保留现有场景表）
  -> 场景排查工作区
       固定上下文栏：返回概览 / Feature与场景 / 执行状态与耗时 / 场景切换
       左侧场景导航：Feature选择 / 搜索 / 状态菜单 / Scenario与Example
       主内容视图：概览 | 执行过程 | 证据
       按需证据查看器：图片、视频、日志、堆栈、诊断引用
```

进入详情时隐藏目前重复占位的一级侧栏，让空间用于排查工作区；通过明确的“返回执行概览”
回到原概览外壳。详情是下钻，不再同时用常驻“测试详情”一级入口表达另一条导航主线。
从文件首次打开仍进入原执行概览，不能默认跳入一个不明来源的场景。

```text
┌──────────────────────────────────────────────────────────────────┐
│ ← 执行概览   calc / 计算相加   失败 · 00:04   ‹  ›  下个需跟进       │
├───────────────────┬──────────────────────────────────────────────┤
│ Feature选择       │ 概览    执行过程    证据 2                    │
│ 搜索场景或步骤    ├──────────────────────────────────────────────┤
│ 状态：全部        │ 当前视图内容                                  │
│                   │                                              │
│ S01 计算相加 失败  │ 选择证据后打开统一查看器                       │
│ S02 ...           │ 不在每个区块重复渲染同一份堆栈或日志           │
└───────────────────┴──────────────────────────────────────────────┘
```

顶部只有一组场景切换操作。Feature 下拉和场景搜索只放左侧导航，不再与标题、返回、
状态按钮一起挤在一个宽工具栏。面包屑表达位置，不把所有文字都做成按钮。
场景文件路径、标签、完整执行 ID、环境参数放在可展开的“执行信息”，不抢占主任务区。

### 场景导航与上下文

- 左侧是选择列表，不是重复的诊断卡片。行内只保留编号、名称、只读执行状态、耗时；
  失败摘要最多一行。名称过长换行或省略，完整内容可通过悬停或焦点说明取得。
- 左侧搜索与状态菜单取交集，作用于当前 Feature 的执行单元；沿用现有搜索数据范围，
  控件标签明确写“搜索场景或步骤”，不新增一个与首页范围不同却同名的全局搜索。
- Scenario 和 Example 是可选择行；状态本身不是按钮。选中行使用浅背景和左侧标记，
  不用仅靠红/绿色表达选中，也不把悬停样式与选中样式做成一样。
- Outline 的展开箭头与选择入口分离：箭头只展开/收起；选择父项显示 Examples 汇总；
  选择 Example 才进入其真实步骤。禁止一次点击同时触发展开、选中和跳页三个动作，
  也不能把按钮嵌套在另一个整行按钮里。
- 从首页进入具体 Example 时展开对应父项并定位到选中行。Outline 父项不伪造一次执行，
  主区显示参数表与每行结果，不显示绑定到某个 Example 的 AI 结论。
- 顶部上一项/下一项按当前可见执行单元顺序切换，不计 Outline 汇总父项。
  “下个需跟进”只选 failed/unknown；无目标时明确禁用，不默默跳回已处理项。
- 返回概览恢复原筛选、排序、Feature 折叠、选中行和滚动位置，不把详情搜索覆盖到首页。

### 三个内容视图

| 视图 | 回答的问题 | 默认内容 | 不在这里铺开的内容 |
| --- | --- | --- | --- |
| 概览 | 本场景结果怎样、差异在哪、下一步看什么 | 场景结果、首个关键失败、AI辅助判断（若有）、关键证据入口 | 全量步骤日志、完整堆栈、模型原始回答、配置转储 |
| 执行过程 | 做过什么、在哪一步出现问题 | 紧凑Step列表、选中步骤的摘要与动作、所属证据入口 | 把每个通过Step的所有内部记录默认展开 |
| 证据 | 有哪些材料、属于哪里、能否查看 | 附件与文本证据清单、类型/所属节点/采集状态、筛选与查看 | 依靠裸路径列表或让用户去日志目录自行查找 |

内容视图用真正的 tabs：选中态、键盘焦点和面板关系一致；不是三段看起来相似的文字。
进入场景默认打开“概览”；用户显式切换场景时保留所选内容视图，避免连续排查反复重选。
“执行过程”视图切换场景后默认定位首个失败Step，没有失败则定位首个实际步骤。

概览的内容顺序固定：

1. 执行结果与关键事实。显示失败位置、结构化关键差异；无结构化诊断时使用安全短摘要。
   场景通过时显示通过结果，不捏造“失败位置”或无意义的空诊断区。
2. AI 辅助诊断（若启用且有记录）。仅主要判断、第一条下一步、可读证据引用；
   推断与确定事实视觉分开，不让模型段落替代执行结果。沿用局部视觉稿的紧凑层次，
   完整回答、不确定性、其他候选与预算按需展开。
3. 关键证据。优先当前失败Step截图、相关录屏和直接引用的材料；图片可显示真实缩略图，
   不裁成无法检验的装饰图。其他材料通过“全部证据”进入清单，不重复复制所有附件。
4. 执行信息。来源、参数、标签、采集完整性和环境白名单等作为低强调的可展开信息。

### Step 与动作的展示规则

Step 列表是规整的执行记录，行内固定为“展开 / 序号 / Gherkin关键字与名称 / 状态 / 耗时 / 证据数”。
名称是内容，展开按钮才是操作；有内容不等于已展开。首个失败Step默认展开，其他Step默认收起，
通过Step可主动展开检查，不能为了简洁删除其已有动作或日志。

- 展开区先展示此Step的短结果，再展示动作表和证据入口，不再重复一组“关键字/状态”卡片。
- 动作表使用实际 operation、outcome、目标摘要（存在时）、耗时和异常摘要；
  False/None/empty 返回类别不是断言失败，不能按字符串或颜色擅自改判。
- 完整错误、日志和识别材料通过统一查看器打开；Step 只保留一份摘要，不与场景概览重复铺全文。
- 展开按钮有明确的展开/收起图标、aria-expanded、悬停和焦点态，支持 Enter/Space。
  没有详情时不显示一个不可用却像可点击的折叠箭头。
- 选中Step和测试失败是不同维度：选中用位置强调，失败用状态标记，不能都刷整行红色。

### 证据清单与统一查看器

清单列为“类型 / 名称 / 所属Step或Scenario / 采集状态 / 查看”，筛选只作用于已有记录。
同一附件按稳定身份显示一次，多个引用指向同一项；不按文件名或修改时间猜归属。
列表至少覆盖已存在的截图、视频、调试图、结构化日志、异常和 AI 输入事实，
无相应记录时如实给出未采集或不可用，不从磁盘扫描补成另一套来源。

桌面端使用按需打开的右侧查看抽屉，不增加常驻第三列；建议宽度 420～560px，
窄屏转为全屏查看。抽屉为有标题的模态 dialog，打开后聚焦、背景不可操作，
Esc或关闭按钮退出并恢复触发控件焦点；关闭不丢失所选场景、视图、Step或滚动位置。

| 材料类型 | 主查看方式 | 必需状态与行为 |
| --- | --- | --- |
| 截图/调试图 | 原比例完整图，默认适配查看区，可缩放和复位 | 显示所属节点和真实区域（若有），不裁图；加载失败可见 |
| 录屏 | 原生视频控件播放已有视频 | 不现场转码/抽帧；无法解码时说明并提供打开原文件 |
| 日志 | 所选节点及其明确子节点的记录，按原顺序显示 | 可筛级别、复制可见文本；UI过滤不等于采集丢失，保留原截断计数 |
| 异常/技术诊断 | 摘要与堆栈分层，代码等宽显示 | 来源与阶段可查，长内容在查看器主体滚动，不撑开整份详情 |
| AI 引用事实 | 展示本次请求实际使用的事实与来源 | 先定位该诊断的evidence清单，不能用短编号推断其他Run或未发送原件 |

“查看”在当前工作区打开查看器；“打开原文件”是显式的次级外部打开动作，两者图标、名称和反馈不同。
不把普通文件链接包装成已有预览，也不在浏览器 file: 限制下声称所有媒体均可播放。
复制失败需明确反馈，仍可选择文本；不为复制能力引入服务或扩大文件访问范围。

AI 引用显示稳定短编号和可读名称，同一诊断中的同一事实编号保持一致。
点击后打开对应材料并突出来源；需要定位执行步骤时切到“执行过程”、展开实际Step并短暂高亮。
仅有场景信息的事实不提供不存在的Step跳转。引用的完整身份保留在数据和辅助说明中，不作为主要标题。

### 控件与视觉规范

原则是不用悬停或反复试点才能知道什么能操作。报告不需要制造一个强主CTA，
但每个操作必须与只读信息有不同的外观和语义。

| 类型 | 统一外观 | 行为与状态 |
| --- | --- | --- |
| 命令按钮 | 明确边界、32px桌面高度、4px圆角；工具用图标或图标加文本 | default/hover/focus/disabled齐全，图标按钮有tooltip和可访问名称 |
| 只读状态 | 小型符号加文字，弱背景，无按钮边框和手形光标 | 不可点击；测试、采集和诊断状态分组命名 |
| 筛选菜单 | 带“状态”等范围标签及下拉标识 | 当前值可见；不是伪装成状态标记的可点文字 |
| 内容tabs | 统一基线与选中指示，不是胶囊按钮堆 | role/aria-selected/panel和键盘切换一致 |
| 可选择列表行 | 轻量行背景、明确选中标记及悬停 | 导航选择与行内展开是两个独立动作，不嵌套交互控件 |
| 展开项 | 整行明确箭头、上下分隔、至少32px命中区 | open/closed可识别，内容有独立内边距，不使用裸浏览器三角加贴边正文 |
| 页内证据引用 | 短编号、低强调链接样式，hover/focus强化 | 定位/打开材料后有明显反馈，不显示整串机器ID |
| 文件操作 | 类型图标和明确动作，例如“查看图片”“打开原文件” | 区分内置查看与外部打开，不让名称成为唯一暗示 |
| 数量/参数/tag | 普通元信息或弱标签 | 无hover、无手形、不伪装成按钮；可筛选时使用独立明确控件 |

统一复用已有 --text、--muted、--line、--info、--pass、--fail 等 token，
禁止新增未定义的 --border 或各处写一套相近颜色。红色只用于实际失败和错误，
不把“下一条需跟进”命令或所有技术材料都染红；AI“已生成”用中性/信息色，不借用测试通过的绿色语义。

字体沿用现有中文友好的无衬线栈，不额外联网加载字体。详情正文 13px、辅助文字 11～12px、
区块标题 14px、场景标题 18px；长文本行距 1.65～1.8，不再用 8～9px 承载排障操作。
空间以 4/8/12/16/24px 为主，页面区块使用完整带状分区或自然布局，不层层套卡片。
交互图标统一选型，优先本地复用成熟图标资源（如 Lucide 子集），不运行时使用 CDN，
也不为界面改造擅自安装工具或切换用户环境。未采用图标库前不能混入多套手绘SVG。
移除默认焦点轮廓时必须有清晰替代；不把“点击这里”“快捷键说明”等教程堆到正常报告内容中。

### 结果状态与特殊情形

| 维度 | 展示位置 | 禁止混淆 |
| --- | --- | --- |
| Scenario/Step执行状态 | 当前对象标题及执行记录 | passed/failed/skipped/unknown口径不变，AI不修改 |
| Run整体结果 | 执行概览的运行摘要；详情可查看运行问题 | 场景全通过而收尾失败仍是Run问题，不制造失败Step |
| 采集状态 | 执行信息和材料范围提示 | complete不等于测试通过，缺图/截断不等于没有执行 |
| AI诊断状态 | AI区标题，例如“诊断已生成/证据不足/超时” | completed不等于原因已被确认，更不等于测试通过 |

关闭AI时移除AI区域，概览仍展示事实和证据；分析失败时显示失败原因并保留原执行结果。
无附件、未采集日志、材料超限、图片未允许发送、已有图片但因预算未发送、文件加载失败分别表达。
模型建议补充某资料不代表该资料是必需验收项。空视图给出对象和范围，不提供无法执行的假按钮。

### 布局、滚动与窄屏

- 工作区可用宽度至少1100px时，左导航约280px，主区使用 minmax(0, 1fr)，不再叠加
  320px导航、620px主区、720px工具栏等相互冲突的最小宽度。
- 768～1099px时，场景列表作为可展开导航抽屉，主内容优先；顶部保留一个有名称的场景选择入口，
  不能只剩“01/02”数字让用户猜。表单和工具栏有稳定轨道，不按视口缩放字体。
- 更窄时改为单列，场景选择与证据查看均可全屏打开；操作命中区至少44px，

只在当前模板的前端状态中增加 activeDetailTab、activeStepId、openStepIds、

### 可操作的验收清单

1. 首页场景表的统计、列、搜索、排序、筛选、折叠和来源定位与改造前一致，返回时位置恢复。

8. Outline父项展开与选择不互相误触，Example参数与状态正确，父项不伪装成一次执行。
9. 关闭AI、诊断失败、无图、无动作、采集不完整和旧报告缺少新增字段时，基本排查旅程仍完整。
10. 场景通过但Run清理失败不制造失败Step，多来源报告不继承某个Run的根诊断，状态计数不变。

13. 同一旧报告JSON可纯render，渲染前后源JSON与原工件字节不变，不请求网络/模型、不重采或重跑业务。

## 和框架的接入点

本节保留早期接入示意，不作为当前采集/收尾调用链。现已由Collector统一采集、runner出口封存，
finish_run_state单次交付；以本文“当前实现状态”和统一采集实施方案第9～11节为准。
界面改造不得据下列历史伪代码恢复Hook重复采集或公共日志初始化。

当前采用单一 `SparkReporter`，不写 Behave formatter，也不把数据聚合和 HTML 渲染逻辑塞进 `environment.py`。

```text
autowork_core/runtime/reporting/
  __init__.py       # 暴露 SparkReporter 和无状态 Hook 分发函数
  spark.py          # 收集数据并渲染 autowork-report.json/html
  templates/
    spark_report.html  # 正式运行时模板
```

`create_run_state()` 根据配置创建本次运行唯一的 Reporter，`environment.py` 通过报告包的无状态函数转发生命周期事件：

```python
@dataclass
class AutoworkRunState:
  # 省略其他 run-scoped 字段
  reporter: SparkReporter | None

def create_run_state():
  return AutoworkRunState(
    reporter=SparkReporter() if settings.spark_report else None,
  )

def before_all(context):
  configure_logging()
  context.autowork_run = create_run_state()
  dispatch_report_hook(context.autowork_run.reporter, "before_all", context)

dispatch_report_hook(context.autowork_run.reporter, "before_feature", context, feature)
dispatch_report_hook(context.autowork_run.reporter, "before_scenario", context, scenario)
dispatch_report_hook(context.autowork_run.reporter, "before_step", context, step)
dispatch_report_hook(
  context.autowork_run.reporter,
  "after_step",
  context,
  step,
  screenshot_path=screenshot_path,
  screenshot_error=screenshot_error,
)
dispatch_report_hook(
  context.autowork_run.reporter,
  "after_scenario",
  context,
  scenario,
  record_path=record_path,
)
dispatch_report_hook(context.autowork_run.reporter, "after_all", context)
```

`before_all` 创建 `AutoworkRunState`，其中的 `reporter`、recorder 和公共 data 模板使用同一 Test Run 生命周期；每个 Feature 会从公共 data 模板 fork 自己的 data 层，locator 由页面显式加载。`dispatch_report_hook()` 接收当前 Reporter：关闭报告时实例为 `None`，否则调用对应 Hook 并隔离报告异常。它没有全局注册表或对象状态，不是 HookManager。目录模式使用一个 Behave Runner：所有 `before_feature` 持续向同一 Reporter 追加数据，`after_all` 统一输出一次报告。当前不提供多 Reporter 插件注册能力。

`SparkReporter` 职责：

- `before_all` 初始化 report store
- `before_feature` 记录 feature
- `before_scenario` 记录 scenario 起始时间
- `before_step` 记录 Gherkin step 起始时间
- `after_step` 记录 step 状态、错误、失败截图附件和截图保存失败原因
- `after_scenario` 记录录屏附件、场景状态和耗时，补齐 missing steps，并按 Background + Scenario 顺序排序
- `after_feature` 聚合 Scenario Outline examples，并计算 feature 状态
- `after_all` 输出 `autowork-report.json` 和 `autowork-report.html`

## 附件策略

推荐：

```text
失败步骤：截图
失败场景：录屏
OCR/PIC 失败：自动挂载 step 执行期间新生成的 debug image
所有失败：logs.logs 链接
```

成功步骤默认不放截图，避免报告膨胀。

截图和录屏文件名会自动缩短并追加 hash，避免 Windows 路径过长导致失败。录屏由项目内置 ffmpeg 执行，产物写入 `artifacts/recordings/`；`failed` 模式通过分片滚动缓存保留失败前最近 `BUFFER_SECONDS` 秒，失败时合并成 mp4 并挂到报告，`all` 模式保留完整场景 mp4。即使截图保存失败，报告也会继续生成，并在失败步骤详情里展示截图错误。

## 为什么不直接用 ExtentReports

ExtentReports 的 Spark UI 很好看，但 Python + Behave 没有足够成熟的官方适配。仿它的布局自己生成 HTML，反而更适合当前框架。
