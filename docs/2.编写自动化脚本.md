# 2. 编写自动化脚本

本文按一个完整用例说明 Feature、Step、WindowPage/View、locator 和 data 分别写什么，
并覆盖常用标签、应用生命周期、Recorder 录制及 AI 生成。安装和运行环境先看
[1.快速开始](1.快速开始.md)。

示例目标：启动记事本，输入一段文本，然后校验输入框内容包含这段文本。

## 调用链

一次用例的推荐调用链：

```text
feature 场景
  -> steps 步骤定义
    -> WindowPage/View 窗口与 locator 所有权、稳定复用方法
      -> BasePage 通用动作
        -> locator / data / OCR / 图片 / pywinauto
```

分层原则：

| 层 | 写什么 | 不写什么 |
| --- | --- | --- |
| feature | 业务场景 | 控件细节、xpath、auto_id |
| steps | 参数解析、场景特有线性动作、业务期望和跨窗口编排 | XPath、坐标、inline locator、直接 pywinauto |
| page_obj | 窗口/locator 所有权和稳定复用业务动作 | behave step 装饰器、仅使用一次的包装方法 |
| locators | 控件定位 | 测试数据 |
| data | 测试数据 | 控件定位 |
| actions | 通用 UI 动作 | 业务含义 |

## 文件清单

完整脚本通常会涉及这些文件：

```text
Bdd/test_features/notepad_debug.feature
Bdd/steps/test_debug_steps/notepad_debug_step.py
Bdd/page_obj/notepad_page.py
Bdd/locators/notepad_locator.yaml
Bdd/data/notepad_data.yaml
Bdd/local_runner.py
```

正式用例把 feature 放到 `Bdd/features/`；本地调试放到 `Bdd/test_features/`。

## 第一步：写 feature

文件：`Bdd/test_features/notepad_debug.feature`

```gherkin
Feature: 记事本调试

  @debug @notepad
  Scenario: 输入文本并校验
    When 在记事本输入预设文本
    Then 记事本内容应包含预设文本
```

说明：

- Feature 只说“预设文本”，不暴露 data key。
- step 里不要出现 `auto_id`、`xpath`、`click` 这类 UI 细节。
- 标签可以用于筛选，例如 `@debug`、`@smoke`、`@orders`。

## 第二步：写 data

文件：`Bdd/data/notepad_data.yaml`

```yaml
notepad_text: Hello BDD Autowork
```

在 Page Object 的 data 参数中传 `"$notepad_text"` 时，框架从 Feature data 读取
`Hello BDD Autowork`。不带 `$` 的字符串按直接文本处理。

## 第三步：写 locator

文件：`Bdd/locators/notepad_locator.yaml`

```yaml
notepad_window:
  top_level: true
  backend: uia
  control_type: Window
  class_name: Notepad

notepad_editor:
  root: notepad_window
  by: xpath
  value: "//Edit[@control_type='Edit']"
```

如果当前 Windows 记事本编辑区不是 `Edit`，可以用调试 GUI 或 Inspect 查实际控件，再改成更稳定的条件，例如：

```yaml
notepad_editor:
  root: notepad_window
  by: xpath
  value: "//Document"
```

规则：

- 顶层窗口 `notepad_window` 不写 `root`。
- 编辑区 `notepad_editor` 写 `root: notepad_window`，避免从全桌面查。
- 长期用例优先把 locator 写到 YAML，不要散落在 Page Object 里。

## 第四步：写 Page Object

文件：`Bdd/page_obj/notepad_page.py`

```python
from autowork_core.page import WindowPage


class NotepadPage(WindowPage):
    root_locator_file = "notepad_locator.yaml"
    root_locator = "notepad_window"
    data_file = "notepad_data.yaml"

    def open_editor(self):
        self.wait_exists("$notepad_editor", timeout=10)

    def input_note(self):
        self.open_editor()
        self.input_text("$notepad_editor", "$notepad_text", use_paste=True)

    def assert_note_contains(self):
        self.assert_attr_contains(
            "$notepad_editor",
            "value",
            "$notepad_text",
            timeout=5,
        )
```

这里有几个重点：

- `root_locator_file` 和 `root_locator` 声明唯一桌面窗口；窗口内复杂子页面使用
  `WindowView` 和同目录 View YAML，规则见下文“窗口与子页面所有权”。
- `data_file` / `data_files` 声明测试数据资源。
- `open_editor()` 是页面内部辅助方法；首次定位 `notepad_editor` 时，框架会从 YAML 懒解析并缓存 `notepad_window`。
- `input_note()` 是业务动作，step 只需要调用它。
- `assert_note_contains()` 用 `assert_attr_contains(..., "value", ...)` 校验输入框值。
- Page Object 使用 `$notepad_text` 严格引用 data；不带 `$` 时按直接文本处理。
- 正式长期脚本不调用 `set_root()`，也不在 Python 中定义 inline locator。`set_root()` 只保留给明确的临时调试脚本。

## 窗口与子页面所有权

桌面对象按真实 UI 所有权划分：

```text
Desktop application
  -> WindowPage       一个稳定的顶层窗口
    -> WindowView     同一窗口内的 Tab、工作区或子页面
      -> component    View 内的复用区域，不拥有窗口 Root
```

- 一个 `WindowPage` 只代表一个顶层窗口。
- 一个窗口包只能声明一个 top-level Root；`WindowView` 共享该 Root，不能声明新 Root。
- 菜单、ComboBox popup 和 Tooltip 等瞬态表面属于父窗口，不单独建 Page。
- 稳定且可独立复用的顶层对话框属于另一个 `WindowPage`。
- Step 负责参数、场景特有线性动作、业务期望和跨窗口编排；Page/View 负责窗口、
  locator 和稳定复用能力。

推荐按业务域和窗口组织：

```text
Bdd/locators/<domain>/<window>/
  window.yaml
  <view>.yaml

Bdd/page_obj/<domain>/<window>/
  page.py
  <view>.py
```

View YAML 中的 locator 只能引用所属窗口的 Root。访问 View 时可用
`active_locator` 检查其已显示：

```python
from autowork_core.page import WindowPage, WindowView


class CustomerPage(WindowPage):
    root_locator_file = "customer/window.yaml"
    root_locator = "customer_window"

    @property
    def details(self) -> "CustomerDetailsView":
        return self.get_view(CustomerDetailsView)


class CustomerDetailsView(WindowView):
    locator_file = "customer/details.yaml"
    active_locator = "$customer_details_panel"
```

第一次出现的流程先在 Step 中通过真实 owner 线性实现；第二个独立场景复用，或用户
明确确认稳定契约后，再提取 Page 方法或 Flow。Flow 只组合 Page 的公开方法，不拥有
locator。后续导航打开的新窗口仍由对应 Page 显式等待。

## 第五步：写 step

文件：`Bdd/steps/test_debug_steps/notepad_debug_step.py`

```python
from behave import then, when
from autowork_core.page import get_page
from Bdd.page_obj.notepad_page import NotepadPage


@when("在记事本输入预设文本")
def step_input_notepad(context):
    page = get_page(context, NotepadPage)
    page.input_note()


@then("记事本内容应包含预设文本")
def step_assert_notepad(context):
    page = get_page(context, NotepadPage)
    page.assert_note_contains()
```

这个示例复用了清晰的记事本能力，因此 Step 只做三件事：

1. 接收 feature 参数。
2. 通过 `get_page(context, NotepadPage)` 获取页面对象。
3. 调用页面业务方法。

## 分层 Step scope

默认仍按 Feature 文件名推导 Step 文件。较大的 Feature 可以在 Feature、Rule、Scenario
或 Scenario Outline 上声明 `@step:`（兼容`@stepfile:`、`@step_file:`、`@steps:`）：

```gherkin
@step:order_status/default
Feature: Update an order status

  @step:order_status/scheduled
  Rule: Scheduled orders

    Scenario: A scheduled order can be activated
      Given a scheduled order exists

    @step:order_status/special
    Scenario: A special scheduled order can be activated
      Given a scheduled order exists
```

每个Scenario的可见定义按`Feature -> Rule -> Scenario/Outline`分层。子层存在完全相同的
matcher签名时覆盖父层；子层没有定义时回退父层；两个不同pattern同时命中同一句Gherkin
会在应用启动前失败。Examples和Background不能声明scope，Outline的scope作用于全部行。

Feature Background仍按标准Gherkin作用于所有Rule中的Scenario；只对某一Rule成立的前置
条件应写成Rule Background。应用生命周期callback只允许放在Feature默认层。

目录可以保持扁平，稳定编号同样合法：

```text
Bdd/steps/order_status/
  default.py
  rule_001.py
  scenario_0001.py
```

编号一旦分配不得因排序变化而重排，删除后也不复用。业务名与稳定编号都只是文件名，
真实执行身份由scope绑定、Step pattern和内容指纹共同确定。

Recorder录制操作事实时不要求先写`@step:`。创建AI Request前，框架读取当前Feature，
确认Scenario、Background、Examples和Step业务结构与录制快照一致，再冻结ScopeBindingV1。
仅补充或调整scope标签不需要重录；Request创建后再改标签会使Request/Plan/Transaction
失效。目标文件不存在时状态为`missing_create_allowed`，表示AI事务可以创建，并不会生成
空占位文件。

首次出现或场景特有的线性流程可以在 Step 中通过所属 Page/View 调用：

```python
page.click("$named_locator")
page.input_text("$named_input", value)
page.wait_visible("$named_result")
```

窗口和 locator 仍由 Page/View 拥有。只有已有方法、独立场景重复出现或用户明确确认
稳定契约时，才把这段动作提取为业务方法或 Flow。正式 Step 始终禁止 XPath、坐标、
inline locator、`set_root()`、直接 pywinauto 和固定 `sleep`。

## Step 匹配与复用

- Step 文本的大小写、标点和空格都会影响匹配。
- `And` / `But` 沿用前一个 Gherkin 关键字类型。
- Definition 中的 `{name}` 是 Behave 参数；Outline 中的 `<name>` 先由 Examples 替换。
- 优先保留一个清晰的参数化 Step，避免同时存在可匹配同一句话的固定文本版本。
- `@step` 可跨 Given/When/Then 匹配，只在业务语句确实不依赖关键字类型时使用。

新增 Step 前先搜索当前 Feature 的 scoped Step 文件，再搜索 `Bdd/steps/` 和对应
Page/View。业务含义不同但文本相同的 Step 可以留在不同 Feature scope；不要为了全局
去重强行共用。未实现的 Step 不得使用 `pass`、`...` 或空返回制造假通过。

正常运行会在启动应用前用 Behave matcher 检查当前 scope。需要无导入副作用的静态
检查时运行：

```powershell
python -m autowork_core.runtime.step_validation Bdd/steps `
  --feature-path Bdd/test_features/example.feature `
  --explain-scopes
```

重点处理 `undefined`、`ambiguous` / duplicate 和 scope error。

## 常用标签

| 标签 | 作用 |
| --- | --- |
| `@maint` | 维护中，最高优先级跳过 |
| `@skip` | 跳过执行 |
| `@rep` | 按框架规则跳过 |
| `@api` | 只运行 API/Step，不启动应用、宿主资源和录屏 |
| `@step:<path>` / `@stepfile:<path>` | 在Feature、Rule、Scenario或Outline声明分层Step文件 |
| `@single:<mode>:<step>` | 仅供本地 runner 单步调试 |

`@maint`、`@skip`、`@rep` 命中后不会启动应用、宿主资源或录屏。自定义标签可直接用于
Behave 筛选；`@single` 的模式和 Outline 行选择见
[1.快速开始：单步调试](1.快速开始.md#单步调试)。

## 应用启动前后的自定义操作

如果操作必须发生在应用启动前、启动命令返回后或应用关闭后，不要把它写成普通
Gherkin Step。框架会在第一个 Step 前启动应用，因此可以在Feature默认Step
文件顶层声明应用生命周期回调：

```python
from autowork_core.runtime.application_lifecycle import (
    after_app_start,
    after_app_stop,
    before_app_start,
)


@before_app_start(tags="custom_key")
def write_startup_file(context, scenario):
    write_file_for_startup()


@after_app_start(tags="custom_key")
def record_started_state(context, scenario):
    record_application_started()


@after_app_stop(tags="custom_key")
def write_finished_file(context, scenario):
    write_file_after_application_stops()
```

在需要执行这些回调的 Scenario 上添加对应标签：

```gherkin
@custom_key
Scenario: 使用自定义启动文件运行测试
  Given ...
```

执行顺序固定为：

```text
before_app_start
  -> 框架启动应用
  -> after_app_start
  -> Scenario Steps
  -> 框架关闭应用
  -> after_app_stop
```

使用时记住：

- 回调直接定义在当前 scoped Step 文件中，可用 `tags=` 限定 Scenario；
- 回调异常会使 Scenario 失败，不会静默忽略；
- auto 模式会在 Step 前执行宿主项目定义的启动就绪门；Step 不重复同一个等待。后续
  业务跳转打开的其他窗口仍由对应 Page 显式等待；
- `after_app_start` 表示启动命令已返回，不替代后续业务窗口等待；
- `after_app_stop` 用于恢复启动前改动，即使场景失败也会尝试执行；
- `attach` 模式没有框架拥有的启停边界，不能使用这些回调。

异常聚合、注册顺序和生命周期实现见
[维护/2.架构设计](维护/2.架构设计.md#behave-生命周期)。

## 可选：录制并交给 AI

录制不是实现Feature的必经步骤。可以直接手写Step/Page脚本；只有需要通过操作证据辅助
AI生成、补录或跨工程传递录制资料时，才使用Recorder。

启动调试工具：

```powershell
python -m Bdd.debug_tools
```

在 Recorder 工作台中：

1. 在“Feature与录制”页选择项目内的Feature目录。首页递归列出Feature、
  Scenario/Examples的录制覆盖、最近导出和真实问题；“无录制”和“—”只是事实，不是待办。
2. Feature未写清但你掌握确定业务事实时，可填写一段“业务补充（可选）”；不要填写
  locator、API、等待或动作类型。
3. 点击“录制选中 Step”，按真实业务流程操作应用。
4. 临时准备操作用`F7`暂停/继续；断言目标悬停后按`F9`。F9自动记录白话检查且不阻塞
  录制；需要时在“F9检查”中补充业务含义、明确检查期望或忽略该检查。
5. `F10`保存本次录制，`Shift+F11`放弃。
6. 在“检查与补录”忽略误录或补上缺失操作；动作类型、角色、binding、merge、locator和
  代码结构由Copilot处理，普通用户没有这些技术编辑入口。原始证据不会被覆盖。
7. Scenario完整后点击唯一的“交给Copilot”，在Copilot Chat运行复制的命令：

  ```text
  /recorder-generate ".../ai/requests/request_xxx.json"
  ```

8. 录制内容不足时界面会说明具体缺什么并返回对应Step检查或补录；生成后才显示“本次生成”，
  成功后可选择“可以使用 / 我已修改结果 / 不采用”供后续复用。

需要跨工程传递时，在同一“Feature与录制”页使用“导出所选录制资料”和“导入录制资料”。
只要Feature至少有一个当前有效录制即可导出，不要求所有Scenario都录制；包会明确显示
实际覆盖数。多选仍为每个Feature生成一个独立包。目标Feature内容不同会直接阻止导入，
不会覆盖。历史页只维护Run，不提供普通导入导出入口。

Data Table 与普通 Step 一样录制。每行需要独立初始化时使用 Outline/Examples。日常使用
不需要手工修改 Request、Plan 或 Transaction；协议和跨机器迁移见
[维护/3.Recorder设计](维护/3.Recorder设计.md)。

## 代码中的参数流向

以这句 Feature 为例：

```gherkin
When 在记事本输入预设文本
```

参数流向：

```text
业务语句
  -> step_input_notepad(context)
  -> page.input_note()
  -> self.input_text("$notepad_editor", "$notepad_text", use_paste=True)
  -> get_locator("$notepad_editor") 严格找 locator
  -> get_data("$notepad_text") 严格找 data
  -> input_text(context, locator, "Hello BDD Autowork", use_paste=True)
```

这就是框架降低脚本复杂度的核心：feature 只表达业务，Page Object 只调用统一入口，定位和数据交给 YAML。

长期脚本应在 Page Object 中使用 `$` 引用资源，避免 key 拼错被当成直接文本：

```python
self.input_text("$notepad_editor", "$notepad_text", use_paste=True)
self.assert_attr_contains("$notepad_editor", "value", "$notepad_text")
```

如果确实要输入 `$` 开头的字面量，使用 `$$` 转义，例如 `"$$100"` 会作为 `$100`。

显式资源引用：

| 写法 | 含义 |
| --- | --- |
| `$save_button` | 按参数类型严格读取 locator 或 data |
| `$loc:save_button` | 强制读取 locator |
| `$data:customer_name` | 强制读取 data |
| `$$100` | 字面量 `$100` |

## 常见写法

### 页面动作组合

```python
def create_customer(self, name_key, email_key):
  self.input_text("$customer_name_input", name_key)
  self.input_text("$customer_email_input", email_key)
  self.click("$save_button")
  self.wait_visible("$save_success_message", timeout=10)
```

### 跨页面流程

少量跨页面流程可以先在 step 中组合：

```python
@when('创建记录并打开详情')
def step_create_record_and_open_detail(context):
  main = get_page(context, MainWindowPage)
  detail = get_page(context, DetailWindowPage)
  main.create_record("$record_name")
  detail.open_record("$record_name")
```

如果流程越来越多，再考虑增加 `Bdd/flows/` 这类流程层。

### 临时 locator

调试时可以直接传临时 locator：

```python
self.click("root=notepad_window|ocr=File")
self.click({"root": "notepad_window", "by": "xpath", "value": "//Button[@name='保存']"})
```

稳定后建议沉淀到 `Bdd/locators/*.yaml`。

## 编写检查清单

提交脚本前检查：

- feature 是否描述业务，而不是控件点击顺序。
- step 是否足够薄，只调用 Page Object。
- WindowPage 是否声明了正确的 `root_locator_file`、`root_locator` 和 data。
- WindowView 是否只使用所属窗口包中的 locator。
- locator 文件名是否真实存在；不存在会 fail-fast。
- 视觉定位是否限定了 `region`。
- data key 是否有业务含义。
- 本地 runner 是否指向正确 feature。
- 调试参数是否只放在 `settings_overrides`，没有污染 `config.yaml`。
- 失败时是否先按问题查 [5.故障排查](5.故障排查.md)，而不是增加固定等待。
